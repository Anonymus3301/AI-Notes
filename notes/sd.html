The four-step framework in detail

Step Typical time (45 min) What you do What the interviewer is looking for
1. Requirements 5 min Ask questions; split functional from non-functional; agree on scope That you do not start drawing before understanding the problem
2. Estimates 5 min Rough users, QPS, storage, bandwidth That you size the system and know whether it needs 1 server or 1,000

Functional requirements say what the system does ("a user can post, follow, and see a feed"). Non-functional requirements say how well: availability, latency, consistency, durability, scalability, cost, security. Interviews are mostly decided by non-functional reasoning.

Questions worth asking at the start.

  • Who are the users and how many (daily active users)? Is traffic read-heavy or write-heavy?
  • What are the core features for this session? What is explicitly out of scope?
  • What latency is acceptable? Is stale data acceptable for any feature?
  • Is the system global or single-region? Are there compliance constraints?
  • Which matters more here: consistency or availability?

Interview tip. Say your assumptions out loud and write them on the board. "I will assume 50 million daily users and a 100:1 read to write ratio; tell me if that is off." That turns a guess into a shared contract and shows structure.

S1Load balancing, caching, CDN

In one line: load balancers spread traffic over many servers, caches keep hot data in memory, and CDNs serve static content from servers near the user.

Analogy. A supermarket: many checkout counters (servers), a manager directing the queue (load balancer), popular items stacked by the entrance (cache), and branch stores in every neighbourhood (CDN).

Why it matters in interviews. These three components appear in almost every design. Interviewers expect you to place them correctly, explain the policy you chose (which algorithm, which cache strategy, which TTL), and name what can go wrong (hot keys, stampedes, stale data).

Core ideas

Scaling up vs out. Vertical scaling means a bigger machine: simple, but it has a ceiling and a single point of failure. Horizontal scaling means more machines: nearly unlimited, but needs a load balancer and stateless servers. Keep session state out of app servers (in a shared cache or a signed token) so any server can handle any request.

Load balancer (LB) basics. A LB receives client traffic and forwards each request to a healthy backend. It performs health checks (periodically probing backends and removing failed ones), can terminate TLS, and can add retries and timeouts.

Layer Routes by Typical use
L4 (transport) IP address and port Fast, simple, any TCP/UDP traffic
L7 (application) URL path, headers, cookies Path-based routing (/api vs /static), A/B tests, canary releases

LB algorithms.

Algorithm How it picks Good for Weakness
Round robin Next server in turn Equal servers, similar requests Ignores load
Weighted round robin Turns proportional to capacity Mixed server sizes Static weights
Least connections Fewest active connections Long or uneven requests Needs connection tracking
IP hash / consistent hashing Hash of client or key Affinity, caches, sharded backends Hot keys can overload one node
Random of two choices Sample two, pick the less loaded Surprisingly good load spread Needs load info

Sticky sessions pin a user to one server (via cookie or IP hash). They are a workaround for stateful servers and complicate failover. Prefer stateless servers.

Avoiding the LB as a single point of failure. Run LBs in pairs (active-passive with a floating IP, or active-active), and use DNS or global server load balancing to spread traffic across regions.

Caching layers. A request can be answered at many levels, each cheaper than the next:

Layer Example Notes
Browser HTTP cache headers Free for the server; hard to invalidate
CDN edge Images, JS, video, cacheable API responses Near users; global
Application cache Redis, Memcached Shared by app servers; sub-millisecond
Local in-process cache A dictionary or LRU in each server Fastest; not shared, so copies can diverge
Database Buffer pool, query cache Automatic; limited

Cache strategies.

Strategy Write path Read path Pros Cons
Cache-aside (lazy) App writes DB, then deletes or updates cache App checks cache, on miss loads from DB and fills cache Simple; only hot data cached First read is slow; stale window
Read-through Same as cache-aside but the cache library loads the data Cache loads on miss Cleaner app code Cache must know the DB
Write-through App writes to cache, cache writes to DB synchronously Reads hit cache Cache always fresh Higher write latency
Write-back (write-behind) App writes to cache; DB updated later in batches Reads hit cache Very fast writes Data loss risk if cache dies

Eviction policies. LRU (least recently used) is the default workhorse; LFU (least frequently used) favours consistently popular items; TTL expires items after a set time regardless of use; FIFO and random exist but are rarely best.

Why hit ratio matters. Suppose a cache hit takes 1 ms and a miss costs 1 ms plus a 20 ms database read. At a 95% hit ratio the average latency is 0.95 × 1 + 0.05 × 21 = 2.0 ms; at 80% it is 0.8 × 1 + 0.2 × 21 = 5.0 ms. More importantly, at 95% only 5% of traffic reaches the database, so the database can be 20 times smaller.

Cache problems and fixes.

Problem What happens Fix
Stampede (thundering herd) A hot key expires and thousands of requests hit the DB together Request coalescing (one loader, others wait), jittered TTLs, early refresh
Penetration Requests for keys that do not exist always miss and hit the DB Cache "not found" for a short time; Bloom filter in front
Hot key One key gets enormous traffic and overloads one cache node Local in-process copy, key replication (key#1..#N)
Stale data Cache and DB disagree Short TTL, invalidate on write, accept eventual consistency where harmless
Avalanche Many keys expire at once Randomise TTLs, stagger warm-up

CDN basics. A content delivery network keeps copies of content at edge locations worldwide. Pull CDN: the edge fetches from your origin on first request and caches it. Push CDN: you upload content to the CDN ahead of time. Control freshness with Cache-Control: max-age=... and versioned file names (app.3f9c1.js), so a new release gets a new URL and never needs purging. CDNs also absorb traffic spikes and DDoS and shorten TLS handshakes.

Code

import json, redis
r = redis.Redis()

def get_user(user_id: int, db) -> dict:
    key = f"user:{user_id}"
    if (hit := r.get(key)) is not None:
        return json.loads(hit)                         # cache hit
    user = db.fetch_user(user_id)                     # cache miss
    r.setex(key, 300, json.dumps(user))               # TTL 5 minutes
    return user

Reading the code. This is cache-aside. r.get returns None on a miss. On a miss we read the database and store the result with setex (set with expiry), so it disappears after 300 seconds. The walrus operator := assigns and tests in one line.

Fixing three weaknesses at once: jittered TTL, negative caching, and single-flight loading.

import json, random, threading

_locks: dict[str, threading.Lock] = {}
_locks_guard = threading.Lock()

def _lock_for(key: str) -> threading.Lock:
    with _locks_guard:
        return _locks.setdefault(key, threading.Lock())

def get_user_safe(user_id: int, db) -> dict | None:
    key = f"user:{user_id}"
    if (hit := r.get(key)) is not None:
        return json.loads(hit)                       # may be the cached "null"
    with _lock_for(key):                             # only one thread loads per key
        if (hit := r.get(key)) is not None:          # re-check: someone may have filled it
            return json.loads(hit)
        user = db.fetch_user(user_id)                # None if the user does not exist
        ttl = (60 if user is None else 300) + random.randint(0, 30)   # shorter for "not found", plus jitter
        r.setex(key, ttl, json.dumps(user))          # json.dumps(None) is "null"
        return user

The per-process lock coalesces requests inside one server. Across many servers you would use a short-lived Redis lock (SET key value NX EX 5) or let one server refresh while others serve slightly stale data.

An LRU cache from scratch (a classic interview question; OrderedDict makes it short):

from collections import OrderedDict

class LRUCache:
    def __init__(self, capacity: int):
        self.capacity, self.data = capacity, OrderedDict()

    def get(self, key):
        if key not in self.data:
            return None
        self.data.move_to_end(key)               # mark as most recently used
        return self.data[key]

    def put(self, key, value):
        if key in self.data:
            self.data.move_to_end(key)
        self.data[key] = value
        if len(self.data) > self.capacity:
            self.data.popitem(last=False)        # evict the least recently used

c = LRUCache(2)
c.put("a", 1); c.put("b", 2); c.get("a"); c.put("c", 3)   # evicts "b"
print(list(c.data))                                        # ['a', 'c']

Both operations are O(1). The same idea can be built by hand with a hash map plus a doubly linked list, which interviewers often ask you to draw.

Cache-Control: public, max-age=300, stale-while-revalidate=60     # shared caches may keep it 5 min
Cache-Control: private, no-store                                   # never cache (personal data)

Traps

Trap. Cache stampede: a hot key expires and 10,000 requests hit the DB at once. Use request coalescing, jittered TTLs, or early refresh.

Trap. Forgetting cache invalidation on writes. Decide explicitly: delete the key on update, or accept staleness up to the TTL, and say so.

Trap. Caching personalised or private responses in a shared CDN. Use private or no-store, or vary by user.

Trap. Using sticky sessions as the main design. A server crash then logs out its users. Store session state centrally.

Trap. Drawing a single load balancer box as if it cannot fail. Mention redundancy.

Practice

  1. A site has a 90% cache hit ratio, 2 ms hits, and 30 ms misses (plus the cache lookup). What is the average latency? What if the hit ratio rises to 99%?
  2. Which cache strategy would you choose for (a) a product catalogue, (b) a shopping cart, (c) a like counter? Explain.
  3. Sketch how you would serve a viral image to 10 million users in an hour.
Show answers
  1. Treat a miss as 2 ms + 30 ms = 32 ms. At 90%: 0.9 × 2 + 0.1 × 32 = 5.0 ms. At 99%: 0.99 × 2 + 0.01 × 32 = 2.3 ms; the database load also falls tenfold.
  2. (a) Cache-aside with a TTL; reads dominate and slight staleness is fine. (b) Write-through or a durable store, because losing a cart hurts. (c) Write-back or buffered counters (increment in Redis, flush periodically); small loss or lag is acceptable.
  3. Upload once to object storage, serve through a CDN with a long max-age and a versioned URL; origin sees only a few misses per edge location, and the CDN absorbs the spike.

Check yourself

Why must app servers be stateless to scale horizontally?

If a server keeps user state locally, a request must return to that same server. Stateless servers let the load balancer send any request anywhere and let you add or remove servers freely.

What is the difference between L4 and L7 load balancing?

L4 forwards connections based on IP and port and does not look at the content; L7 understands HTTP and can route by path, header, or cookie.

S2SQL vs NoSQL, sharding, replication

In one line: SQL gives schemas, joins, and transactions; NoSQL trades some of that for flexible schemas and easy horizontal scale; replication copies data for reads and failover; sharding splits data across machines.

Analogy. Replication is photocopying the phone book for every office. Sharding is splitting it into A–M and N–Z books kept in different offices.

Why it matters in interviews. The database choice and the data-scaling story are the heart of most designs. You are expected to justify SQL or NoSQL with the access patterns, then explain how it grows past one machine and what happens when a node dies.

Core ideas

ACID and BASE. Relational databases typically provide ACID transactions: Atomicity (all or nothing), Consistency (constraints hold), Isolation (concurrent transactions do not corrupt each other), Durability (committed data survives crashes). Many NoSQL systems follow BASE ideas: Basically Available, Soft state, Eventually consistent, favouring availability and scale.

Choosing a database from the access pattern.

Pick When Examples
Relational (Postgres, MySQL) Transactions, relations, ad-hoc queries, strong consistency Payments, orders, users
Key-value (Redis, DynamoDB) Simple lookups by key at huge scale, low latency Sessions, carts, URL mappings
Document (MongoDB) Nested, evolving records read as a unit Product catalogues, profiles
Wide-column (Cassandra, HBase) Massive write throughput, time series, known query patterns Messages, metrics, activity logs
Graph (Neo4j) Relationship traversal Recommendations, social graph queries
Search (Elasticsearch) Full-text search and aggregations Product search, logs
Object storage (S3) Large blobs Images, video, backups

A strong answer often uses polyglot persistence: several stores, each chosen for one job.

Indexes. An index trades extra storage and slower writes for faster reads. B-tree indexes (common in relational databases) support range queries and sorted scans. LSM-tree storage engines (Cassandra, RocksDB) turn random writes into sequential ones, giving high write throughput at the cost of read amplification, softened by Bloom filters and compaction.

Normalisation vs denormalisation. Normalised schemas avoid duplication and keep updates simple but need joins. Denormalised schemas copy data to make reads fast, at the cost of keeping copies in sync. At large scale, joins across shards are expensive, so denormalising is common.

Replication. Keep copies of the data on several machines.

Pattern Description Trade-offs
Leader–follower One leader takes writes; followers copy changes and serve reads Simple; read scaling; replication lag; failover needed
Multi-leader Several nodes accept writes (often one per region) Low write latency per region; conflict resolution needed
Leaderless Any replica takes reads and writes; quorums decide (Dynamo style) High availability; tunable consistency; complexity

Synchronous replication waits for followers (safer, slower); asynchronous does not (faster, but a leader crash can lose the last writes). A common compromise is one synchronous follower and the rest asynchronous. Replication lag means a follower may briefly return old data, so a user who just edited their profile might not see it. Fix with read-your-writes: route that user's reads to the leader for a short time, or track a write timestamp.

Failover. When the leader dies, a follower is promoted (manually or by an automated election). Risks: losing recent writes, two nodes both believing they are leader (split brain), and clients still pointing at the old leader.

Sharding (partitioning). Split data horizontally so each shard holds a subset of rows. You need a shard key and a rule mapping keys to shards.

Strategy Rule Pros Cons
Range Key ranges (A–M, N–Z; date ranges) Range queries are easy Hot spots (all new data hits the latest range)
Hash hash(key) mod N or consistent hashing Even spread Range queries span shards
Directory (lookup table) A service maps keys to shards Flexible, easy rebalancing Lookup is a dependency and bottleneck
Geographic By user region Data locality, compliance Uneven load; cross-region users

Choosing a shard key. It should have high cardinality, spread load evenly, and match the most common query so that most queries touch one shard. A bad key (for example country, or a timestamp) creates hot shards. Celebrity users can create hot keys even with a good hash.

Resharding. Adding shards must not move most of the data. Plain hash mod N moves almost everything when N changes (shown in the code below); consistent hashing moves only about 1/N of the keys.

Cross-shard operations. Joins and transactions across shards are costly. Options: design so related data lives on the same shard (shard orders by user_id), denormalise, run scatter-gather queries and merge results, or use distributed transaction patterns such as two-phase commit (strong but slow and blocking) or sagas (a chain of local transactions with compensating actions).

Generating unique ids across shards. Auto-increment does not work globally. Options: UUIDs (no coordination but not sortable and large), a ticket server, or time-ordered ids such as Snowflake (timestamp + machine id + sequence).

Code

import hashlib
SHARDS = ["db-0", "db-1", "db-2", "db-3"]
def shard_for(user_id: str) -> str:
    return SHARDS[int(hashlib.md5(user_id.encode()).hexdigest(), 16) % len(SHARDS)]

Reading the code. MD5 turns the id into a large integer that is spread evenly; the remainder after dividing by the number of shards picks one. Python's built-in hash() is randomised per process for strings, which is why a stable hash such as MD5 is used here.

Measuring the resharding problem:

import hashlib

def h(key: str) -> int:
    return int(hashlib.md5(key.encode()).hexdigest(), 16)

keys = [f"user{i}" for i in range(100_000)]
moved = sum(1 for k in keys if h(k) % 4 != h(k) % 5)
print(f"modulo 4 -> 5 shards: {moved / len(keys):.0%} of keys move")   # about 80%

Consistent hashing with virtual nodes (keys and servers are placed on a ring; a key belongs to the next server clockwise):

import bisect, hashlib

class ConsistentHash:
    def __init__(self, nodes=(), vnodes=100):
        self.vnodes, self.ring, self.owner = vnodes, [], {}
        for n in nodes:
            self.add(n)

    @staticmethod
    def _h(s: str) -> int:
        return int(hashlib.md5(s.encode()).hexdigest(), 16)

    def add(self, node: str):
        for i in range(self.vnodes):                 # many points per node smooths the load
            p = self._h(f"{node}#{i}")
            bisect.insort(self.ring, p)
            self.owner[p] = node

    def remove(self, node: str):
        for i in range(self.vnodes):
            p = self._h(f"{node}#{i}")
            self.ring.remove(p)
            del self.owner[p]

    def get(self, key: str) -> str:
        i = bisect.bisect(self.ring, self._h(key)) % len(self.ring)   # wrap around the ring
        return self.owner[self.ring[i]]

ch = ConsistentHash(["db-0", "db-1", "db-2", "db-3"])
before = {k: ch.get(k) for k in keys}
ch.add("db-4")
moved = sum(1 for k in keys if ch.get(k) != before[k])
print(f"consistent hashing 4 -> 5 nodes: {moved / len(keys):.0%} of keys move")   # roughly 15-20%, close to the ideal 1/5

Only the keys that now fall between the new node's points and their predecessors move, about 1/5 of the data in theory (a run with 100 virtual nodes per server typically lands in the 15–20% range), all of it onto the new node.

A tiny read-your-writes router:

import time

class Router:
    def __init__(self, leader, followers):
        self.leader, self.followers = leader, followers
        self.last_write = {}                          # user_id -> time of last write

    def write(self, user_id, sql, args):
        self.last_write[user_id] = time.monotonic()
        return self.leader.execute(sql, args)

    def read(self, user_id, sql, args, lag_budget=5.0):
        recent = time.monotonic() - self.last_write.get(user_id, -1e9) < lag_budget
        db = self.leader if recent else self.followers[hash(user_id) % len(self.followers)]
        return db.execute(sql, args)

Traps

Trap. Modulo sharding reshuffles almost every key when you add a shard. Use consistent hashing or a lookup directory.

Trap. Sharding too early. A single well-indexed Postgres with read replicas handles a lot. Say when you would shard and what triggers it (data size, write throughput).

Trap. Choosing a shard key that matches no query. Every query then fans out to all shards.

Trap. Forgetting replication lag when reading from followers right after a write.

Trap. Claiming NoSQL is automatically "more scalable". Scale comes from partitioning and access-pattern design, not from the label.

Practice

  1. You are designing an e-commerce order database. Which shard key would you choose, and which queries become expensive?
  2. A leader–follower setup has 1 second average replication lag. A user posts a comment and immediately reloads, but does not see it. Give two fixes.

Show answers
  1. user_id: "my orders" queries hit one shard. Queries by order_id alone, or reports across all users, become scatter-gather; mitigate with a secondary lookup (order_id → user_id) and an analytics warehouse.
  2. Read-your-writes by routing that user's reads to the leader for a few seconds, or return the new comment directly from the write response and merge it client-side; alternatively use synchronous replication for that path.

Check yourself

When would you pick Cassandra over Postgres?

When you need very high write throughput and horizontal scale across many nodes with known query patterns (for example time-series or messages), and you can live without joins and multi-row transactions.

What is the difference between replication and sharding?

Replication copies the same data to several nodes (availability and read scale). Sharding splits different data across nodes (capacity and write scale). Real systems use both.

S3Consistency models and CAP

In one line: during a network partition you must choose between consistency (everyone sees the latest write) and availability (everyone gets an answer); outside partitions, the real trade-off is latency vs consistency (PACELC).

Analogy. Two bank branches lose their phone line. Either they stop serving withdrawals (consistent) or keep serving and reconcile later (available, risk of overdraft).

Why it matters in interviews. "Which consistency do you need here, and why?" is a favourite follow-up. A good answer is feature-specific, names the model, and explains the user-visible effect and the cost.

Core ideas

The three letters of CAP.

  • Consistency (C): every read sees the most recent write (in the linearizable sense), as if there were a single copy.
  • Availability (A): every request to a working node gets a non-error response.
  • Partition tolerance (P): the system keeps working when the network drops or delays messages between nodes.

Partitions will happen in any distributed system, so P is not optional. The real choice appears during a partition: refuse some requests to stay consistent (CP), or answer with possibly stale data to stay available (AP). Without a partition you can have both.

PACELC. CAP says nothing about normal operation. PACELC adds: if there is a Partition, choose A or C; Else (normal operation), choose Latency or Consistency. Waiting for more replicas to confirm makes writes more consistent and slower. This is why "AP vs CP" is too coarse; Martin Kleppmann's essay argues the labels are often misleading.

The consistency spectrum (strongest to weakest):

Model Guarantee Example use
Strong / linearizable Reads see the latest write; operations appear in one global order Bank balances, leader election, inventory for the last item
Sequential All see the same order, but not necessarily real-time order Some coordination services
Causal If A caused B, everyone sees A before B Comments and replies
Read-your-writes You see your own updates Profile edits, posting a comment
Monotonic reads You never see data go backwards in time Timelines
Eventual Replicas converge if writes stop Like counts, view counts, feeds

Quorums. With N replicas, a write waits for W acknowledgements and a read queries R replicas. If R + W > N, every read overlaps with the latest write, so it can find the newest version. Typical N = 3: W = 2, R = 2 gives strong-ish reads and tolerates one failure. W = 1, R = 1 is fast but only eventually consistent. Quorums alone are not full linearizability (concurrent writes, sloppy quorums, and clock issues can still cause anomalies).

N W R R + W > N? Behaviour
3 2 2 yes (4 > 3) Reads see latest writes; survives 1 node failure
3 3 1 yes (4 > 3) Fast reads, writes fail if any node is down
3 1 3 yes (4 > 3) Fast writes, slow reads
3 1 1 no (2 < 3) Fastest; may read stale data

Resolving conflicts when replicas accept concurrent writes: last write wins (simple, but silently drops data and relies on clocks), vector clocks (detect concurrent updates and hand both versions to the application), or CRDTs (data structures designed to merge automatically, such as counters and sets).

Consensus. To get strong consistency across replicas, systems use consensus protocols (Raft, Paxos) to elect a leader and agree on an ordered log. These need a majority of nodes alive, which is why clusters have 3 or 5 nodes. Coordination services (etcd, ZooKeeper) package this for leader election and configuration.

Different features, different guarantees. A single product mixes models: payments strong, profile edits read-your-writes, feed and like counts eventual. State that in the interview.

A small quorum simulation shows why R + W > N matters:

import random

class Replica:
    def __init__(self):
        self.value, self.version = None, 0

def write(replicas, value, version, w):
    acked = 0
    for rep in random.sample(replicas, len(replicas)):     # random order simulates arrival
        if acked == w:
            break                                           # remaining replicas miss the update
        rep.value, rep.version = value, version
        acked += 1

def read(replicas, r):
    picked = random.sample(replicas, r)
    return max(picked, key=lambda rep: rep.version).value  # newest version among r replicas

def stale_rate(n, w, r, trials=20_000):
    stale = 0
    for _ in range(trials):
        reps = [Replica() for _ in range(n)]
        write(reps, "old", 1, n)                            # everyone has v1
        write(reps, "new", 2, w)                            # only w replicas get v2
        stale += read(reps, r) != "new"
    return stale / trials

for n, w, r in [(3, 2, 2), (3, 1, 1), (3, 1, 2), (3, 3, 1)]:
    print(f"N={n} W={w} R={r}: stale reads {stale_rate(n, w, r):.1%}")

S4Message queues and event-driven design

In one line: queues and logs decouple producers from consumers, smooth traffic spikes, and let slow work happen in the background — at the cost of eventual consistency and duplicate handling.

Analogy. A restaurant order rail. The waiter clips tickets on the rail and moves on; cooks pull tickets at their own pace. If the kitchen is slow, tickets pile up instead of the waiter freezing.

Why it matters in interviews. Whenever a step is slow, spiky, or can fail independently (sending email, resizing images, updating analytics), the right answer is "put it on a queue". You are then expected to discuss delivery guarantees, ordering, retries, and what happens to messages that keep failing.

Core ideas

Why use a queue.

  • Decoupling: producer and consumer evolve and scale independently.
  • Load levelling: a spike becomes a backlog processed at a steady rate.
  • Resilience: if a consumer is down, messages wait instead of being lost.
  • Fan-out: one event can trigger many independent consumers.

Three messaging styles.

Style How it works Examples Use for
Work queue Each message is processed by one worker; deleted after success SQS, RabbitMQ Background jobs
Pub/sub Each subscriber gets its own copy of every message SNS, Google Pub/Sub Notifying many services
Log (stream) Append-only, ordered, replayable; consumers track their own position (offset) Kafka, Kinesis Event streams, analytics, rebuilding state

Kafka vocabulary. A topic is split into partitions. Order is guaranteed within a partition, not across the topic. Producers choose the partition, usually by hashing a key (such as user_id), so all events for one user stay in order. A consumer group shares the work: each partition is read by exactly one consumer in the group, so the number of partitions caps the parallelism. Messages stay for a retention period and can be replayed.

Delivery semantics.

Guarantee Meaning How it happens
At-most-once A message may be lost, never duplicated Acknowledge before processing
At-least-once Never lost, may be duplicated Acknowledge after processing; retries on failure
Exactly-once Processed once Hard in general; in practice, at-least-once delivery plus idempotent processing (effectively once), or transactional features within one system

The practical rule: assume at-least-once and make consumers idempotent. Process the same message twice and the result must be the same, for example by recording a processed message id with a unique constraint.

Acknowledgement and visibility timeout. In SQS-style queues, a received message becomes invisible for a set time. If the worker deletes it (acknowledges) in time, it is done; if not, the message reappears and another worker retries. Set the timeout longer than the typical processing time.

Dead-letter queue (DLQ). After a message fails a set number of times (a poison message), move it to a DLQ for inspection instead of retrying forever and blocking progress. Alert on DLQ depth.

Backpressure. If producers outrun consumers, the queue grows without bound. Options: add consumers (autoscale on queue depth), rate-limit producers, drop or sample low-value work, or reject new requests with a clear error.

Ordering. Global ordering does not scale. Ask what order is actually needed (usually per user or per conversation) and use a partition key for that.

The dual-write problem and the outbox pattern. Writing to the database and publishing a message are two operations; a crash between them leaves them inconsistent. The transactional outbox fixes it: in one database transaction, write the business row and an "outbox" row; a separate relay reads the outbox and publishes to the queue, marking rows as sent. Delivery is at-least-once, so consumers are idempotent.

Sagas. For a business process across services (reserve stock → charge card → create shipment), each step is a local transaction; if one fails, run compensating actions (release stock, refund). Either choreography (services react to each other's events) or orchestration (a coordinator drives the steps).

Event sourcing and CQRS (brief). Event sourcing stores the sequence of events as the source of truth and rebuilds state by replaying them. CQRS separates the write model from read models optimised for queries. Powerful but complex; mention them where an audit trail or multiple read views justify the cost.

S5Rate limiting, retries, circuit breakers

In one line: protect your system from too much traffic (rate limiting), recover from transient failures (retries with backoff), and stop hammering something that is down (circuit breakers).

Analogy. A nightclub doorman (rate limiter), someone redialling a busy number with growing pauses (retry), and a fuse box that trips to protect the house (circuit breaker).

Why it matters in interviews. "What happens when a dependency is slow or down?" and "How do you stop one user from overloading the service?" are standard probes. Naming the right pattern and its failure modes shows you have operated real systems.

Core ideas

Why rate limit. To prevent abuse and noisy neighbours, protect downstream dependencies, control cost, and keep fair usage across customers. Place it at the API gateway or edge, plus finer limits inside services. Return HTTP 429 Too Many Requests with a Retry-After header and, if useful, headers showing the limit and remaining quota.

Rate-limiting algorithms.

Algorithm Idea Pros Cons
Fixed window Count requests per calendar window (for example per minute) Trivial, cheap Bursts at window edges (up to 2× the limit across a boundary)
Sliding window log Store a timestamp per request; count those in the last N seconds Accurate Memory per user grows with the limit
Sliding window counter Weighted blend of current and previous window counts Accurate enough, tiny memory Approximation
Token bucket Bucket refills at a steady rate up to a capacity; each request takes a token Allows controlled bursts; simple Two parameters to tune
Leaky bucket Requests enter a queue drained at a fixed rate Smooth output rate Bursts get delayed or dropped

Token bucket is the most common interview answer: the rate sets the long-run average, the capacity sets the largest burst.

Distributed rate limiting. If many gateway nodes serve the same user, the counter must be shared, usually in Redis. Keep the check-and-update atomic (a Lua script or INCR with EXPIRE) to avoid races. For very high scale, allow slight over-limit with local counters synced periodically.

Limit by what? User or API key, IP address, endpoint, or tenant, often several at once (for example 100/min per user and 10,000/min per tenant).

Retries. Retry only transient failures (timeouts, 429, 5xx), only idempotent operations (or with an idempotency key), with exponential backoff and jitter, and a maximum attempt count and total time. Without these, retries amplify outages.

Retry amplification. If each of 3 layers retries 3 times, one user request can become 27 calls to the bottom service during an outage. Retry at one layer, or use a retry budget (for example, retries may be at most 10% of requests).

Timeouts and deadlines. Every network call needs a timeout. Propagate an overall deadline down the call chain so lower services stop work for requests the caller has already abandoned.

Circuit breaker. Wraps calls to a dependency and tracks failures.

State Behaviour
Closed Calls pass through; failures are counted
Open After too many failures, calls fail immediately (no waiting on a dead service) for a cool-off period
Half-open After the cool-off, let a few trial calls through; success closes the circuit, failure reopens it

Other resilience patterns.

  • Bulkheads: separate thread or connection pools per dependency so one slow service cannot exhaust everything.
  • Fallbacks: return cached data, a default, or a degraded feature when a dependency fails.
  • Load shedding: under overload, reject low-priority requests early to protect the important ones.
  • Graceful degradation: keep core features (checkout) running when extras (recommendations) are down.
  • Idempotency keys: make retried writes safe (chapter S4).

  [*] --> Closed
  Closed --> Open: failures exceed threshold
  Open --> HalfOpen: cool-off timer ends
  HalfOpen --> Closed: trial calls succeed
  HalfOpen --> Open: trial call fails

import time

class TokenBucket:
    def __init__(self, rate: float, capacity: int):
        self.rate, self.capacity = rate, capacity
        self.tokens, self.last = capacity, time.monotonic()
    def allow(self) -> bool:
        now = time.monotonic()
        self.tokens = min(self.capacity, self.tokens + (now - self.last) * self.rate)
        self.last = now
        if self.tokens >= 1:
            self.tokens -= 1
            return True
        return False

bucket = TokenBucket(rate=5, capacity=10)   # 5 req/s steady, bursts of 10
print([bucket.allow() for _ in range(12)])  # first 10 True, then False

Reading the code. On each call we first refill: elapsed seconds × rate tokens are added, capped at capacity. Then we spend one token if available. Using time.monotonic() (not wall-clock time) protects against clock changes. This lazy refill needs no background timer. The first 10 calls succeed (the burst), the next fail because no time has passed to refill.

Sliding window counter (accurate enough with two integers per user):

import time

class SlidingWindowCounter:
    def __init__(self, limit: int, window: float = 60.0):
        self.limit, self.window = limit, window
        self.curr_start = time.monotonic()
        self.curr, self.prev = 0, 0

    def allow(self) -> bool:
        now = time.monotonic()
        elapsed = now - self.curr_start
        if elapsed >= self.window:                     # roll the window forward
            self.prev = self.curr if elapsed < 2 * self.window else 0
            self.curr, self.curr_start, elapsed = 0, now, 0.0
        weight = 1 - elapsed / self.window             # how much of the previous window still counts
        estimated = self.prev * weight + self.curr
        if estimated >= self.limit:
            return False
        self.curr += 1
        return True

A shared limiter in Redis (fixed window with atomic INCR; simple and race-free because INCR is atomic):

import redis
r = redis.Redis()

def allow(user_id: str, limit: int = 100, window_s: int = 60) -> bool:
    key = f"rl:{user_id}:{int(time.time() // window_s)}"   # one key per window
    count = r.incr(key)
    if count == 1:
        r.expire(key, window_s)                            # clean up after the window
    return count <= limit

(There is a tiny gap between incr and expire; a Lua script or SET key 0 EX window NX first removes it.)

A circuit breaker with all three states:

import time

class CircuitOpen(Exception): ...

class CircuitBreaker:
    def __init__(self, max_failures=5, reset_after=30.0):
        self.max_failures, self.reset_after = max_failures, reset_after
        self.failures, self.opened_at, self.state = 0, 0.0, "closed"

    def call(self, fn, *args, **kwargs):
        if self.state == "open":
            if time.monotonic() - self.opened_at < self.reset_after:
                raise CircuitOpen("failing fast")
            self.state = "half_open"                       # allow one trial call
        try:
            result = fn(*args, **kwargs)
        except Exception:
            self.failures += 1
            if self.state == "half_open" or self.failures >= self.max_failures:
                self.state, self.opened_at = "open", time.monotonic()
            raise
        self.failures, self.state = 0, "closed"            # success resets everything
        return result

Retry with exponential backoff, full jitter, and a deadline:

import random, time

def call_with_retries(fn, max_attempts=5, base=0.2, cap=5.0, deadline_s=10.0):
    start = time.monotonic()
    for attempt in range(max_attempts):
        try:
            return fn()
        except TransientError:                               # your own exception for retryable errors
            if attempt == max_attempts - 1 or time.monotonic() - start > deadline_s:
                raise
            time.sleep(random.uniform(0, min(cap, base * 2 ** attempt)))   # full jitter

Traps

Trap. Retrying non-idempotent writes (like "charge card") without an idempotency key. You will double-charge customers.

Trap. Retry storms: all clients retry at the same moment after a failure, re-crashing the service. Use jitter and caps.

Trap. Per-node rate limiters that are not shared. With 10 gateway nodes each allowing 100/min, the real limit is up to 1,000/min.

Trap. Fixed-window limiters allow 2× bursts around the boundary. Mention sliding windows or token bucket.

Trap. A circuit breaker with no fallback. Failing fast is only useful if the caller does something sensible (cached data, a friendly error).

Check yourself

What is the difference between token bucket and leaky bucket?

Token bucket permits bursts up to its capacity and then enforces an average rate. Leaky bucket smooths output to a constant rate by queueing, so bursts are delayed rather than allowed through.

Why does a half-open state exist?

To test whether the dependency has recovered using a few trial calls, instead of either staying closed forever or flooding a recovering service with full traffic.

S6Back-of-envelope estimation

In one line: turn vague scale (“50 million users”) into QPS, storage, and bandwidth with round numbers, so the design fits reality.

Analogy. A caterer estimating how much rice to cook: guests × portion × buffer. You do not need to be exact, just within the right order of magnitude.

Why it matters in interviews. Estimates decide your design: 100 requests per second fits on one machine, 100,000 does not. Doing the arithmetic quickly and out loud shows you ground design in numbers rather than vibes.

Core ideas

The recipe.

  1. State assumptions: daily active users (DAU), actions per user per day, size per record, read:write ratio, retention period.
  2. Average QPS = actions per day ÷ 86,400 seconds (round to ~100,000 to make mental math easy).
  3. Peak QPS = average × a peak factor (2× to 5×; 3× is a safe default).
  4. Storage = records per day × bytes per record × days kept × replication factor.
  5. Bandwidth = QPS × bytes per request (separately for ingress and egress).
  6. Cache size = about 20% of the daily hot data (the 80/20 rule) or hot-set size × item size.
  7. Servers = peak QPS ÷ QPS per server, with headroom for failures (N+1 or N+2).

A reusable estimator:

from dataclasses import dataclass

@dataclass
class Estimate:
    dau: int
    writes_per_user: float
    reads_per_user: float
    bytes_per_record: int
    years: int = 5
    peak_factor: float = 3.0
    replication: int = 3
    server_qps: int = 2_000
    hot_fraction: float = 0.2

    def report(self) -> dict:
        sec = 86_400
        w_avg = self.dau * self.writes_per_user / sec
        r_avg = self.dau * self.reads_per_user / sec
        records = self.dau * self.writes_per_user * 365 * self.years
        raw_tb = records * self.bytes_per_record / 1e12
        daily_read_gb = self.dau * self.reads_per_user * self.bytes_per_record / 1e9
        return {
            "write_qps_avg": round(w_avg), "write_qps_peak": round(w_avg * self.peak_factor),
            "read_qps_avg": round(r_avg), "read_qps_peak": round(r_avg * self.peak_factor),
            "storage_tb_raw": round(raw_tb, 1), "storage_tb_replicated": round(raw_tb * self.replication, 1),
            "cache_gb": round(daily_read_gb * self.hot_fraction, 1),
            "read_servers_needed": -(-round(r_avg * self.peak_factor) // self.server_qps) + 2,   # +2 spare
        }

print(Estimate(dau=50_000_000, writes_per_user=2, reads_per_user=100, bytes_per_record=500).report())

  • Storage over 5 years: 100M × 60 months = 6 billion records × 500 bytes ≈ 3 TB. Small enough for a handful of nodes.

  • Conclusion: read-heavy and small. A cache plus replicated key-value store suffices; no heroic sharding at first.

Chat app. Assume 500 million DAU sending 40 messages a day, 100 bytes each.

S7Design a URL shortener and a key-value store

In one line: the URL shortener is the classic warm-up (id generation, redirects, read-heavy caching); the key-value store is the classic deep dive (partitioning, replication, and storage engine).

Analogy. The shortener is a coat check: hand over a long coat, get a small ticket. The key-value store is the coat-check room built to hold millions of coats across many rooms without losing any.

Why it matters in interviews. These two problems exercise nearly every building block: estimation, APIs, id generation, caching, database choice, scaling, consistency, and failure handling. If you can narrate them smoothly, you can adapt the same moves to most other prompts.

Part A — URL shortener

Step 1: requirements.

  • Functional: create a short URL from a long one; redirect short to long; optional custom alias; optional expiry; basic click analytics.
  • Non-functional: very low redirect latency; high availability (a dead short link is a broken web page); links are unguessable enough; scale to billions of links.
  • Out of scope unless asked: user accounts, rich dashboards.

Step 2: estimates (from chapter S6): about 40 writes per second, 4,000 reads per second, roughly 3 TB over five years. Read-heavy, small data.

Step 3: API.

POST /api/v1/urls    { "long_url": "...", "alias": "optional", "expires_at": "optional" } -> { "short_url": "https://sho.rt/aZ3x9Q" }
GET  /{code}         -> 301 or 302 redirect to the long URL (404 if unknown or expired)

301 vs 302. A 301 (permanent) can be cached by browsers, so later visits never reach you: less load, but you lose analytics and cannot change the target. A 302 (temporary) is hit every time: more load, accurate analytics and control. Most shorteners use 302 (or 301 with careful cache headers if analytics are not needed).

Step 4: id generation, the core decision. The short code should be short, unique, and hard to guess. A base62 string (0-9a-zA-Z) with 7 characters gives 62⁷ ≈ 3.5 trillion combinations, far more than the 6 billion we need.

Approach How Pros Cons
Hash the URL (MD5/SHA, take the first 7 chars) Deterministic Same URL gives same code Collisions need a retry strategy; custom aliases and per-user links are awkward
Counter → base62 A global incrementing id encoded in base62 No collisions; very short codes Codes are sequential and guessable; the counter is a bottleneck
Counter ranges per server Each app server leases a block (for example 1,000,000 ids) from a coordinator No per-request coordination; fast Lost range if a server dies (acceptable); still sequential unless scrambled
Random 7 chars + uniqueness check Generate random, insert if not exists, retry on conflict Unguessable One extra write attempt on collision
Key generation service (pre-generated keys) A service pre-computes unique keys and hands them out Fast, no collisions at request time Extra component to run

A common good answer: counter ranges leased from a coordination service, then scramble the number with a reversible permutation (or XOR with a secret) before base62 encoding, so codes are unique, compact, and not trivially enumerable.

Step 5: data model. One table: code (primary key) → long_url, created_at, expires_at, owner_id. A key-value or wide-column store (DynamoDB, Cassandra) or a sharded relational table keyed by code fits; access is always by key. Shard by code (hash).

Step 6: read path. Browser → CDN/edge (optional) → load balancer → app server → cache (Redis, key = code) → database on miss. Use cache-aside with a TTL, and cache negative results briefly to protect against scans of nonexistent codes.

Step 7: analytics. Do not write to the analytics store on the redirect path. Emit a click event to a queue (chapter S4) and aggregate asynchronously.

Step 8: abuse and reliability. Rate limit link creation per user (chapter S5), scan for malicious targets, expire unused links, replicate the database across zones, and run multiple app servers behind a load balancer.

Code: base62 encode and decode.

import string
ALPHABET = string.digits + string.ascii_letters      # 0-9, a-z, A-Z  (62 chars)
BASE = len(ALPHABET)

def encode(n: int) -> str:
    if n == 0:
        return ALPHABET[0]
    out = []
    while n:
        n, r = divmod(n, BASE)
        out.append(ALPHABET[r])
    return "".join(reversed(out))

def decode(s: str) -> int:
    n = 0
    for ch in s:
        n = n * BASE + ALPHABET.index(ch)
    return n

print(encode(125_000_000_000), decode(encode(125_000_000_000)))   # a 7-character code, round trip
print(62 ** 7)                                                    # 3,521,614,606,208 possible codes

Scrambling sequential ids so codes are not guessable (a simple invertible multiplicative permutation modulo 62⁷):

SPACE = 62 ** 7
MULT = 2_654_435_761            # must be coprime with SPACE; it is odd and not divisible by 31
assert __import__("math").gcd(MULT, SPACE) == 1

def scramble(n: int) -> int:
    return (n * MULT) % SPACE   # bijection on [0, SPACE): distinct inputs give distinct outputs

code = encode(scramble(1)).rjust(7, "0")

(SPACE = 2⁷ × 31⁷'s analogue here is 62⁷ = 2⁷ × 31⁷, so any multiplier that is odd and not a multiple of 31 is coprime. Pad codes to a fixed length.)

Part B — Key-value store (Dynamo style)

Requirements. put(key, value) and get(key) with low latency, huge scale, high availability, and tunable consistency; nodes can fail and be added without downtime.

Building the design step by step.

  1. Partitioning: spread keys across nodes using consistent hashing with virtual nodes (chapter S2), so adding or removing a node moves only a small share of keys.
  2. Replication: store each key on the next N distinct nodes clockwise on the ring (commonly N = 3), ideally in different racks or availability zones.
  3. Consistency: use quorums: a write succeeds after W acknowledgements, a read consults R replicas, with R + W > N for fresher reads (chapter S3).
  4. Coordinator: any node can receive a request and act as coordinator, forwarding to the replicas responsible for the key.
  5. Failure detection: nodes gossip heartbeats to each other; no single master is needed.
  6. Temporary failures: sloppy quorum with hinted handoff: if a replica is down, another node accepts the write along with a hint and forwards it when the replica returns.
  7. Permanent divergence: anti-entropy with Merkle trees: replicas compare hash trees of their key ranges and sync only the differing parts.
  8. Conflicts: concurrent writes to different replicas are versioned with vector clocks and reconciled by the application or by a rule such as last-write-wins.

Single-node storage engine (LSM tree). Writes are fast because they are sequential.

  • Write path: append the write to a write-ahead log (WAL) on disk for durability, then insert into an in-memory sorted structure (the memtable). When the memtable fills, flush it to disk as an immutable sorted file (an SSTable).
  • Read path: check the memtable, then SSTables from newest to oldest. A Bloom filter per SSTable cheaply says "definitely not here", avoiding disk reads.
  • Compaction: background merging of SSTables removes overwritten and deleted entries and keeps reads fast.
  • Deletes are written as tombstones and cleaned up during compaction.

Code: a toy LSM-flavoured store (memtable, WAL, flush) that shows the shape of the write path:

import json, os

class TinyKV:
    def __init__(self, path="kv_data", memtable_limit=3):
        os.makedirs(path, exist_ok=True)
        self.path, self.limit = path, memtable_limit
        self.memtable, self.sstables = {}, []                 # newest SSTable last
        self.wal = open(os.path.join(path, "wal.log"), "a", encoding="utf-8")

    def put(self, key, value):
        self.wal.write(json.dumps({"k": key, "v": value}) + "\n")
        self.wal.flush(); os.fsync(self.wal.fileno())         # durable before acknowledging
        self.memtable[key] = value
        if len(self.memtable) >= self.limit:
            self._flush()

    def _flush(self):
        table = dict(sorted(self.memtable.items()))           # sorted, immutable "SSTable"
        self.sstables.append(table)
        self.memtable = {}
        open(os.path.join(self.path, "wal.log"), "w").close() # safe to truncate after flush (simplified)

    def get(self, key):
        if key in self.memtable:
            return self.memtable[key]
        for table in reversed(self.sstables):                  # newest first
            if key in table:
                return table[key]
        return None

kv = TinyKV()
for i in range(7):
    kv.put(f"k{i}", i)
kv.put("k1", "new")
print(kv.get("k1"), kv.get("k5"), len(kv.sstables))            # new 5 2

Real engines add Bloom filters, on-disk SSTables with index blocks, multi-level compaction, and WAL replay on restart.

Traps

Trap. Hashing the long URL and truncating without handling collisions. Two different URLs can map to the same 7 characters.

Trap. A single global counter in one database as the id generator. It is a bottleneck and a single point of failure; lease ranges instead.

Trap. Writing analytics synchronously on the redirect path. It adds latency and couples redirect availability to the analytics store.

Trap. Designing the KV store with a master that every request passes through. Use any-node coordination and gossip to avoid a single point of failure.

Trap. Forgetting deletes in an LSM design. Without tombstones, an old value in a lower SSTable reappears.

  2. Base62: 62⁶ ≈ 56.8 billion, so 6 characters just fit, and 7 gives comfortable headroom. Base36: 36⁷ ≈ 78 billion fits 50 billion in 7 characters but with less headroom; 8 characters is safer.

Check yourself

Why is a URL shortener read-heavy and how does that shape the design?

Each link is created once but clicked many times. So the design optimises redirects: caching hot codes, replicated storage, CDN or edge handling, and asynchronous analytics, while writes stay simple.

What does a Bloom filter give an LSM tree?

A fast, memory-light check that says "definitely not in this file" or "maybe", letting the engine skip most disk reads for missing keys.

S8Design a news feed

In one line: the hard question is when to build each user’s timeline — at write time (fan-out on write), at read time (fan-out on read), or a hybrid for celebrities.

Analogy. A newspaper. Fan-out on write is printing and delivering a personalised paper to every subscriber each time a story is filed. Fan-out on read is making every reader walk to the newsroom and assemble their own paper. Hybrid delivers the papers for ordinary writers and lets readers fetch the star columnists themselves.

Why it matters in interviews. The feed is the canonical read-heavy, fan-out-heavy design. The expected insight is the write-vs-read fan-out trade-off and how the celebrity problem breaks the simple answer. It tests caching, sharding, queues, and ranking in one problem.

Core ideas

Step 1: requirements.

  • Functional: publish a post; follow and unfollow; view a home feed of recent posts from people you follow, newest (or ranked) first; infinite scroll.
  • Non-functional: feed loads in well under a second; high availability; eventual consistency is acceptable (a new post may take a few seconds to appear); supports users with millions of followers.

Step 2: estimates. Suppose 300 million DAU opening the feed 10 times a day: 3 billion feed reads per day ≈ 35,000 per second average, 100,000 at peak. If 100 million posts are created per day, that is about 1,160 posts per second. Each user follows about 200 accounts and has about 200 followers on average. Reads outnumber writes by roughly 30:1, so optimise reads.

Step 3: data model.

Entity Key fields Store
Post post_id, author_id, text, media_url, created_at Sharded by author_id or post_id (wide-column or sharded SQL)
Follow graph (follower_id, followee_id), indexed both ways Sharded relational or graph/key-value store
Feed cache user_id → list of post_ids (newest first, capped) Redis sorted sets or lists
Media Image or video files Object storage behind a CDN

Use time-ordered ids (Snowflake-style) so sorting by id is sorting by time.

Step 4: the three strategies.

Strategy On post On feed read Pros Cons
Fan-out on read (pull) Store the post once Fetch recent posts of every followee and merge Cheap writes; no work for inactive users Slow reads (many lookups); heavy at peak
Fan-out on write (push) Push the post id into each follower's feed cache Read one precomputed list Very fast reads Expensive writes for popular authors; wasted work for inactive followers
Hybrid Push for normal users; skip pushing for celebrities Read precomputed list and merge in celebrity posts at read time Fast reads, bounded write cost More complex

The celebrity problem. An account with 20 million followers posting once would trigger 20 million feed writes. Hybrid fixes this: choose a threshold (for example 100,000 followers); above it, do not push; at read time, merge the user's precomputed feed with the latest posts from the few celebrities they follow.

Step 5: post flow (write path).

  1. Client posts to the API; the service stores the post and returns immediately.
  2. It publishes a "post created" event to a queue (chapter S4).
  3. Fan-out workers read the author's follower list (in pages) and push post_id into each follower's feed cache, skipping inactive users (no login in 30 days; rebuild their feed on return).
  4. Media uploads go straight to object storage via pre-signed URLs; a pipeline generates thumbnails and renditions.

Step 6: feed read flow.

  1. Fetch post_ids from the user's feed cache (a page of 20 to 50).
  2. Merge in recent celebrity posts (hybrid).
  3. Hydrate: fetch post bodies, author profiles, and like and comment counts from caches in batch (multiget).
  4. Optionally rank (relevance model) instead of pure recency.
  5. Return a page plus a cursor (for example the last post id) for the next page. Use cursor pagination, not offsets, because new posts shift offsets.

Edge cases. Unfollow: remove that author's posts from the feed lazily at read time. Delete post: mark deleted and filter at hydration; cleanup asynchronously. Cold start: new users get a default or trending feed. Cache loss: rebuild a feed from the follow graph and recent posts (the pull strategy is the fallback).

Scaling levers. Shard the feed cache by user_id; keep only the latest N ids (for example 800) per user; batch and parallelise fan-out; use read replicas for the graph; replicate caches across regions; serve media via CDN.

import heapq
from collections import defaultdict

FOLLOWERS = defaultdict(set)         # author -> set of followers
FOLLOWING = defaultdict(set)         # user -> set of authors
POSTS = {}                           # post_id -> (timestamp, author, text)
FEED = defaultdict(list)             # user -> list of (timestamp, post_id), newest first
CELEB_THRESHOLD = 3                  # tiny, for the demo (use ~100,000 in real life)
CELEB_POSTS = defaultdict(list)      # celebrity -> list of (timestamp, post_id)
CLOCK = [0]

def follow(user, author):
    FOLLOWERS[author].add(user); FOLLOWING[user].add(author)

def post(author, text):
    CLOCK[0] += 1
    pid, ts = f"p{CLOCK[0]}", CLOCK[0]
    POSTS[pid] = (ts, author, text)
    if len(FOLLOWERS[author]) >= CELEB_THRESHOLD:
        CELEB_POSTS[author].insert(0, (ts, pid))            # no push for celebrities
    else:
        for f in FOLLOWERS[author]:                          # fan-out on write
            FEED[f].insert(0, (ts, pid)); del FEED[f][800:]  # cap the feed length

def read_feed(user, limit=10):
    pushed = FEED[user]
    celeb = [e for a in FOLLOWING[user] if len(FOLLOWERS[a]) >= CELEB_THRESHOLD for e in CELEB_POSTS[a]]
    merged = heapq.merge(pushed, sorted(celeb, reverse=True), reverse=True)   # both lists newest first
    return [(POSTS[pid][1], POSTS[pid][2]) for _, pid in list(merged)[:limit]]

for u in ["u1", "u2", "u3"]:
    follow(u, "star")
follow("u1", "friend")
post("friend", "lunch!")
post("star", "big news")
post("friend", "dessert")
print(read_feed("u1"))   # [('friend','dessert'), ('star','big news'), ('friend','lunch!')]

Reading the code. friend has one follower, so their posts are pushed into u1's feed. star has three followers (at the demo threshold), so posts are stored once and pulled at read time. heapq.merge combines two already-sorted lists in O(n) without re-sorting. The per-user cap (del FEED[f][800:]) bounds memory.

Why is a hybrid fan-out usually the final answer?

Pure push explodes for users with huge follower counts, and pure pull makes every feed read expensive. Hybrid pushes cheap cases and pulls the rare expensive ones, bounding both costs.

S9Design chat and a notification system

In one line: chat is long-lived connections plus ordered, durable messages with per-user delivery state; notifications are a queue-driven pipeline with templates, preferences, retries, and rate limits.

Analogy. Chat is a phone exchange: it keeps lines open, knows which line belongs to whom, and connects calls. Notifications are a postal sorting office: letters arrive, get addressed and prioritised, and are handed to different carriers (email, SMS, push).

Why it matters in interviews. Chat stresses real-time connections, ordering, storage at scale, and delivery semantics. Notifications stress asynchronous pipelines, third-party failures, and user preferences. Both appear often, and they share the queue, retry, and idempotency toolkit from earlier chapters.

Part A — Chat

Requirements. One-to-one and group chat; delivery in real time when online; offline users receive messages later; message history; delivery and read receipts; presence (online/last seen) optional; media sharing. Non-functional: low latency, no lost messages, per-conversation ordering, huge scale (hundreds of millions of users, hundreds of thousands of messages per second at peak: see chapter S6).

Connections: how does the server push to a client?

Technique How Verdict
Short polling Client asks repeatedly Wasteful and laggy
Long polling Request held open until data or timeout Works everywhere; heavier
Server-sent events One-way stream server to client Good for notifications
WebSocket Persistent two-way connection Standard for chat

Architecture.

  • Connection (gateway) servers hold WebSocket connections, tens or hundreds of thousands per machine (memory per connection is the limit). They are stateful in that sense, so a session registry (Redis) maps user_id → connection server.
  • Chat service receives a message, assigns an id and sequence, stores it, and routes it.
  • Message store: a write-heavy wide-column or key-value store (Cassandra, HBase, DynamoDB), partitioned by conversation_id and clustered by message id or sequence, so one conversation's history is contiguous.
  • Queue or pub/sub between services to decouple delivery from storage.
  • Push notification path (APNs for iOS, FCM for Android) for offline users.
  • Media goes to object storage with a CDN; the message carries only the URL.

Message flow (1:1).

  1. Alice's client sends the message over its WebSocket to her gateway server, with a client-generated id for deduplication.
  2. The chat service validates it, assigns a per-conversation sequence number, and persists it. Persist first so nothing is lost.
  3. It looks up Bob in the session registry. If online, route the message to Bob's gateway and push it down his connection; if offline, enqueue a push notification and keep the message for sync.
  4. Bob's client sends a delivered ack, later a read ack. These update message state and are forwarded to Alice.

Ordering and ids. Global ordering is unnecessary. Order within a conversation using a monotonically increasing sequence (assigned by the conversation's owning shard) or a time-ordered id. Clients sort by it and use gaps to detect missing messages.

Group chat. For small groups, fan out one copy to each member's inbox (like a feed's fan-out on write). For very large groups or channels, store once and let members pull by sequence, because fan-out per message is too expensive.

Offline sync. Each client remembers the last sequence it saw per conversation; on reconnect it asks "give me everything after seq N". Retries are safe because messages carry ids (idempotent).

Presence. Clients send heartbeats; the server marks users online, with a TTL (for example 30 seconds) in Redis that expires if heartbeats stop. Fan out presence only to a user's active contacts, and tolerate delays; it is a good example of eventual consistency.

End-to-end encryption (E2EE). If required, clients hold keys and servers only relay ciphertext. This limits server-side features (search, moderation), so state the trade-off.

Code: sequence numbers, deduplication, and offline sync in miniature.

from collections import defaultdict, deque

class ChatHub:
    def __init__(self):
        self.seq = defaultdict(int)               # conversation_id -> last sequence
        self.log = defaultdict(list)              # conversation_id -> messages (the durable store)
        self.seen = set()                         # (conversation_id, client_msg_id) for dedupe
        self.online = {}                          # user -> callback (their connection)
        self.pending_push = deque()               # notifications for offline users

    def send(self, conv, sender, members, client_msg_id, text):
        if (conv, client_msg_id) in self.seen:    # a retry after a lost ack: do not duplicate
            return None
        self.seen.add((conv, client_msg_id))
        self.seq[conv] += 1
        msg = {"conv": conv, "seq": self.seq[conv], "from": sender, "text": text}
        self.log[conv].append(msg)                # persist first
        for user in members:
            if user == sender:
                continue
            if user in self.online:
                self.online[user](msg)            # real-time delivery
            else:
                self.pending_push.append((user, msg))   # push notification path
        return msg["seq"]

    def sync(self, conv, after_seq):              # offline catch-up
        return [m for m in self.log[conv] if m["seq"] > after_seq]

hub = ChatHub()
hub.online["bob"] = lambda m: print("bob got", m["text"])
hub.send("c1", "alice", ["alice", "bob", "carol"], "m-1", "hi all")
hub.send("c1", "alice", ["alice", "bob", "carol"], "m-1", "hi all")     # duplicate ignored
print([m["text"] for m in hub.sync("c1", 0)], len(hub.pending_push))      # ['hi all'] 1

Part B — Notification system

Requirements. Send notifications over push, SMS, and email; support transactional (OTP, receipt) and marketing messages; respect user preferences and quiet hours; high throughput; do not lose important notifications; avoid duplicates and spam.

Architecture.

Key design points.

  • Priority queues: OTP and security alerts must not wait behind a million marketing emails. Separate queues and worker pools per priority and channel (a bulkhead).
  • Templates and localisation: store templates by type and language; workers render with data from the event.
  • User preferences and consent: per-channel and per-category opt-outs; legal requirements for unsubscribe; quiet hours with scheduling.
  • Idempotency: each notification has an id; a unique check prevents duplicate sends when upstream retries.
  • Retries with backoff for provider failures, and DLQ after the limit; fall back to another channel or provider for critical messages.
  • Rate limiting: per user (do not send 50 pushes in a minute) and per provider (respect their quotas) (chapter S5).
  • Device tokens: store per device; remove tokens that the provider reports as invalid.
  • Observability: delivery, open, and failure metrics; alert on rising failure rates or queue depth.

Traps

Trap. Sending the message to the recipient before persisting it. If the server crashes in between, the message is lost and the sender sees it as sent.

Trap. Relying on timestamps for ordering across devices. Use server-assigned sequence numbers.

Trap. One queue for all notification types. A marketing blast delays password-reset codes.

Trap. Treating third-party providers as always up. They throttle and fail; build retries, DLQs, and a fallback provider.

Trap. Pushing every message to huge groups individually. Use pull-by-sequence for very large channels.

  1. Typing indicators are ephemeral: send over the connection, never store, drop if lost. "Last seen" can be a lightly updated value (heartbeats, TTL in Redis) with seconds of staleness; neither needs durable storage guarantees like messages do.
  2. Persist (and replicate) the message before acknowledging it to the sender. After a crash, the message is in the store; recipients receive it on reconnect via sync-by-sequence, and the push-notification path covers offline users.
  3. Try provider A with a short timeout; on failure or timeout, retry once with backoff; then switch to provider B; record attempts with the same notification id to avoid double sends, and stop after the OTP's validity window expires. Alert on elevated failure rates.

Check yourself

Why persist before routing a chat message?

Durability first guarantees the message survives a crash. Delivery can be retried from storage; a message that only existed in memory and was not stored cannot be recovered.

Why have separate priority queues for notifications?

Time-critical messages (OTP, alerts) must not be delayed by bulk traffic. Separate queues and workers isolate them, a bulkhead against noisy neighbours.

S10Design search and autocomplete

In one line: search is an inverted index (term → documents) sharded across machines and ranked by relevance; autocomplete is a prefix structure (a trie or precomputed top-k per prefix) refreshed offline and served from cache.

Analogy. The index at the back of a textbook: look up a word, get the page numbers. Autocomplete is the phone's predictive keyboard.

Why it matters in interviews. Search shows you understand data structures at scale (inverted index, trie), offline versus online work, ranking, and sharding. Autocomplete adds extreme latency requirements (tens of milliseconds) and the "precompute and cache" mindset.

Part A — Search

Requirements. Given a text query, return relevant documents (products, pages, messages) quickly; support filters and pagination; new or changed documents appear within seconds to minutes; typo tolerance is a plus.

The inverted index. Instead of scanning every document for a word, build a map from each term to the list of documents containing it (a posting list), with positions and frequencies.

"refund" -> [doc2, doc7, doc9]
"policy" -> [doc2, doc3, doc9]
query "refund policy" (AND) -> intersect lists -> [doc2, doc9]

Index building (analysis pipeline). Split text into tokens, lowercase, remove punctuation, optionally remove stop words ("the", "of"), and apply stemming or lemmatisation ("refunds" → "refund"). The same analysis must be applied to queries.

Query processing. Parse the query, look up posting lists, combine them (intersection for AND, union for OR), then score candidates. Keep posting lists sorted by document id so intersection is a fast merge.

Ranking. Classic text relevance: TF-IDF (a term is important if it is frequent in the document but rare overall) and its refinement BM25, which also normalises for document length and saturates term frequency. Real systems blend text relevance with signals such as freshness, popularity, personalisation, and click-through, often with a machine-learned re-ranker on the top few hundred candidates.

Scaling the index.

  • Document-partitioned (sharded by document): each shard indexes a subset of documents; a query goes to all shards, each returns its top-k, and a coordinator merges them. This is what Elasticsearch and Solr do; it scales writes and keeps each shard's index smaller.
  • Term-partitioned: each shard owns some terms. Queries touch fewer shards, but multi-term queries need cross-shard joins and hot terms overload a shard. Less common.
  • Replicas per shard for availability and query throughput.
  • Near-real-time indexing: new documents are buffered and made searchable after a short refresh interval (about a second), segments are merged in the background.

Data pipeline. Source database → change events (CDC) or a queue → indexing workers → search cluster. The search index is a derived, rebuildable view, not the source of truth. Plan for re-indexing.

Typo tolerance and suggestions. Use edit-distance (fuzzy matching) limited to 1 or 2 edits, character n-grams, or phonetic matching. Spelling correction can also come from query logs.

Code: a small inverted index with TF-IDF ranking.

import math, re
from collections import defaultdict, Counter

STOP = {"the", "a", "of", "to", "and", "is"}

def analyze(text: str) -> list[str]:
    tokens = re.findall(r"[a-z0-9]+", text.lower())
    return [t.rstrip("s") for t in tokens if t not in STOP]      # crude stemming for the demo

class SearchIndex:
    def __init__(self):
        self.postings = defaultdict(dict)        # term -> {doc_id: term_frequency}
        self.doc_len, self.docs = {}, {}

    def add(self, doc_id, text):
        terms = analyze(text)
        self.docs[doc_id], self.doc_len[doc_id] = text, len(terms)
        for term, tf in Counter(terms).items():
            self.postings[term][doc_id] = tf

    def search(self, query, k=3):
        terms = analyze(query)
        n_docs = len(self.docs)
        scores = defaultdict(float)
        for t in terms:
            plist = self.postings.get(t, {})
            if not plist:
                continue
            idf = math.log(1 + n_docs / len(plist))              # rarer terms count more
            for doc_id, tf in plist.items():
                scores[doc_id] += (tf / self.doc_len[doc_id]) * idf
        return sorted(scores.items(), key=lambda kv: kv[1], reverse=True)[:k]

idx = SearchIndex()
idx.add(1, "Refund policy for cancelled orders")
idx.add(2, "How to track the status of your order")
idx.add(3, "Refund status and refund timelines")
print([(d, round(s, 3), idx.docs[d]) for d, s in idx.search("refund status")])

Reading the code. analyze lowercases, drops stop words, and crudely strips plural "s" so "refunds" and "refund" match. postings is the inverted index. Scoring sums term frequency (normalised by document length) × inverse document frequency for each query term. Document 3 contains both "refund" (twice) and "status", so it ranks first. Production engines use BM25 and compressed posting lists, but the structure is identical.

Intersecting two sorted posting lists (what AND queries cost):

def intersect(a: list[int], b: list[int]) -> list[int]:
    i = j = 0
    out = []
    while i < len(a) and j < len(b):
        if a[i] == b[j]:
            out.append(a[i]); i += 1; j += 1
        elif a[i] < b[j]:
            i += 1
        else:
            j += 1
    return out                                  # O(len(a) + len(b))

Part B — Autocomplete (typeahead)

Requirements. As the user types, show the top 5 to 10 completions for the prefix within roughly 50–100 ms total (including the network), based on popularity; fresh trends reflected within minutes to hours; no offensive suggestions.

Approaches.

Approach Idea Notes
Trie with counts Tree of characters; each node stores frequency Walk to the prefix node, then collect top-k below it; can be slow for short prefixes with huge subtrees
Precomputed top-k per prefix For every prefix store its top-k completions in a key-value store or in each trie node Constant-time lookup; the standard high-scale answer
Search-index based Edge n-grams in the search engine Simple to build with existing infrastructure; less control

Pipeline.

  1. Log every completed search query (with timestamp, region, language) into a stream.
  2. Aggregate counts offline or in a stream job (daily batch plus a recent-trends window), applying decay so old queries fade.
  3. Build the prefix to top-k structure, filter blocked and unsafe terms, and publish it to the serving store.
  4. Serve from an in-memory store or cache keyed by prefix; also cache in the browser and CDN for common prefixes.

Optimisations. Limit prefixes to the first N characters (for example 20); only index queries above a minimum count; start suggesting after 1 to 2 characters; debounce requests on the client (wait ~100 ms after the last keystroke); cancel outdated in-flight requests; personalise by merging a few personal and local suggestions into the global list.

Scaling. Shard the prefix store by prefix hash (or by first characters, watching for hot prefixes), replicate for reads, and keep the dataset small enough to fit in memory, since query logs dwarf the set of popular completions.

Code: precomputed top-k per prefix.

from collections import defaultdict

class Autocomplete:
    def __init__(self, k=3): self.k, self.top = k, defaultdict(list)
    def build(self, query_counts: dict[str, int]):
        for q, c in query_counts.items():
            for i in range(1, len(q) + 1):
                self.top[q[:i]].append((c, q))
        for p in self.top:
            self.top[p] = sorted(self.top[p], reverse=True)[:self.k]
    def suggest(self, prefix: str): return [q for _, q in self.top.get(prefix, [])]

ac = Autocomplete(); ac.build({"refund status": 900, "refund policy": 1200, "referral code": 300})
print(ac.suggest("ref"))   # ['refund policy', 'refund status', 'referral code']

Reading the code. build registers every prefix of every query with its count, then keeps only the top k per prefix, an offline job. suggest is then a single dictionary lookup, which is why this scales. Memory is roughly the sum of prefix lengths × k, so cap query counts and prefix length.

A trie alternative with top-k kept at each node:

class TrieNode:
    __slots__ = ("children", "top")
    def __init__(self): self.children, self.top = {}, []

def insert(root: TrieNode, word: str, count: int, k: int = 3):
    node = root
    for ch in word:
        node = node.children.setdefault(ch, TrieNode())
        node.top.append((count, word))
        node.top = sorted(set(node.top), reverse=True)[:k]      # keep only the best k at every node

def complete(root: TrieNode, prefix: str):
    node = root
    for ch in prefix:
        node = node.children.get(ch)
        if node is None:
            return []
    return [w for _, w in node.top]

Trap. Scanning all documents with LIKE '%term%'. Use an inverted index.

Trap. Using the search index as the primary database. It is a derived view; keep a source of truth and the ability to rebuild.

Trap. Computing autocomplete suggestions at request time from raw logs. Precompute and cache; the latency budget leaves no room.

Trap. Analysing the query differently from the documents (different stemming, casing). Terms will not match.

Check yourself

Why is the search index sharded by document rather than by term?

Document sharding spreads indexing and storage evenly, keeps shards independent, and parallelises queries (each shard returns its top-k). Term sharding creates hot terms and requires cross-shard joins for multi-term queries.

Why precompute top-k per prefix?

It turns each keystroke into one key lookup instead of a computation over many candidates, meeting the tens-of-milliseconds latency requirement.

Appendix E — Final self-assessment

Answer aloud without looking. If you cannot answer in two or three sentences, revisit the chapter.

1. Why must app servers be stateless, and where does session data go?

So any server can handle any request and servers can be added or removed freely. Session data goes to a shared store (Redis) or into a signed token. (S1)

2. Describe cache-aside and two ways it goes wrong.

Check the cache, on a miss read the database and fill the cache. Problems: stampedes when a hot key expires, stale data after writes, and penetration by missing keys. (S1)

3. Why does hash(key) mod N hurt when you add a shard, and what is the fix?

Nearly all keys map to a different shard when N changes. Consistent hashing (with virtual nodes) or a directory moves only about 1/N of keys. (S2)

4. State CAP and PACELC in your own words.

During a partition choose consistency or availability; otherwise choose latency or consistency. (S3)

5. What does R + W > N guarantee?

Every read quorum overlaps the latest write quorum, so a read can find the newest version (though not every anomaly is removed). (S3)

6. How do you get "effectively exactly-once" processing?

At-least-once delivery plus idempotent consumers using a unique message or idempotency key. (S4)

7. What problem does the transactional outbox solve?

The dual-write gap between updating the database and publishing an event; both are recorded in one transaction and a relay publishes later. (S4)

8. Compare token bucket and fixed-window rate limiting.

Token bucket allows bounded bursts and a steady average; fixed windows are simpler but permit up to double the limit around window boundaries. (S5)

9. Explain the three states of a circuit breaker.

Closed passes calls; open fails fast after repeated failures; half-open sends trial calls to test recovery. (S5)

10. Roughly how many requests per second is 1 billion requests per day?

About 12,000 per second on average (1e9 / 86,400). (S6)

11. How do you generate short URL codes and why 301 vs 302?

Counter ranges (scrambled) encoded in base62, or random with uniqueness checks. 301 is cacheable by browsers (less load, no analytics); 302 hits you each time. (S7)

12. What is the celebrity problem in feeds and its fix?

Pushing a post to millions of followers is too expensive. Use a hybrid: push for normal users, merge celebrity posts at read time. (S8)

13. How do you guarantee ordering in chat?

Assign a per-conversation sequence number on the server and sort clients by it; do not rely on client clocks. (S9)

14. Why is the search index not the source of truth?

It is a derived, rebuildable view optimised for queries; the primary database holds authoritative data and feeds the index through change events. (S10)

15. How does autocomplete meet a 50 ms budget?

Precomputed top-k per prefix stored in memory and cached, refreshed by an offline or streaming pipeline, with client debouncing. (S10)
