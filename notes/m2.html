2.1Python foundations — the 20% you use 80% of the time

In one line: variables, collections, functions, comprehensions, and modules carry almost every AI script you will write.

Analogy. Python is a kitchen. Lists are shelves (ordered), dicts are labelled jars (lookup by name), sets are a spice rack with no duplicates, and functions are recipes you reuse.

Why it matters for AI work. An LLM pipeline is mostly data shuffling: lists of documents, dicts of metadata, strings that become prompts, and small functions that glue steps together. If these basics are fluent, the fancy parts (embeddings, agents, evals) are just more of the same.

Core ideas

Built-in scalar types. str (text), int, float, bool, and None (the "nothing here" value). Strings are immutable: operations like .strip() return a new string instead of changing the old one. Floats are binary approximations, so 0.1 + 0.2 == 0.3 is False; compare with math.isclose or round for display.

Truthiness. Empty things are falsy: "", [], {}, set(), 0, None. That lets you write if not docs: instead of if len(docs) == 0:. Be careful when 0 or "" is a valid value, for example a score of 0.0. Use is None for that distinction.

The four collections.

Type Ordered? Mutable? Duplicates? Typical AI use
list yes yes yes Documents, chunks, chat messages
dict insertion order yes unique keys Metadata, API payloads, config
set no yes no Unique labels, seen ids, fast membership tests
tuple yes no yes Fixed records like (doc_id, score)

Lookup in a dict or set is effectively instant, while x in some_list scans the whole list. When you test membership in a loop (for example "have I seen this id?"), use a set.

Slicing and indexing. items[0] is the first, items[-1] the last, items[2:5] elements 2 to 4, items[::2] every second item. Slices never raise IndexError; they just return less. The chunk function below relies on slicing past the end being safe.

Useful dict moves.

cfg = {"top_k": 5}
cfg.get("chunk_size", 800)         # 800, no KeyError when the key is missing
cfg.setdefault("filters", {})      # insert only if absent, then return it
merged = {**cfg, "top_k": 3}       # copy with an override (Python 3.9+: cfg | {"top_k": 3})
for key, value in cfg.items():     # iterate key and value together
    print(key, value)

Comprehensions are loops that build a collection. The pattern is [expression for item in iterable if condition]. Use them while they stay readable on one or two lines. If you need nested conditions, a normal loop is kinder to your teammates.

Generators are lazy comprehensions: (len(d) for d in docs) produces values one at a time and never holds the whole list in memory. A function with yield is a generator too. This is how you stream a 10 GB file or a 50,000-record API without running out of memory (chapter 2.11 uses yield from).

Functions. Defaults, keyword arguments, and type hints make calls self-documenting. *args collects extra positional arguments into a tuple; **kwargs collects extra keyword arguments into a dict. Both appear constantly when you wrap SDK calls and forward options.

Modules and imports. Any .py file is a module. import json loads one; from pathlib import Path pulls out a name. A folder of modules with an __init__.py is a package. Guard script entry points with if __name__ == "__main__": so importing the file does not run it.

def chunk(text: str, size: int = 500, overlap: int = 50) -> list[str]:
    step = size - overlap
    return [text[i:i + size] for i in range(0, len(text), step)]

# Unpacking and enumerate
for i, piece in enumerate(chunk("abc" * 400, size=300), start=1):

# f-strings with formatting
cost = 0.004213
print(f"Cost so far: ${cost:.3f}")

Reading the code.

  • {d: len(d.split()) for d in docs} is a dict comprehension: each document becomes a key, its word count the value.
  • chunk slides a window of size characters forward by size - overlap each time, so neighbouring chunks share overlap characters. That overlap keeps a sentence that straddles a boundary from being cut in half in both chunks. If overlap >= size, step is zero or negative and range fails, so a real version should validate that.
  • enumerate(..., start=1) gives you a counter without managing an index variable.
  • In the f-string, :.3f means "float with three decimals". Other handy format specs: :, (thousands separator), :>8 (right-align in 8 characters), :.1% (percentage), and !r (show the repr, useful for debugging strings with hidden whitespace).

A more realistic chunker that respects word boundaries and validates its inputs:

def chunk_words(text: str, size: int = 200, overlap: int = 40) -> list[str]:
    if not 0 <= overlap < size:
        raise ValueError("overlap must be >= 0 and smaller than size")
    words = text.split()
    step = size - overlap
    chunks = []
    for start in range(0, len(words), step):
        piece = words[start:start + size]
        chunks.append(" ".join(piece))
        if start + size >= len(words):       # last window reached the end
            break
    return chunks

Traps

Trap. Mutable default arguments: def f(x=[]) shares one list across calls. Use x: list | None = None then x = x or [].

Trap. Copying a nested structure with b = a.copy() only copies the top level; inner lists and dicts are still shared. Use copy.deepcopy(a) when you need an independent copy, for example before editing a prompt template per request.

Trap. is checks identity, == checks equality. Use is only for None, True, and False. if label is "refund" can fail unpredictably.

Trap. Modifying a list while looping over it skips items. Build a new list (a comprehension) or loop over a copy.

Check yourself

Why is a set faster than a list for "have I seen this id?"

A set uses hashing, so membership is roughly constant time. A list is scanned from the start, so cost grows with its length.

What does x: list | None = None fix?

It avoids the shared mutable default. A fresh list is created inside the function on each call that needs one.

2.2Files and JSON

In one line: open files with a context manager, and convert between Python objects and JSON with json.load / json.dumps.

Analogy. JSON is the universal shipping box. dumps packs your dict into a box; loads unpacks a box someone else sent.

Why it matters for AI work. Nearly everything that crosses a boundary in an AI system is JSON: API requests and responses, tool-call arguments, eval datasets, cached results, and logs. Reading and writing it safely is a daily skill.

Core ideas

Context managers close files for you. with open(...) as f: guarantees the file is closed even if an exception happens inside the block. Always pass encoding="utf-8"; otherwise Python uses the platform default, which differs between Windows and Linux and causes mysterious UnicodeDecodeErrors with Indian-language text, emoji, or curly quotes.

pathlib.Path beats string paths. Paths become objects you can combine with /, inspect, and read in one call.

How Python types map to JSON.

dict object

Anything else (datetime, set, Decimal, a custom class) is not serialisable by default. Convert it yourself, or pass default=str as a quick fallback: json.dumps(obj, default=str).

ensure_ascii=False keeps non-English characters readable in the file instead of writing \u0939\u093f... escapes. indent=2 pretty-prints for humans; leave it off for compact machine files.

JSON Lines (.jsonl) stores one JSON object per line. It is perfect for eval sets and logs because you can append a record without rewriting the file, and read it lazily one line at a time.

Memory trick: the s in dumps/loads stands for string.

Reading a large JSONL file lazily (constant memory, skips blank lines, reports the bad line number):

def read_jsonl(path):
    with open(path, encoding="utf-8") as f:
        for n, line in enumerate(f, start=1):
            line = line.strip()
            if not line:
                continue
            try:
                yield json.loads(line)
            except json.JSONDecodeError as e:
                raise ValueError(f"{path}:{n}: invalid JSON ({e.msg})") from e

Safe writes for important files. If your program crashes halfway through writing, you are left with a corrupt file. Write to a temporary file, then atomically replace the original:

def write_json_atomic(path: Path, obj) -> None:
    tmp = path.with_suffix(path.suffix + ".tmp")
    tmp.write_text(json.dumps(obj, indent=2, ensure_ascii=False), encoding="utf-8")
    tmp.replace(path)          # atomic on the same filesystem

This is exactly the trick the Boss-level checkpoint file needs.

Stripping code fences from LLM output when you cannot use structured outputs:

import re

FENCE = re.compile(r"^`{3}(?:json)?\s*|\s*`{3}$", re.IGNORECASE)

def parse_llm_json(text: str):
    cleaned = FENCE.sub("", text.strip())
    return json.loads(cleaned)       # still may raise JSONDecodeError: handle it

Traps

Trap. LLMs often wrap JSON in triple backticks. Strip fences before json.loads, or better, use structured outputs so you never have to.

Trap. JSON object keys are always strings. json.loads(json.dumps({1: "a"})) gives {"1": "a"}, so integer keys come back as text.

Trap. Opening a file with mode "w" truncates it immediately. Use "a" to append, and only use "w" when you really mean to replace.

Trap. json.load on an empty file raises JSONDecodeError. A crash that leaves a zero-byte file is a common cause; atomic writes prevent it.

Check yourself

When would you choose JSONL over a single JSON array?

When the data grows over time, is appended record by record, or is too big to load at once. Each line is independent, so a crash only damages the last line.

Why always pass encoding="utf-8"?

Default encodings differ across operating systems. Being explicit makes the code behave identically everywhere.

2.3OOP and error handling

In one line: classes bundle state and behaviour (a client with its config); exceptions let you fail loudly and recover deliberately.

Analogy. A class is a cookie cutter; objects are the cookies. Exceptions are smoke alarms — you want them to go off, and you want a plan for when they do.

Why it matters for AI work. Every real LLM app wraps a provider client, a prompt, and some history into an object, and every real LLM app fails sometimes: rate limits, timeouts, malformed output. How you classify and handle those failures decides whether users see a polite message or a stack trace.

Core ideas

Classes, instances, and self. __init__ runs when you create an object and stores its starting state on self. Methods are functions that receive the object as their first argument. State that belongs to one object lives on self; state shared by every object lives on the class (use sparingly).

Dependency injection. Notice that SupportBot does not create its own LLM client; it receives one. That single decision makes the class testable (pass a fake), swappable (pass a different provider), and configurable. Prefer passing dependencies in over constructing them inside.

Composition over inheritance. Inheritance says "is a" (RateLimited is a LLMError) and suits exception hierarchies. For behaviour, prefer "has a": SupportBot has an LLM and has a history. Deep inheritance trees become hard to change.

Exception flow. Know what each block does:

Block Runs when Use it for
try always first The risky call
except X try raised an X Handling errors you can actually recover from
else try raised nothing Success-only follow-up work
finally always, even after return or an uncaught error Closing resources, recording metrics

Design an exception hierarchy. One base class (LLMError) lets callers catch "anything from our LLM layer" in one line, while subclasses (RateLimited, BadOutput, ProviderDown) allow different recovery per case. Put useful data on the exception (retry_after), not only in the message string.

Chain exceptions. When you translate a low-level error into your own, use raise MyError("...") from original. The traceback then shows both, so you do not lose the root cause.

Fail fast, handle at the right level. Catch an exception where you know what to do about it (retry, fall back, show a message). Lower layers should usually let it propagate. Python's culture is EAFP, "easier to ask forgiveness than permission": try the operation and handle the failure, rather than pre-checking every condition.

Code

class LLMError(Exception):
    """Base error for our LLM layer."""

class RateLimited(LLMError):
    def __init__(self, retry_after: float):
        super().__init__(f"rate limited, retry after {retry_after}s")
        self.retry_after = retry_after

class SupportBot:
    def __init__(self, llm, system_prompt: str):
        self.llm = llm
        self.system_prompt = system_prompt
        self.history: list[dict] = []

    def reply(self, text: str) -> str:
        try:
            answer = self.llm.complete(self.system_prompt, text)
        except RateLimited as e:
            return f"We are busy, try again in {e.retry_after:.0f}s."
        except LLMError:
            return "Something went wrong; a human will follow up."
        else:
            self.history.append({"user": text, "bot": answer})
            return answer
        finally:
            pass  # always runs: close resources, record metrics

Reading the code. Order matters: except RateLimited must come before except LLMError, because Python uses the first matching handler and RateLimited is also an LLMError. The else branch only runs on success, which keeps the "save to history" step out of the risky try.

Translating provider errors into your own (so the rest of the app never imports provider-specific exceptions):

import httpx

class ProviderDown(LLMError): ...

class HttpLLM:
    def __init__(self, base_url: str, key: str):
        self.client = httpx.Client(base_url=base_url, timeout=20,
                                   headers={"Authorization": f"Bearer {key}"})

    def complete(self, system: str, text: str) -> str:
        try:
            r = self.client.post("/chat", json={"system": system, "text": text})
            if r.status_code == 429:
                raise RateLimited(float(r.headers.get("Retry-After", 5)))
            r.raise_for_status()
            return r.json()["answer"]
        except httpx.TimeoutException as e:
            raise ProviderDown("provider timed out") from e
        except httpx.HTTPStatusError as e:
            raise ProviderDown(f"provider returned {e.response.status_code}") from e

Traps

Trap. except Exception: pass hides bugs forever. Catch the specific errors you can handle, and log the rest.

Trap. A bare except: also catches KeyboardInterrupt and SystemExit, so you cannot stop the program with Ctrl+C. Never use it.

Trap. Returning a finally: value or using return inside finally swallows exceptions silently. Use finally only for cleanup.

Trap. Putting too much inside try makes it unclear which line failed. Keep the risky call small and move follow-up work to else.

2.4Decorators, context managers, dataclasses

In one line: decorators wrap functions with extra behaviour, context managers guarantee setup and cleanup, and dataclasses write boring class code for you.

Analogy. A decorator is gift wrap — same present inside, nicer outside. A context manager is a hotel room: check-in and checkout happen even if you leave in a hurry.

Why it matters for AI work. Timing, retrying, caching, and logging every LLM call are cross-cutting concerns. Decorators let you add them without touching the function body. Config objects (top_k, chunk size, model name) are exactly what dataclasses are for.

Core ideas

Decorators are functions that take a function and return a function. The line @timed above def answer is shorthand for answer = timed(answer). Inside, the wrapper runs code before and after calling the original. It accepts *args, **kwargs so it works with any signature.

Decorators with arguments need one more layer: a function that takes the arguments and returns the real decorator.

import functools

def log_calls(level: str = "INFO"):
    def decorator(fn):
        @functools.wraps(fn)
        def wrapper(*args, **kwargs):
            print(f"[{level}] calling {fn.__name__}")
            return fn(*args, **kwargs)
        return wrapper
    return decorator

@log_calls(level="DEBUG")
def embed(text: str) -> list[float]:
    return [0.0] * 3

Context managers pair setup with cleanup. Two ways to write one: a class with __enter__ and __exit__, or a generator function decorated with @contextmanager, where code before yield is setup and code after is cleanup. Use them for files, database connections, locks, temporary directories, timers, and spend budgets.

Dataclasses generate __init__, __repr__, and __eq__ from annotated fields. Useful options:

Option Effect
frozen=True Instances are immutable, hashable, and safe to share between threads
slots=True Lower memory, blocks accidental new attributes (Python 3.10+)
field(default_factory=dict) Fresh mutable default per instance
__post_init__ Validate or derive fields after creation
dataclasses.replace(obj, top_k=3) Copy with one change (needed for frozen objects)
dataclasses.asdict(obj) Convert to a plain dict for JSON or logging

Dataclass vs Pydantic. Dataclasses do not validate types at runtime. Use dataclasses for trusted internal config and Pydantic (chapter 2.5) for anything that comes from outside.

Code

import time, functools
from contextlib import contextmanager
from dataclasses import dataclass, field

def timed(fn):
    @functools.wraps(fn)
    def wrapper(*args, **kwargs):
        t0 = time.perf_counter()
        try:
            return fn(*args, **kwargs)
        finally:
            print(f"{fn.__name__} took {time.perf_counter() - t0:.3f}s")
    return wrapper

@contextmanager
def budget(limit_usd: float):
    spent = {"usd": 0.0}
    yield spent
    if spent["usd"] > limit_usd:
        print(f"Over budget: ${spent['usd']:.2f} > ${limit_usd}")

@dataclass(frozen=True)
class RetrievalConfig:
    top_k: int = 5
    chunk_size: int = 800
    filters: dict = field(default_factory=dict)

@timed
def answer(q: str, cfg: RetrievalConfig) -> str:
    return f"answering {q!r} with k={cfg.top_k}"

with budget(1.0) as spent:
    print(answer("refund policy?", RetrievalConfig(top_k=3)))
    spent["usd"] += 0.02

Reading the code.

  • timed uses time.perf_counter() (a high-resolution clock meant for measuring durations) and a finally so the time is printed even if the function raises.
  • budget yields a small dict that the with body can update. When the block ends, the code after yield checks the total. As written, if the body raises, the check is skipped. To make cleanup always run, wrap the yield in try/finally:
@contextmanager
def budget(limit_usd: float):
    spent = {"usd": 0.0}
    try:
        yield spent
    finally:
        if spent["usd"] > limit_usd:
            print(f"Over budget: ${spent['usd']:.2f} > ${limit_usd}")
  • RetrievalConfig is frozen, so nobody can change top_k halfway through a request. filters uses default_factory so each config gets its own dict.

An async-aware timing decorator. A plain wrapper around an async def times only the creation of the coroutine, not its execution. Detect and handle both:

import asyncio, inspect

def timed_any(fn):
    if inspect.iscoroutinefunction(fn):
        @functools.wraps(fn)
        async def awrapper(*a, **k):
            t0 = time.perf_counter()
            try:
                return await fn(*a, **k)
            finally:
                print(f"{fn.__name__} took {time.perf_counter() - t0:.3f}s")
        return awrapper
    return timed(fn)

2.5Type hints and mypy

In one line: type hints document intent; mypy reads them and catches “you passed a list where a string was expected” before production does.

Analogy. Type hints are labels on electrical sockets. mypy is the electrician who checks you did not plug 220 V into a 110 V device.

Why it matters for AI work. LLM code passes around nested structures (messages, tool schemas, embeddings). A mistyped key or a wrong shape fails late and expensively, after an API call has already cost money. Types move those failures to your editor.

Core ideas

Basic syntax. name: str, count: int = 0, def f(x: int) -> str:. Since Python 3.9 you write built-in generics directly: list[str], dict[str, float], tuple[int, str]. Since 3.10 you write unions as int | None instead of Optional[int].

The vocabulary you will actually use.

Hint Meaning
X \| None Value or nothing; forces you to handle None
list[X], dict[K, V], set[X] Typed collections
Callable[[int, str], bool] A function taking (int, str) returning bool
Iterable[X], Iterator[X] Anything you can loop over; generators
Any Opt out of checking (use sparingly)
Literal["a", "b"] Only these exact values
TypedDict A dict with known keys and value types
Protocol "Anything with these methods" (structural typing, like duck typing with checks)

Why Protocol is great for AI code. Embedder below says "anything with an embed method". OpenAI wrappers, local models, and test fakes all qualify without inheriting from a common base class.

Gradual typing. You do not have to annotate everything on day one. Start with function signatures at module boundaries, run mypy without --strict, and tighten over time. Use # type: ignore[error-code] sparingly, with the specific code, and a comment on why.

Types are not validation. Hints are erased at runtime. Python will happily run top_k(..., k="2") and fail later. For data that arrives from outside your program, use Pydantic, which parses and validates at runtime:

2.6pytest and mocking external APIs

In one line: pytest runs plain assert tests; mocks replace the real LLM call so tests are fast, free, and deterministic.

Analogy. Testing with the real API is rehearsing a play with real fire. Mocks are the stage fire — looks the same to the actors, nobody gets burned.

Why it matters for AI work. Real LLM calls are slow, cost money, and return slightly different text each time. If your tests depend on them, nobody runs the tests. Mock the boundary, test your own logic (parsing, routing, prompt building, error handling), and keep a small live suite for the real thing.

Core ideas

What to test, and what not to. Test the code around the model: does classify normalise labels, does the retry logic stop after N attempts, does the prompt builder include the right context, does a malformed response become a clean error. Do not use unit tests to judge model quality; that is the job of evals (a dataset plus a scoring metric, covered later in the course).

Arrange, Act, Assert. Set up inputs, call the function, check the result. One behaviour per test, and a name that says what is guaranteed: test_classify_returns_other_for_unknown_label.

Pytest features worth knowing.

Feature What it does
Plain assert Pytest rewrites it to show helpful diffs on failure
@pytest.mark.parametrize Run one test over many input/expected pairs
Fixtures Reusable setup, injected by argument name
tmp_path Built-in fixture giving a fresh temporary folder
monkeypatch Temporarily set env vars or replace attributes
pytest.raises(X) Assert that code raises an exception
Markers Tag tests (live, slow) and select with -m

Mocks. MagicMock creates an object that accepts any attribute or call and records how it was used. You can set return_value or side_effect (a function or an exception to raise). Afterwards inspect call_args to check what your code sent.

Mock at the boundary you own. Wrap the provider in your own small function or class (llm.complete) and mock that, rather than mocking deep SDK internals. Tests then survive SDK upgrades.

Mocking HTTP directly. If you call httpx, the respx library intercepts requests and returns canned responses, which lets you simulate 429s, 500s, and timeouts easily.

2.7Structured logging

In one line: log events as key–value fields (JSON), not prose, so you can search “all requests where latency_ms > 2000 and model = X”.

Analogy. Prose logs are a diary. Structured logs are a spreadsheet. Try finding every Tuesday you spent over ₹500 in a diary.

Why it matters for AI work. When a user says "the bot gave a weird answer yesterday", you need to find that exact request, see which prompt version and model handled it, how long it took, and what it cost. Without structured logs you are guessing.

Core ideas

Levels. Use them consistently so you can filter noise.

Level Use for
DEBUG Detailed diagnostics, normally off in production
INFO Normal events worth recording (one line per LLM call)
WARNING Something unexpected but handled (a retry happened)
ERROR An operation failed
CRITICAL The service cannot continue

Loggers, handlers, formatters. A logger (named, usually logging.getLogger(__name__)) creates records. A handler decides where they go (stdout, a file). A formatter decides how they look. Loggers form a hierarchy by dotted name, so configuring "rag" also governs "rag.retrieval".

Configure logging once, at the program's entry point, never inside library modules. Modules just call logging.getLogger(__name__).

What to record on every LLM call.

Field Why
request_id Join logs across services and with user reports
model, prompt_version Compare behaviour across changes
tokens_in, tokens_out Cost and context-size tracking
latency_ms (and time to first token for streams) Performance
cache_read_tokens Check that prompt caching works
status / error_type Reliability
cost_usd Budget control

def logged_call(client, model: str, messages: list, request_id: str):

             tokens_in=u.prompt_tokens, tokens_out=u.completion_tokens,
             cost_usd=round(cost, 6))
    return r

2.8Async Python — async def, await, asyncio

In one line: while one request waits on the network, asyncio runs others, so 50 LLM calls take about as long as the slowest one, not the sum.

Analogy. A waiter who takes table 1’s order, then table 2’s while table 1’s food cooks. A synchronous waiter stands at the kitchen door until each plate is ready.

Why it matters for AI work. LLM and embedding calls are almost pure waiting. Summarising 500 documents one by one might take 40 minutes; with controlled concurrency it takes a few. Web servers like FastAPI are also async, so you will meet await constantly.

Core ideas

Vocabulary.

Term Meaning
Coroutine What you get by calling an async def function; it has not run yet
await "Pause me here until this finishes; let others run meanwhile"
Event loop The scheduler that switches between waiting tasks
Task A coroutine scheduled to run (asyncio.create_task)
gather Run many awaitables and collect their results in order
TaskGroup Structured version: if one task fails, the rest are cancelled (Python 3.11+)
Semaphore A limiter: at most N inside the block at once

Concurrency is not parallelism. Asyncio runs on one thread and interleaves tasks at await points. It speeds up I/O-bound work (network, disk). It does not speed up CPU-bound work such as tokenising huge texts or heavy number crunching; use processes (concurrent.futures.ProcessPoolExecutor) for those.

Always limit concurrency. Firing 5,000 requests at once will hit provider rate limits and exhaust sockets. A Semaphore (as below) caps the number in flight. Combine it with retries (chapter 2.13).

Timeouts and cancellation. async with asyncio.timeout(10): (3.11+) cancels the enclosed work after 10 seconds and raises TimeoutError. Cancelled tasks receive CancelledError at their next await; do not swallow it.

Mixing sync and async. To run a blocking function without freezing the loop, use await asyncio.to_thread(blocking_fn, arg). To start the loop from normal code, call asyncio.run(main()) once, at the top. In Jupyter, a loop already runs, so write await main() directly instead.

Reading the code.

  • summarise(d) creates 50 coroutines instantly, but the semaphore lets only 10 reach the API at a time; as each finishes, the next one enters.
  • gather(..., return_exceptions=True) returns exceptions as values instead of aborting the whole batch on the first failure. You then separate successes from failures, which is what a resilient ingestion job needs.
  • Results come back in the same order as the inputs, regardless of finish order.

Keeping track of which input failed:

TaskGroup with a timeout (3.11+):

async def run_all(docs: list[str]) -> list[str]:
    out: list[str] = []
    async with asyncio.timeout(120):

If any task raises, the group cancels the rest and raises an ExceptionGroup. Pick gather(return_exceptions=True) when you want partial results, and TaskGroup when failure of one should stop everything.

A producer/consumer queue for very large jobs (workers pull items, so memory stays flat):

async def worker(q: asyncio.Queue, results: list):
    while True:
        item = await q.get()
        try:
            results.append(await summarise(item))
        except Exception as e:
            results.append(e)
        finally:
            q.task_done()

async def run_queue(items, n_workers=10):
    q, results = asyncio.Queue(), []
    for it in items:
        q.put_nowait(it)
    workers = [asyncio.create_task(worker(q, results)) for _ in range(n_workers)]
    await q.join()
    for w in workers:
        w.cancel()
    return results

2.9venv, python-dotenv, secrets hygiene, Git

In one line: one virtual environment per project, secrets in .env (never committed), and Git for every change.

Analogy. A venv is a separate toolbox per job so the plumber’s wrench never ends up in the electrician’s kit. .gitignore is the shredder for anything with a password on it.

Why it matters for AI work. AI libraries move fast and conflict with each other. Two projects needing different versions of openai or pydantic will break one another unless isolated. And API keys are money: a leaked key on a public repo can be found and abused within minutes.

Core ideas

What a virtual environment is. A folder (.venv/) holding its own Python interpreter and its own installed packages. Activating it makes python and pip refer to that copy. Delete the folder and you have deleted the project's dependencies without touching anything else. Never commit .venv/.

Reproducibility. Anyone should be able to rebuild your environment. pip freeze > requirements.txt records exact versions of everything installed. For libraries and larger projects, declare dependencies in pyproject.toml (chapter 2.10). Newer tools such as uv speed up creating environments and installing packages, but the ideas are identical.

.env files. A plain text file of KEY=value lines. python-dotenv loads it into os.environ at startup. The rule: .env holds real secrets and is git-ignored; .env.example holds fake placeholder values and is committed so teammates know which variables exist.

Fail fast on missing config. os.environ["OPENAI_API_KEY"] raises KeyError immediately if the variable is missing, which beats a confusing 401 ten minutes later. Use os.environ.get(...) only when a default is genuinely fine.

Git in one table.

Command What it does
git init Start a repository
git status What changed?
git add -p Stage changes piece by piece (review before committing)
git commit -m "msg" Save a snapshot
git diff / git diff --staged See unstaged / staged changes
git log --oneline History
git switch -c feature/x New branch
git restore file Discard uncommitted changes to a file
git revert <sha> Undo a commit by adding a new one

Commit habits. Small commits with messages that say why ("Retry on 429 to stop nightly job failures"), not just what. Use branches for experiments. Commit prompt changes like code, because prompts are code.

Reading the code. The first block creates and activates the environment, installs two packages, records them, writes a .env and a .gitignore before the first commit (so the secret never enters history), and commits. load_dotenv() does not override variables that already exist in the real environment, which is what you want in production, where the platform injects secrets.

A .env.example to commit:

ANTHROPIC_API_KEY=sk-ant-your-key-here
LOG_LEVEL=INFO

Catching secrets before they are committed. Tools like gitleaks or detect-secrets can run as a pre-commit hook and block a commit that contains a key-shaped string.

If a key leaks, in this order:

  1. Revoke or rotate the key at the provider immediately.
  2. Check the provider's usage dashboard for activity you do not recognise.
  3. Remove it from the code and load it from the environment.
  4. Optionally rewrite history (git filter-repo) and force-push, knowing that forks and clones may still hold it. Rotation is the real fix.

Secrets in production. Use your platform's secret manager (AWS Secrets Manager, GCP Secret Manager, GitHub Actions secrets, Kubernetes secrets) rather than shipping .env files. Module 6 covers deployment.

Traps

Trap. Deleting a leaked key from the latest commit does not remove it from Git history. Rotate the key immediately.

Trap. Creating .gitignore after committing .env does nothing for the already-tracked file. Run git rm --cached .env and then rotate the key.

Trap. Installing packages globally (without activating the venv) is the root of most "works on my machine" problems. Check your prompt shows (.venv) first.

Trap. Committing requirements.txt produced by pip freeze in a messy global environment pulls in dozens of unrelated packages. Freeze from a clean venv.

2.10Project structure — src/, prompts/, tests/, notebooks/

In one line: separate importable code, prompt files, tests, and exploration so the notebook mess never leaks into production.

Analogy. A restaurant: kitchen (src), recipe book (prompts), health inspector (tests), and the test kitchen where chefs experiment (notebooks).

Why it matters for AI work. AI projects start in notebooks and rot there. A clear layout lets a teammate find the prompt, change it, run the tests, and ship, without reading a 400-cell notebook.

Core ideas

What goes where.

Folder / file Purpose Rule of thumb
src/<package>/ Importable application code Everything deployed lives here
prompts/ Prompt templates as text files Version them (answer_v2.txt), review changes like code
tests/ Unit tests and eval datasets Mirrors src/ structure
tests/evals/golden.jsonl Question/expected-answer pairs Your regression suite for quality
notebooks/ Exploration Never imported by production code
pyproject.toml Metadata, dependencies, tool config Single source of truth
.env.example Documents required variables Committed; the real .env is not
README.md How to install, run, test If it is not here, it does not exist

Why a src/ layout. Putting the package inside src/ forces you to install it (pip install -e .) before importing it, so tests exercise the installed package the way real users would, and you avoid accidentally importing stray files from the working directory.

Prompts as files. Keeping prompts out of Python strings makes diffs readable, lets non-engineers edit them, and lets you load, hash, and log a prompt_version with each request.

One place for config. A config.py that reads environment variables into a typed settings object (with pydantic-settings) avoids os.environ[...] scattered across the code.

2.11HTTP — requests, status codes, pagination, JSON parsing

In one line: an API call is a method + URL + headers + body; you read the status code, parse the JSON, and follow pagination until there are no more pages.

Analogy. Pagination is a waiter who brings 100 dishes at a time and a note saying “ask for page 2”. You keep asking until the note says “that is everything”.

Why it matters for AI work. Every LLM provider, vector database, and client system you integrate speaks HTTP. When an SDK misbehaves, understanding the raw request and response is how you debug it. Many client systems will not have an SDK at all.

Core ideas

Anatomy of a request.

Part Example Notes
Method GET, POST, PUT, PATCH, DELETE GET reads; POST creates or triggers; PUT replaces; PATCH edits; DELETE removes
URL https://api.example.com/v1/records?limit=100 Query string carries filters and paging
Headers Authorization, Content-Type, Accept, User-Agent Metadata about the request
Body {"text": "hi"} Sent with POST/PUT/PATCH; JSON is typical

Anatomy of a response. A status code, headers (Content-Type, Retry-After, rate-limit headers), and a body. Check the status code first, then parse.

Status code classes. 2xx success, 3xx redirect, 4xx you did something wrong, 5xx they did something wrong. The 4xx/5xx split drives retry logic: fix 4xx, retry (some) 5xx.

Code Meaning What you do
200 / 201 OK / created Parse body
400 / 422 Your request is wrong Fix input, do not retry
401 / 403 Auth problem Check key or permissions
404 Not found Handle gracefully
429 Rate limited Back off, retry
500 / 502 / 503 Server problem Retry with backoff

Also worth knowing: 204 (success, no body), 408 (request timeout), 409 (conflict, often a duplicate), 413 (payload too large), and 504 (gateway timeout).

requests vs httpx. Both have nearly the same API. httpx adds async support, HTTP/2, and stricter, explicit timeouts, which is why this course prefers it. Reuse a Client (it keeps connections open) instead of calling httpx.get repeatedly.

Timeouts are mandatory. Without one, a hung server hangs your program forever. In httpx, timeout=10 applies to connect, read, write, and pool waits individually; use httpx.Timeout(30, connect=5) for finer control.

Pagination styles.

Style Looks like Weakness
Offset / page ?page=7 or ?offset=600&limit=100 Rows shift while you crawl, causing skips or duplicates
Cursor / token ?cursor=abc123 or a next URL Needs sequential fetching, but stable
Link header Link: <...?page=3>; rel="next" Must parse the header (r.links["next"] in httpx/requests)
Time window ?updated_after=2025-01-01T00:00:00Z Needs a reliable timestamp field

Respect rate-limit signals. A 429 often includes Retry-After (seconds or a date). Some APIs add headers like X-RateLimit-Remaining. Read them and slow down before you are blocked.

import httpx

def fetch_all(base_url: str, token: str):
    url, params = f"{base_url}/records", {"limit": 100}
    with httpx.Client(timeout=10, headers={"Authorization": f"Bearer {token}"}) as client:
        while url:
            r = client.get(url, params=params)
            r.raise_for_status()
            body = r.json()
            yield from body["data"]
            url, params = body.get("next"), None       # cursor pagination

2.12Authentication — API keys, headers, rotation

In one line: most AI APIs authenticate with a secret key in a header; you load it from the environment and design for rotating it without downtime.

Analogy. An API key is a hotel key card. Lose it, and you deactivate it and issue a new one — the room (your account) stays the same.

Why it matters for AI work. A key is both identity and a credit card. Clients will also hand you OAuth tokens, basic-auth credentials, and signed requests. Knowing the common schemes and the safe habits for each saves you from both lockouts and breaches.

Core ideas

Common schemes.

Scheme How it is sent Typical use
API key in a custom header x-api-key: ... Anthropic, many SaaS APIs
Bearer token Authorization: Bearer <token> OpenAI, most REST APIs, OAuth access tokens
Basic auth Authorization: Basic base64(user:pass) Older systems, internal services
OAuth 2.0 client credentials Exchange id and secret for a short-lived token Server-to-server integrations with client systems
Signed requests HMAC or cloud signature over the request AWS, webhooks

Key hygiene rules.

  • Load from the environment; never hard-code.
  • Use separate keys per environment (dev, staging, prod) and per service, so a leak has a small blast radius and you can see who spent what.
  • Least privilege: use restricted or scoped keys where the provider offers them.
  • Keep keys on the backend. Anything in browser JavaScript or a mobile app bundle is public.
  • Never log a key. If you must identify it, log only the last four characters.
  • Set spending limits and usage alerts at the provider.

Rotation without downtime. Because you cannot update every server at the same instant, support two valid keys during an overlap window. Create the new key, deploy code that accepts it, move traffic, then revoke the old one.

sequenceDiagram
  participant Ops
  participant Provider
  participant App
  Ops->>Provider: create key B
  Ops->>App: deploy config with B (A still valid)
  App->>Provider: calls use B
  Ops->>Provider: revoke key A

OAuth 2.0 client-credentials with token caching (common for client-system integrations):

import time, httpx

class TokenProvider:
    def __init__(self, token_url: str, client_id: str, client_secret: str):
        self.token_url, self.cid, self.secret = token_url, client_id, client_secret
        self._token: str | None = None
        self._expires_at = 0.0

    def get(self) -> str:
        if self._token and time.time() < self._expires_at - 30:   # refresh 30s early
            return self._token
        r = httpx.post(self.token_url, timeout=10, data={
            "grant_type": "client_credentials",
            "client_id": self.cid, "client_secret": self.secret})
        r.raise_for_status()
        body = r.json()
        self._token = body["access_token"]
        self._expires_at = time.time() + body.get("expires_in", 3600)
        return self._token

Handling 401 during a request. Refresh the token once and retry; if it still fails, raise. Do not loop forever.

2.13Retries — exponential backoff with jitter

In one line: when a call fails transiently (429, 5xx, timeouts), wait 1 s, 2 s, 4 s… plus randomness, so thousands of clients do not retry in lockstep.

Analogy. A crowd at a jammed door. If everyone pushes again at exactly the same moment, it stays jammed. Jitter is everyone waiting a slightly random number of seconds.

Why it matters for AI work. LLM APIs rate-limit and occasionally fail. A pipeline without retries dies on the first hiccup; a pipeline with naive retries (instant, unlimited) can hammer a struggling service and get you blocked. Good retry logic is what makes the Resilient Ingestor resilient.

Core ideas

Decide what to retry. Retry only transient failures: network errors, timeouts, 429, 500, 502, 503, 504. Never retry 400, 401, 403, 404, or 422; the same request will fail the same way.

Exponential backoff. Each failed attempt doubles the wait: base × 2^attempt. This gives a struggling server room to recover.

Jitter. Add randomness so clients desynchronise. "Full jitter" picks a random wait between 0 and the exponential cap, and is a good default.

Attempt Exponential cap (base 1 s) Full-jitter wait range
0 1 s 0 – 1 s
1 2 s 0 – 2 s
2 4 s 0 – 4 s
3 8 s 0 – 8 s
4 16 s 0 – 16 s
5+ capped at 30 s 0 – 30 s

Honour Retry-After. If the server says how long to wait, wait at least that long.

Bound everything. Set a maximum attempt count and a maximum total time. An infinite retry loop turns an outage into a cascading failure.

Idempotency. Retrying is only safe if repeating the call cannot cause a second side effect. GET, PUT, and DELETE are meant to be idempotent; POST usually is not. For POST operations like "create payment", send an idempotency key (a unique id per logical operation) so the server can recognise repeats.

Built-in retries. The OpenAI and Anthropic SDKs already retry some errors (default max_retries is small, typically 2). Know what they do before stacking your own retries on top, or you multiply attempts.

flowchart LR
  C["Call"] --> R{"Success?"}
  R -->|yes| D["Done"]
  R -->|429 or 5xx| W["Wait base x 2^attempt + random"]
  W --> C
  R -->|400 401 403| F["Fail fast, no retry"]

Code

import random, time
import httpx
from tenacity import retry, stop_after_attempt, wait_random_exponential, retry_if_exception

def is_retryable(e: BaseException) -> bool:
    if isinstance(e, httpx.TimeoutException):
        return True
    return isinstance(e, httpx.HTTPStatusError) and e.response.status_code in {429, 500, 502, 503, 504}

@retry(retry=retry_if_exception(is_retryable), wait=wait_random_exponential(min=1, max=30),
       stop=stop_after_attempt(6), reraise=True)
def fetch(url: str) -> dict:
    r = httpx.get(url, timeout=10)
    r.raise_for_status()
    return r.json()

# Hand-rolled "full jitter" if you cannot add a dependency:
def sleep_for(attempt: int, base=1.0, cap=30.0) -> float:
    return random.uniform(0, min(cap, base * 2 ** attempt))

Reading the code. is_retryable encodes the policy in one place. The decorator retries only when that returns True, waits a random exponential time between 1 and 30 seconds, gives up after 6 attempts, and reraise=True surfaces the original error instead of tenacity's wrapper. sleep_for is the same idea without a dependency.

A hand-written loop that honours Retry-After:

def fetch_with_retries(client: httpx.Client, url: str, max_attempts: int = 5):
    for attempt in range(max_attempts):
        try:
            r = client.get(url)
            if r.status_code in {429, 500, 502, 503, 504}:
                retry_after = r.headers.get("Retry-After")
                delay = float(retry_after) if retry_after and retry_after.isdigit() \
                        else sleep_for(attempt)
                time.sleep(delay)
                continue
            r.raise_for_status()
            return r.json()
        except httpx.TimeoutException:
            time.sleep(sleep_for(attempt))
    raise RuntimeError(f"gave up after {max_attempts} attempts: {url}")

2.14Webhooks — signature verification and idempotency

In one line: a webhook is the other system calling you; verify the HMAC signature to prove it is really them, and dedupe by event id because they will retry.

Analogy. A courier rings your bell with a parcel. You check the company seal (signature) and that you have not already signed for this tracking number (idempotency).

Why it matters for AI work. Payments, CRMs, document-signing tools, and batch-job APIs notify you by webhook ("payment succeeded", "batch finished"). If you accept unsigned requests, anyone can fake events; if you do not dedupe, a retried event can trigger the same action twice, such as emailing a customer twice or running an expensive LLM job again.

Core ideas

Polling vs webhooks. Polling means you ask repeatedly "anything new?" Webhooks mean the provider tells you when something happens. Webhooks are faster and cheaper, but you must expose a public endpoint and defend it.

HMAC signatures. The provider and you share a secret. For each event the provider computes HMAC-SHA256(secret, body) and sends it in a header. You recompute it over the raw bytes you received and compare. A match proves the sender knows the secret and the body was not altered.

Replay protection. An attacker could capture a valid request and resend it later. Providers therefore include a timestamp (often signed together with the body). Reject events older than a tolerance, such as 5 minutes.

Idempotency. Providers deliver at least once: if your endpoint is slow or returns an error, they retry, and sometimes they send duplicates anyway. Record each processed event.id and skip repeats. A unique database constraint is the most reliable guard because it is atomic even under concurrent requests.

Respond fast, work later. Return 200 quickly after verifying and recording the event, then process in the background (a queue or BackgroundTasks). If you do heavy work inline, the provider times out and retries, creating duplicates.

Order is not guaranteed. Event B may arrive before event A. Design handlers to tolerate that, for example by fetching the latest state from the API instead of trusting the payload alone.

sequenceDiagram
  participant P as Provider
  participant API as Your endpoint
  participant DB
  P->>API: POST event, header X-Signature
  API->>API: recompute HMAC of raw body, compare
  API->>DB: insert event_id if new
  DB-->>API: duplicate? skip
  API-->>P: 200 quickly
  API->>API: process in background

Code

import hmac, hashlib
from fastapi import FastAPI, Request, HTTPException

app = FastAPI()
SECRET = b"whsec_..."
seen: set[str] = set()                       # use a DB unique constraint in production

@app.post("/webhooks/payments")
async def payments(request: Request):
    raw = await request.body()                # verify the RAW bytes, not re-serialised JSON
    expected = hmac.new(SECRET, raw, hashlib.sha256).hexdigest()
    if not hmac.compare_digest(expected, request.headers.get("X-Signature", "")):
        raise HTTPException(401, "bad signature")
    event = await request.json()
    if event["id"] in seen:
        return {"status": "duplicate"}
    seen.add(event["id"])
    # enqueue work; respond fast so the provider does not time out and retry
    return {"status": "ok"}

Reading the code. request.body() gives the exact bytes sent; re-encoding parsed JSON can change spacing or key order and break the signature. hmac.compare_digest compares in constant time. A bad signature returns 401 before any parsing of the content for business logic. The in-memory seen set disappears on restart and is not shared between server processes, which is why production code uses a database.

A production-style version with timestamp tolerance, a database uniqueness check, and background processing:

import hmac, hashlib, sqlite3, time
from fastapi import FastAPI, Request, HTTPException, BackgroundTasks

app = FastAPI()
SECRET = b"whsec_..."
TOLERANCE_S = 300
db = sqlite3.connect("events.db", check_same_thread=False)
db.execute("CREATE TABLE IF NOT EXISTS events (id TEXT PRIMARY KEY, received_at REAL)")

def process(event: dict) -> None:
    ...   # slow work: update records, call an LLM, send email

@app.post("/webhooks/payments")
async def payments(request: Request, bg: BackgroundTasks):
    raw = await request.body()
    ts = request.headers.get("X-Timestamp", "")
    sig = request.headers.get("X-Signature", "")

    # Sign "timestamp.body" so the timestamp cannot be swapped by an attacker
    signed = ts.encode() + b"." + raw
    expected = hmac.new(SECRET, signed, hashlib.sha256).hexdigest()
    if not hmac.compare_digest(expected, sig):
        raise HTTPException(401, "bad signature")
    if not ts.isdigit() or abs(time.time() - int(ts)) > TOLERANCE_S:
        raise HTTPException(400, "stale timestamp")

    event = await request.json()
    try:
        with db:
            db.execute("INSERT INTO events (id, received_at) VALUES (?, ?)",
                       (event["id"], time.time()))
    except sqlite3.IntegrityError:
        return {"status": "duplicate"}          # primary key stops repeats atomically

    bg.add_task(process, event)
    return {"status": "ok"}

Each provider defines its own header names and signing recipe (Stripe uses a Stripe-Signature header with t= and v1= parts; GitHub uses X-Hub-Signature-256 with a sha256= prefix). Always follow the provider's documentation exactly; the header names above are illustrative.

Testing locally. Providers cannot reach localhost. Use a tunnel tool (ngrok, Cloudflare Tunnel) to expose your dev server, and use the provider's "send test event" button. Also write unit tests that build a valid signature yourself:

def sign(body: bytes, ts: str, secret=b"whsec_...") -> str:
    return hmac.new(secret, ts.encode() + b"." + body, hashlib.sha256).hexdigest()

Security checklist. Verify signature on raw bytes · constant-time compare · reject stale timestamps · dedupe by event id · return 2xx fast · never log the secret · serve only over HTTPS · rotate the signing secret periodically (like API keys).

Traps

Trap. Comparing signatures with == leaks timing information. Use hmac.compare_digest. Also check a timestamp header to block replayed requests.

Trap. Parsing the JSON first and then re-serialising it to verify. Whitespace and key order change, so valid signatures fail. Verify the raw body.

Trap. Doing slow work before responding. The provider times out, retries, and you process the same event several times.

Trap. Marking an event "seen" before it is processed successfully can lose it if processing crashes. Decide on your guarantee (store it first and have a recovery job, or use a transactional outbox).

2.15OpenAI SDK — chat completions and streaming

In one line: chat.completions.create returns the whole answer; stream=True gives you tokens as they are generated, which is what makes chat UIs feel instant.

Analogy. Non-streaming is waiting for the full letter in the post. Streaming is a phone call — you hear the first word immediately.

Why it matters for AI work. This single call is the heart of most LLM apps. Knowing its parameters, response fields, errors, and streaming behaviour is the difference between a demo and something you can run in production.

Core ideas

Messages. The conversation is a list of {"role", "content"} dicts. system sets behaviour and rules, user is the person's input, assistant is previous model replies (you resend history yourself, because the API is stateless), and tool carries tool results in function-calling flows. Order matters.

Key parameters.

Parameter What it does Practical advice
model Which model answers Pin an explicit model name in config
temperature Randomness (0 is most deterministic) 0 to 0.3 for extraction and classification; higher for creative text
max_tokens Hard cap on output length Always set; protects cost and latency
top_p Nucleus sampling Change temperature or top_p, not both
seed Best-effort reproducibility Not a guarantee
response_format Ask for JSON or a JSON schema Prefer schema-constrained output over parsing free text
tools Functions the model may call Covered in the agents module
stream Send tokens as they are produced Use for any user-facing chat

The response object. r.choices[0].message.content is the text. r.choices[0].finish_reason tells you why it stopped: "stop" (finished naturally), "length" (hit max_tokens, so the answer may be cut off), "tool_calls", or "content_filter". r.usage holds prompt_tokens, completion_tokens, and total_tokens, which you need for cost tracking.

How streaming works. The server sends small chunks over a long-lived HTTP response (server-sent events). Each chunk's delta.content is a fragment of text. The final chunk carries finish_reason. With stream_options={"include_usage": True}, a last chunk includes token usage (and has an empty choices list, which is why the code checks chunk.choices first).

Metrics that matter for streams. Time to first token (TTFT) is how long before the user sees anything; tokens per second is how fast it flows. TTFT drives perceived speed.

Errors you should handle. The SDK raises typed exceptions: openai.RateLimitError (429), openai.APITimeoutError, openai.APIConnectionError, openai.AuthenticationError (401), openai.BadRequestError (400, for example context too long), and the general openai.APIStatusError. Map them to your own error classes (chapter 2.3).

Measuring time to first token and collecting the full text:

import time

def stream_answer(client, messages, model="gpt-4o-mini"):
    t0 = time.perf_counter()
    first = None
    parts = []
    usage = None
    stream = client.chat.completions.create(
        model=model, messages=messages, stream=True,
        stream_options={"include_usage": True})
    for chunk in stream:
        if chunk.choices and (text := chunk.choices[0].delta.content):
            if first is None:
                first = time.perf_counter() - t0
            parts.append(text)
            yield text                          # hand tokens to the UI as they arrive
        if chunk.usage:
            usage = chunk.usage
    total = time.perf_counter() - t0
    print(f"\nTTFT {first:.2f}s, total {total:.2f}s, usage {usage}")

2.16Anthropic SDK — prompt caching

In one line: mark a long, stable prefix (system prompt, documents, tools) with cache_control; repeat calls within the cache window read it at a big discount and lower latency.

Analogy. Photocopying the same 50-page manual for every customer vs keeping one copy on the counter that everyone reads.

Why it matters for AI work. Many apps send the same large context on every call: a policy document, a codebase summary, a long set of instructions and examples. Without caching you pay full price to re-process it each time. With caching, the repeated part becomes a small fraction of the cost.

Core ideas

The Messages API shape. Compared with the OpenAI call, note three differences: system is a separate top-level parameter (not a message), max_tokens is required, and the reply is a list of content blocks, so the text is in r.content[0].text (check block.type == "text" when tools are involved).

How caching works. You add "cache_control": {"type": "ephemeral"} to a content block. Everything from the start of the prompt up to and including that block becomes a cached prefix. The first call writes the cache (slightly more expensive than a normal call). Later calls with an identical prefix read it (much cheaper and faster). The cache lives for a short time (about five minutes by default, refreshed each time it is used; longer options exist), so it suits bursts of related requests.

Prefix order. The prompt is assembled as tools, then system, then messages. For caching to hit, everything before your breakpoint must be byte-for-byte identical. Put the stable content first and the changing content (the user question, timestamps, per-request ids) last.

Minimum size. Prefixes shorter than a model-specific minimum (on the order of a thousand tokens or more) are not cached. Tiny system prompts will show zero cache activity, which is normal.

Cost model (check current pricing). Typically a cache write costs a bit more than normal input tokens and a cache read costs a small fraction (around a tenth). The saving is therefore large when many calls share a big prefix.

Scenario Effect
1 call, big prefix Slightly more expensive (cache write)
10 calls inside the window The 9 repeat calls read the cache: large saving
Calls spaced longer than the cache lifetime Cache expires; you pay writes again
Prefix changes each call Never hits; wasted write premium

  S["System + 40 page policy doc, cache_control"] --> C1["Call 1: cache write, full price plus a bit"]
  S --> C2["Call 2..N: cache read, much cheaper"]
  Q["Changing user question"] --> C1
  Q --> C2

2.17Client configuration — timeouts, base_url, connection pooling

In one line: set explicit timeouts and retries, reuse one client (it pools connections), and point base_url at any OpenAI-compatible server (Ollama, vLLM, LiteLLM, Azure gateways).

Analogy. One client is a car you keep running. Creating a client per request is buying a new car for every trip to the shop.

Why it matters for AI work. In production the biggest causes of outages are not "the model is wrong" but "a call hung", "we opened too many connections", or "the provider was slow and our workers all blocked". Client settings are cheap insurance. And base_url lets you develop locally for free and switch providers without rewriting code.

Core ideas

Four kinds of timeout. Connect (establishing the connection), read (waiting for data), write (sending data), and pool (waiting for a free connection). A single number sets all four; a structured httpx.Timeout lets you be strict on connect (5 s) and generous on read (30 to 60 s for long generations).

Match the timeout to your SLA. If a web request must answer within 10 seconds, a 120-second LLM timeout makes no sense. Decide your budget, set the timeout below it, and have a fallback.

Retries. The SDK's max_retries covers connection errors, 408, 409, 429, and 5xx with backoff. Set it deliberately (chapter 2.13) and remember it multiplies with any retries you add.

Connection pooling. HTTP connections are expensive to establish (DNS, TCP, TLS). A client keeps a pool of open connections and reuses them. max_connections caps total concurrent connections; max_keepalive_connections caps idle ones kept warm. Match these to your concurrency limit (the semaphore size in chapter 2.8).

One client per process. Create it once at startup and share it. In FastAPI, create it in the lifespan handler and close it on shutdown.

base_url and OpenAI-compatible servers. Many tools expose the same API shape: Ollama, vLLM, LM Studio, LiteLLM proxies, and cloud gateways. Point base_url at them and reuse your code. Compatibility is broad but not perfect: some parameters (tools, structured output, logprobs) may be unsupported or behave differently, so test the features you rely on.

Environment variables. The OpenAI SDK reads OPENAI_API_KEY and OPENAI_BASE_URL automatically, so you can switch targets by configuration alone.

Choosing pool sizes. If you run 10 concurrent tasks, a pool of 10 to 20 is plenty. Setting 1,000 does not make the provider faster; it just invites rate-limit errors.

Proxies and corporate networks. httpx honours standard proxy environment variables (HTTPS_PROXY). Behind a TLS-intercepting proxy you may need to point it at a custom certificate bundle. Do not disable certificate verification to "fix" it.

Trap. Assuming "OpenAI-compatible" means identical. Test tool calling, JSON mode, and streaming on the target server.

Trap. A read timeout that is shorter than your longest legitimate generation will cut off good answers. Streaming helps because data keeps arriving.

2.18DSPy hands-on — compile and optimise

In one line: build a small DSPy program with a real metric and dev set, compile it, and compare it with your hand-written prompt.

Analogy. Hand-writing prompts is tuning a guitar by ear on stage. DSPy is a tuner: you say what "in tune" means (the metric) and it adjusts until the score improves.

Why it matters for AI work. Prompt tweaking by gut feel does not scale and breaks when you change models. DSPy turns "write a better prompt" into an engineering loop: define inputs and outputs, define a metric, give examples, and let an optimizer search for instructions and few-shot examples that score higher.

Core ideas

The vocabulary.

Term Meaning
Signature A declaration of inputs and outputs (and a docstring describing the task)
Module A strategy for fulfilling a signature: dspy.Predict, dspy.ChainOfThought, or your own class composing several steps
LM The configured language model (dspy.configure(lm=...))
Example A labelled data point; .with_inputs("text") marks which fields are inputs
Metric A function that scores a prediction against the expected answer
Optimizer An algorithm (such as MIPROv2) that searches for better instructions and demonstrations
Compile Run the optimizer to produce an improved program

The workflow.

  1. Define the task as a signature.
  2. Build a labelled dataset and split it into train and dev (never mix them).
  3. Write a metric that returns true/false or a number.
  4. Evaluate the baseline on dev.
  5. Compile with an optimizer using only train.
  6. Evaluate the compiled program on dev and compare the score and the cost.
  7. Save the program and version it.

Metric design is the real work. A metric that is too lenient rewards bad answers; one that is too strict rejects good ones. For extraction, exact or tolerance-based comparison is easy. For free text, you may use another model as a judge, but validate the judge against human labels first.

Dataset size. Dozens of examples can show a signal; hundreds give stabler results. Real data from your client beats synthetic data, because synthetic data tends to be easier than the real thing.

When to use it. DSPy shines when you have a measurable task, labelled examples, and expect to change models or prompts repeatedly. For one-off prompts without a metric, plain prompting is simpler. Optimisation costs real money in LLM calls, so start with the light setting.

Code

import dspy, random
dspy.configure(lm=dspy.LM("openai/gpt-4o-mini", temperature=0))

class Extract(dspy.Signature):
    """Extract the invoice total in INR as a number."""
    text: str = dspy.InputField()
    total: float = dspy.OutputField()

data = [dspy.Example(text=f"Invoice ... Grand total: Rs. {n:,}", total=float(n)).with_inputs("text")
        for n in random.sample(range(500, 90_000), 40)]
train, dev = data[:25], data[25:]

def metric(ex, pred, trace=None):
    try:
        return abs(float(pred.total) - ex.total) < 0.5
    except (TypeError, ValueError):
        return False

baseline = dspy.Predict(Extract)
evaluate = dspy.Evaluate(devset=dev, metric=metric, display_progress=True)
print("baseline:", evaluate(baseline))

optimised = dspy.MIPROv2(metric=metric, auto="light").compile(baseline, trainset=train)
print("optimised:", evaluate(optimised))
optimised.save("extract_total.json")

Reading the code.

  • The signature's docstring is the task instruction; the typed fields tell DSPy what goes in and what must come out (a float).
  • random.sample(range(500, 90_000), 40) makes 40 distinct totals; the f-string {n:,} formats them with thousands separators like "Rs. 12,345", so the model must read a number containing commas.
  • The first 25 examples train; the last 15 are held out as the dev set.
  • The metric returns False for unparseable output instead of crashing, so a bad prediction just scores zero.
  • MIPROv2(auto="light") is a low-budget search. It proposes instructions and picks demonstrations that maximise the metric on the train set.

Make runs reproducible. Add random.seed(42) before sampling so train and dev are identical between runs; otherwise score changes may just be dataset luck.

Try a stronger module with one line: swap dspy.Predict(Extract) for dspy.ChainOfThought(Extract) to make the model reason before answering, then evaluate and compare. Cheap experiments like this are DSPy's strength.

Reporting results honestly. Present baseline vs optimised on the dev set, state how many examples, and include cost and latency. Optimised programs often add few-shot examples, which makes prompts longer and costlier per call. A 4-point gain that doubles cost may not be worth it.

DSPy's API evolves quickly; if an argument or attribute differs in your installed version, trust the current docs over this snippet.

Traps

Trap. Never evaluate on the training examples. Keep the dev set untouched, or your “improvement” is memorisation.

Trap. Tuning the optimizer settings repeatedly against the same dev set slowly overfits to it. Keep a final test set you look at once.

Trap. A metric that only checks the output format, not the value, makes every program look great.

Trap. Forgetting cost. A large optimisation run can make hundreds or thousands of model calls.

Design note on concurrency and cursors. Cursor pagination is inherently sequential: you only learn the next cursor after fetching the current page. The speed-up comes from (a) processing and writing earlier pages while fetching the next, and (b) if the API allows, splitting the data into independent ranges (by date or id range) and crawling each range in its own task, each with its own checkpoint entry.

Milestones

  1. Skeleton. Project layout, pyproject.toml, settings, logging, .env.example. Commit.
  2. Happy path. Fetch pages sequentially, validate, write JSONL. Test with respx.
  3. Resilience. Add retries with jitter and Retry-After. Simulate failures with respx side effects.
  4. Checkpointing. After each page, atomically write {"cursor": ..., "written": N}. On start, read it and continue. Kill the process mid-run and confirm it resumes.
  5. Concurrency. Introduce range-splitting with a semaphore, or a pipeline where a writer task consumes a queue.
  6. Hardening. Reject-file handling, summary report at the end, mypy strict, README.

A starting skeleton

import asyncio, json, os, random
from pathlib import Path
import httpx
from pydantic import BaseModel, ValidationError

class Record(BaseModel):
    id: str
    amount: float
    currency: str

def write_atomic(path: Path, obj: dict) -> None:
    tmp = path.with_suffix(".tmp")
    tmp.write_text(json.dumps(obj), encoding="utf-8")
    tmp.replace(path)

async def get_page(client: httpx.AsyncClient, cursor: str | None, max_attempts: int = 6) -> dict:
    for attempt in range(max_attempts):
        try:
            r = await client.get("/records", params={"limit": 100, **({"cursor": cursor} if cursor else {})})
            if r.status_code in {429, 500, 502, 503, 504}:
                ra = r.headers.get("Retry-After")
                await asyncio.sleep(float(ra) if ra and ra.isdigit()
                                    else random.uniform(0, min(30, 2 ** attempt)))
                continue
            r.raise_for_status()
            return r.json()
        except httpx.TimeoutException:
            await asyncio.sleep(random.uniform(0, min(30, 2 ** attempt)))
    raise RuntimeError("page failed after retries")

async def ingest(base_url: str, out: Path, state: Path, rejects: Path) -> None:
    cursor = json.loads(state.read_text())["cursor"] if state.exists() else None
    headers = {"Authorization": f"Bearer {os.environ['API_TOKEN']}"}
    async with httpx.AsyncClient(base_url=base_url, headers=headers, timeout=httpx.Timeout(20, connect=5)) as client:
        while True:
            page = await get_page(client, cursor)
            with out.open("a", encoding="utf-8") as good, rejects.open("a", encoding="utf-8") as bad:
                for raw in page["data"]:
                    try:
                        good.write(Record.model_validate(raw).model_dump_json() + "\n")
                    except ValidationError as e:
                        bad.write(json.dumps({"raw": raw, "error": e.errors()[0]["msg"]}) + "\n")
            cursor = page.get("next")
            write_atomic(state, {"cursor": cursor})
            if not cursor:
                break

Why this resumes correctly. The cursor is saved only after a page is fully written. If the process dies between writing records and saving the cursor, the next run re-fetches that page and writes it again, producing duplicates. To make that safe, either dedupe by id at the end, keep a set of written ids in the checkpoint, or write the page and the cursor together in one SQLite transaction. Choosing and explaining this trade-off is part of the challenge.

Appendix C — Debugging checklist for API integrations

Work down this list before asking for help. Most problems are in the first five lines.

  1. Is the key loaded? Print only bool(os.environ.get("KEY")) or the last four characters.
  2. Is the URL right? Check the base URL, version prefix (/v1), and trailing slashes.
  3. What is the exact status code and body? Print r.status_code and r.text[:500].
  4. Are the headers right? Content type, authorization scheme, API version header.
  5. Is the body shaped correctly? Compare against the provider's example, field by field.
  6. Is it a rate limit? Look for 429 and Retry-After; lower concurrency.
  7. Is it a timeout? Raise the read timeout or stream; check network and proxy.
  8. Is the output truncated? Check finish_reason and max_tokens.
  9. Is the context too long? Count tokens; trim or summarise.
  10. Does it fail only in production? Compare environment variables, versions (pip freeze), and network access.
  11. Can you reproduce it with curl? If yes, the problem is the API call; if no, it is your code.
  12. Did something change? Check Git history, dependency upgrades, and provider status pages.

Appendix D — Final self-assessment

Answer without looking. Anything you cannot explain in two sentences is a chapter to revisit.

1. Why is a mutable default argument dangerous?

The default object is created once, when the function is defined, and shared across calls. Use None and create the object inside. (2.1)

2. When do you choose JSONL over JSON?

For append-heavy, large, or streamed data such as logs and eval sets; each line is independent. (2.2)

3. What is dependency injection and why does it help testing?

Passing the client or collaborator into a class instead of building it inside. Tests can pass a fake. (2.3, 2.6)

4. What does functools.wraps preserve?

The original function's name, docstring, and metadata, so logs and tracebacks stay meaningful. (2.4)

5. Why use Pydantic when you already have type hints?

Hints are not enforced at runtime. Pydantic validates real data as it arrives. (2.5)

6. What is the risk of mocking everything?

You only test your assumptions. Keep a small marked set of live tests. (2.6)

7. Name five fields to log for every LLM call.

Request id, model, prompt version, tokens in and out, latency, cost, status. (2.7)

8. Why limit concurrency even with async?

Provider rate limits and connection limits. A semaphore keeps you inside them. (2.8)

9. What is the first thing to do after a key leaks?

Rotate or revoke it. Removing it from the code does not remove it from history. (2.9)

10. Why keep prompts in files?

Clean diffs, versioning, easy review, and the ability to log which prompt version served each request. (2.10)

11. Which pagination style is safest when data changes during a crawl?

Cursor-based. Offset paging can skip or repeat rows. (2.11)

12. Difference between 401 and 403?

401: credentials missing or invalid. 403: credentials valid but not permitted. (2.12)

13. What do backoff and jitter each solve?

Backoff gives the service time to recover; jitter stops clients retrying in lockstep. (2.13)

14. Why verify a webhook on the raw body?

Re-serialising parsed JSON changes bytes, so the recomputed signature would not match. (2.14)

15. What does finish_reason == "length" tell you?

The answer was cut off at max_tokens. (2.15)

16. Where do you put changing content for prompt caching?

After the cached prefix, typically at the end of the final user message. (2.16)

17. Why create one client per process?

Connection pooling and lower latency; avoids repeated handshakes. (2.17)

18. Why must the dev set stay untouched in DSPy?

Otherwise the score measures memorisation, not generalisation. (2.18)
