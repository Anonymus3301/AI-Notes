5.1ReAct loop and planner–executor

In one line: ReAct = think, act, observe, repeat. Planner–executor = write the whole plan first, then execute steps, re-planning only when something breaks.

Analogy. ReAct is improv theatre: react to each moment. Planner–executor is a heist movie: the plan on the whiteboard, then the crew executes, and someone yells “new plan!” when the alarm goes off.

Core ideas

ReAct interleaves reasoning and tool calls, so it adapts to surprises but can wander. Planner–executor commits to steps up front, which is more predictable and easier to audit, but needs a re-plan path when a step fails. Pick ReAct for exploratory tasks and planner–executor for multi-step jobs with known structure.

flowchart TB
  subgraph ReAct
    T1["Think"] --> A1["Act"] --> O1["Observe"] --> T1
  end
  subgraph PlanExecute
    PL["Planner writes steps 1..n"] --> EX["Executor runs step i"]
    EX --> CK{"Step ok?"}
    CK -->|yes, more steps| EX
    CK -->|failed| RP["Re-plan"] --> EX
    CK -->|all done| FIN["Final answer"]
  end

Code

from langchain_openai import ChatOpenAI
from langchain_core.tools import tool
from langgraph.prebuilt import create_react_agent

@tool
def get_order(order_id: str) -> dict:
    """Look up an order by id."""
    return {"id": order_id, "status": "delivered", "amount": 1299}

@tool
def create_refund(order_id: str, amount: int) -> str:
    """Create a refund for an order."""
    return f"refund created for {order_id}: {amount}"

agent = create_react_agent(ChatOpenAI(model="gpt-4o-mini"), tools=[get_order, create_refund])
result = agent.invoke({"messages": [("user", "Order A-17 arrived broken, please refund it")]})
for m in result["messages"]:
    print(m.type, getattr(m, "content", "")[:120])

Reading the code. The docstring and type hints become the tool description the model reads. The printed messages show the trajectory: human, AI tool call, tool result, final answer. Reading trajectories is the best debugging habit you can build.

Trap. Agents love to loop. Set a recursion_limit, a step budget, and a cost budget.

5.2The tool arbiter pattern

In one line: put a deterministic gate between “the model wants to call a tool” and “the tool runs”: it checks permissions, arguments, limits, and risk, and can require human approval.

Analogy. The model is an enthusiastic intern with ideas. The arbiter is the manager who signs off on purchases above ₹10,000 and refuses anything not on the approved vendor list.

Why it matters for AI work. A model can be tricked or simply wrong. Anything that moves money or data needs rules the model cannot talk its way around. OWASP calls the failure “excessive agency”.

flowchart LR
  LLM["LLM proposes tool call"] --> ARB{"Arbiter"}
  ARB -->|allowed and low risk| RUN["Execute tool"]
  ARB -->|high risk| HUM["Human approval queue"]
  ARB -->|forbidden or invalid| REJ["Reject with reason back to LLM"]
  RUN --> LOG["Audit log"]
  HUM --> RUN

Code

from dataclasses import dataclass
from pydantic import BaseModel, ValidationError

class RefundArgs(BaseModel):
    order_id: str
    amount: int

POLICY = {
    "get_order":     {"risk": "low",  "schema": None},
    "create_refund": {"risk": "high", "schema": RefundArgs, "max_amount": 5000},
}

@dataclass
class Decision:
    action: str          # "run", "approve", "reject"
    reason: str = ""

def arbitrate(tool: str, args: dict, user_roles: set[str]) -> Decision:
    rule = POLICY.get(tool)
    if rule is None:
        return Decision("reject", f"unknown tool {tool}")
    if rule["schema"]:
        try:
            parsed = rule["schema"](**args)
        except ValidationError as e:
            return Decision("reject", f"bad args: {e.errors()[0]['msg']}")
        if tool == "create_refund" and parsed.amount > rule["max_amount"]:
            return Decision("approve", "amount above auto-approve limit")
    if rule["risk"] == "high" and "support_lead" not in user_roles:
        return Decision("approve", "high-risk tool requires a lead")
    return Decision("run")

print(arbitrate("create_refund", {"order_id": "A-17", "amount": 9000}, {"agent"}))

Reading the code. Unknown tools are rejected (default deny). Arguments are validated by a schema before anything runs. Rejections carry a reason that goes back to the model so it can correct itself. Every decision should also be written to an audit log.

Trap. Using another LLM as the only arbiter. LLM judges are useful for quality checks, but permissions and limits must be enforced in code.

5.3Function calling and MCP (Model Context Protocol)

In one line: MCP is an open protocol so any AI app (the host/client) can discover and call tools, resources, and prompts exposed by any MCP server: write the integration once, use it everywhere.

Analogy. USB-C for AI. Before: a different cable for every device. After: one port, and any compliant device just works.

Core ideas

Function calling lets a model request a tool call as structured JSON. MCP standardises how tools are described and reached, over stdio (local process) or HTTP (remote). The host keeps one client per server, and the model sees all discovered tools together.

  subgraph Host["Host app: Claude Desktop, Cursor, your agent"]

    C2["MCP client"]
  end
  C1 -->|stdio| S1["MCP server: orders DB"]
  C2 -->|HTTP| S2["MCP server: ticketing API"]
  S1 --> T1["tools: get_order"]
  S1 --> R1["resources: schema docs"]
  S2 --> T2["tools: create_ticket"]
Primitive Who controls it Example
Tools The model decides to call create_ticket
Resources The app decides to attach A schema file, a policy
Prompts The user picks “Triage this ticket” template

Code

# ops_server.py
from mcp.server.fastmcp import FastMCP
mcp = FastMCP("ops")

@mcp.tool()
def get_order(order_id: str) -> dict:
    """Look up an order by id."""
    return {"id": order_id, "status": "delivered"}

@mcp.resource("policy://refunds")
def refund_policy() -> str:
    """The refund policy text."""
    return "Refunds within 30 days for damaged items."

@mcp.prompt()
def triage(ticket: str) -> str:
    return f"Classify this ticket and suggest the next action:\n{ticket}"

if __name__ == "__main__":
    mcp.run()          # stdio transport by default

pip install "mcp[cli]"
mcp dev ops_server.py     # opens the MCP Inspector to try your tools

Reading the code. Decorators turn plain functions into protocol-level tools, resources and prompts; names, docstrings and type hints become their descriptions. The Inspector lets you test a server before any model touches it.

Trap. An MCP server runs with your credentials. Only install servers you trust, and scope their permissions like any other service account.

5.4Tool use — Tavily web search, parallel tool calls

In one line: give the agent a search tool that returns clean, LLM-ready snippets, and let it request several independent tools in one turn.

Analogy. Sending three interns to three libraries at the same time instead of one intern visiting them one after another.

from tavily import TavilyClient
tavily = TavilyClient()          # reads TAVILY_API_KEY
res = tavily.search("RBI guidelines on digital lending 2025", max_results=5)
for r in res["results"]:
    print(r["title"], r["url"])

from langchain_tavily import TavilySearch
agent = create_react_agent(ChatOpenAI(model="gpt-4o-mini"), tools=[TavilySearch(max_results=3), get_order])

Core ideas

In the raw OpenAI API a single assistant message can contain several tool_calls. Run independent ones concurrently and reply with exactly one tool message per tool_call_id. This cuts latency without extra model calls.

import asyncio, json

async def run_calls(tool_calls, registry):
    async def one(call):
        result = await registry[call.function.name](**json.loads(call.function.arguments))
        return {"role": "tool", "tool_call_id": call.id, "content": json.dumps(result)}
    return await asyncio.gather(*(one(c) for c in tool_calls))

sequenceDiagram
  participant LLM
  participant App
  LLM->>App: tool_calls weather Pune, weather Delhi, fx USD-INR
  par in parallel
    App->>App: weather Pune
  and
    App->>App: weather Delhi
  and
    App->>App: fx rate
  end
  App->>LLM: three tool results

Reading the code. asyncio.gather runs all calls at once and keeps results in order. Matching tool_call_id is mandatory; a missing reply makes the API reject the next request.

Trap. Web results are untrusted input, a perfect prompt-injection vector. Never let search content trigger high-risk tools without the arbiter.

5.5LangGraph — state, nodes, edges, checkpointing, human-in-the-loop

In one line: LangGraph models an agent as a state machine: a typed state, nodes that update it, edges (including conditional ones) that route between nodes, and a checkpointer that saves state so runs can pause and resume.

Analogy. A board game. The state is the board; nodes are moves; edges are the rules for whose turn is next; a checkpoint is a photo of the board so you can continue tomorrow.

Core ideas

Explicit state makes agents debuggable and testable. A checkpointer stores state per thread_id, enabling memory across turns, pause and resume, and replay. interrupt() stops the graph and surfaces a question to a human; Command(resume=...) continues from exactly that point.

flowchart LR
  START(("start")) --> intake["intake: extract claim"]
  intake --> assess["assess: check policy"]
  assess -->|amount under 10k| approve["auto approve"]
  assess -->|amount over 10k| human["interrupt: human review"]
  human --> approve
  human --> deny["deny"]
  approve --> END(("end"))
  deny --> END

Code

from typing import TypedDict, Literal
from langgraph.graph import StateGraph, START, END
from langgraph.checkpoint.memory import InMemorySaver
from langgraph.types import interrupt, Command

class Claim(TypedDict, total=False):
    text: str
    amount: int
    decision: str

def intake(s: Claim):
    return {"amount": 25_000}          # pretend we extracted it with an LLM

def route(s: Claim) -> Literal["approve", "human"]:
    return "approve" if s["amount"] < 10_000 else "human"

def human(s: Claim):
    verdict = interrupt({"question": f"Approve claim of {s['amount']}?"})   # pauses the graph
    return {"decision": verdict}

def approve(s: Claim):
    return {"decision": s.get("decision", "approved")}

g = StateGraph(Claim)
g.add_node("intake", intake); g.add_node("human", human); g.add_node("approve", approve)
g.add_edge(START, "intake")
g.add_conditional_edges("intake", route)
g.add_edge("human", "approve"); g.add_edge("approve", END)
app = g.compile(checkpointer=InMemorySaver())

cfg = {"configurable": {"thread_id": "claim-42"}}
print(app.invoke({"text": "water damage"}, cfg))        # stops at interrupt
print(app.invoke(Command(resume="approved"), cfg))      # a human resumes it later

Reading the code. The same thread_id ties the second call to the paused run. Nodes return only the keys they change. The routing function’s Literal return type documents the possible next nodes.

Trap. InMemorySaver forgets everything on restart. In production use a Postgres or Redis checkpointer.

5.6CrewAI — role-based multi-agent teams

In one line: define agents by role, goal, and backstory; define tasks with expected outputs; put them in a crew and let them collaborate.

Analogy. Assembling a newsroom: a researcher digs, a writer drafts, an editor polishes. Each has a job description; the crew is the newsroom.

from crewai import Agent, Task, Crew, Process

researcher = Agent(role="Market researcher", goal="Find facts about Indian UPI growth",
                   backstory="Ex-analyst who always cites sources.", allow_delegation=False)
writer = Agent(role="Business writer", goal="Write a crisp one-page brief",
               backstory="Writes for busy CXOs. Hates jargon.")

research = Task(description="Collect 5 key UPI statistics from the last two years with sources.",
                expected_output="Bullet list of facts with URLs", agent=researcher)
brief = Task(description="Turn the research into a one-page brief for a bank CTO.",
             expected_output="Markdown brief under 300 words", agent=writer, context=[research])

crew = Crew(agents=[researcher, writer], tasks=[research, brief], process=Process.sequential, verbose=True)
print(crew.kickoff())

flowchart LR
  R["Researcher agent"] -->|facts| W["Writer agent"]
  W -->|brief| OUT["Output"]

Reading the code. Role, goal and backstory become part of each agent’s prompt, so concrete wording (“always cites sources”) shapes behaviour. context=[research] passes the researcher’s output to the writer. expected_output is the acceptance criterion; make it specific.

Trap. More agents ≠ better results. Each hand-off loses context and adds cost. Start with one agent and split only when a role clearly needs different tools or instructions.

Read: CrewAI docs · CrewAI agents · CrewAI tasks

5.7Sequential vs hierarchical process

In one line: sequential runs tasks in a fixed order; hierarchical adds a manager agent that plans, delegates, and reviews.

Analogy. Sequential is an assembly line. Hierarchical is a project manager assigning tickets and checking work.

flowchart TB
  subgraph Sequential
    A1["Task 1"] --> A2["Task 2"] --> A3["Task 3"]
  end
  subgraph Hierarchical
    M["Manager"] --> W1["Worker A"]
    M --> W2["Worker B"]
    W1 --> M
    W2 --> M
  end
crew = Crew(
    agents=[researcher, writer],
    tasks=[research, brief],
    process=Process.hierarchical,
    manager_llm="gpt-4o",          # the manager plans and delegates
)
Sequential Hierarchical
Predictability High Lower
Cost Lower Higher (manager calls)
Best for Known pipelines Open-ended tasks needing re-planning

Choosing. If you can draw the steps in advance, use sequential. Use hierarchical only when the task needs dynamic delegation, and give the manager a stronger model than the workers.

5.8Agentic RAG and n8n automation

In one line: in agentic RAG the model decides whether to retrieve, which index to search, and whether the results are good enough; n8n can host the same pattern visually with an AI Agent node and vector-store tools.

Analogy. Classic RAG is a vending machine: press button, get snack. Agentic RAG is a personal shopper who decides which shops to visit and comes back if the first shop is out of stock.

flowchart LR
  Q["Question"] --> AG["Agent"]
  AG -->|policy question| T1["Search policy index"]
  AG -->|order question| T2["Query orders DB"]
  AG -->|current events| T3["Web search"]
  T1 --> AG
  T2 --> AG
  T3 --> AG
  AG --> ANS["Answer with sources"]
from langchain_core.tools import tool

@tool
def search_policies(query: str) -> str:
    """Search internal policy documents."""
    return "\n".join(d.page_content for d in policy_retriever.invoke(query))

@tool
def search_faq(query: str) -> str:
    """Search the public FAQ."""
    return "\n".join(d.page_content for d in faq_retriever.invoke(query))

agent = create_react_agent(ChatOpenAI(model="gpt-4o-mini"), tools=[search_policies, search_faq, get_order],
                           prompt="Use tools when facts are needed. Cite the tool output you used.")

n8n recipe. Chat Trigger → AI Agent node (model + memory) with tools: Vector Store Tool (Pinecone/Qdrant), HTTP Request Tool, Postgres Tool → respond. It is the same loop as the code above, built by connecting nodes, which suits teams that prefer low-code.

Trap. Tool descriptions are prompts. Vague descriptions (“search stuff”) make the agent pick the wrong tool. Say exactly what each tool contains and when to use it.

5.9Memory — short-term, long-term, episodic

In one line: short-term memory is the current conversation (thread state); long-term memory is facts stored across sessions (often in a vector store or key–value store); episodic memory is records of past runs the agent can learn from.

Analogy. Short-term: what you said 5 minutes ago in this meeting. Long-term: you know the client hates PDFs. Episodic: “last time we tried a bulk refund, the bank API timed out, so batch it”.

flowchart LR
  U["User turn"] --> ST["Short-term: thread messages, trimmed or summarised"]
  ST --> LLM["LLM"]
  LT[("Long-term store: preferences, facts")] -->|search by user id| LLM
  EP[("Episodes: past runs and outcomes")] -->|similar situations| LLM
  LLM -->|write new facts| LT
  LLM -->|log run| EP

Code

from langgraph.store.memory import InMemoryStore
store = InMemoryStore()
ns = ("user", "u-77", "prefs")
store.put(ns, "format", {"value": "prefers bullet points, no PDFs"})
store.put(ns, "lang", {"value": "replies in Hinglish"})

def recall(user_id: str) -> str:
    items = store.search(("user", user_id, "prefs"))
    return "; ".join(i.value["value"] for i in items)

print(recall("u-77"))

Short-term trimming keeps the prompt inside the context window:

from langchain_core.messages import trim_messages
trimmed = trim_messages(history, max_tokens=3000, token_counter=ChatOpenAI(model="gpt-4o-mini"),
                        strategy="last", include_system=True)

Reading the code. The namespace tuple scopes memories per user, which is also your privacy boundary. strategy="last" keeps the most recent messages and include_system=True always keeps the system prompt.

Trap. Long-term memory can store wrong or sensitive facts forever. Add expiry, let users see and delete memories, and do not store PII you do not need.

5.10Multi-agent orchestration — supervisor, peer-to-peer, fault isolation

In one line: a supervisor routes work to specialist agents and combines their results; peer-to-peer agents hand off directly; either way, one agent failing must not crash the whole system.

Analogy. An air-traffic controller (supervisor) versus pilots talking to each other on a shared frequency (peer-to-peer). Fault isolation: one plane’s engine trouble does not ground the airport.

flowchart TB
  U["User"] --> SUP["Supervisor"]
  SUP --> F["Flights agent"]
  SUP --> H["Hotels agent"]
  SUP --> B["Budget agent"]
  F -->|result or error| SUP
  H -->|result or error| SUP
  B -->|result or error| SUP
  SUP --> OUT["Combined plan, notes what failed"]

Code

import asyncio

async def call_agent(name, fn, task, timeout=20):
    try:
        return name, await asyncio.wait_for(fn(task), timeout)
    except Exception as e:                 # isolate the failure
        return name, {"error": type(e).__name__}

async def supervisor(task):
    results = await asyncio.gather(
        call_agent("flights", flights_agent, task),
        call_agent("hotels", hotels_agent, task),
        call_agent("budget", budget_agent, task),
    )
    ok = {n: r for n, r in results if "error" not in r}
    failed = [n for n, r in results if "error" in r]
    return await summarise_plan(ok, failed)     # tell the user what is missing

Reading the code. Each specialist runs under its own timeout and try/except, so a failure becomes data ({"error": ...}) instead of an exception that kills the run. The final summary reports what is missing, which is more honest than a silent partial answer.

Pattern Pros Cons
Supervisor Clear control, easy to audit Supervisor is a bottleneck
Peer-to-peer / swarm Flexible hand-offs Harder to debug and bound
Hierarchical teams Scales to many agents Many LLM calls

Trap. Free-form agent-to-agent chat is hard to bound. Always cap hops and total budget, and log every hand-off.

5.11LLM evaluation — RAGAS, DeepEval, Promptfoo, trajectory evaluation

In one line: evaluate final answers (correctness, faithfulness), and for agents also the trajectory: did it call the right tools, in a sensible order, without wasted steps?

Analogy. A driving test checks not only that you arrived (answer), but that you did not run red lights on the way (trajectory).

Core ideas

Use DeepEval for pytest-style tests in CI, Promptfoo to compare prompts and models side by side, and RAGAS for RAG metrics (Module 3). Trajectory checks catch agents that reach the right answer the wrong way, such as calling the refund tool twice.

# DeepEval: pytest-style LLM tests
from deepeval import assert_test
from deepeval.test_case import LLMTestCase
from deepeval.metrics import AnswerRelevancyMetric, FaithfulnessMetric

def test_refund_answer():
    case = LLMTestCase(input="What is the refund window?",
                       actual_output="You can get a refund within 30 days.",
                       retrieval_context=["Refunds are accepted within 30 days of purchase."])
    assert_test(case, [AnswerRelevancyMetric(threshold=0.7), FaithfulnessMetric(threshold=0.8)])

# promptfooconfig.yaml — compare prompts and models side by side
prompts: [file://prompts/support_v1.txt, file://prompts/support_v2.txt]
providers: [openai:gpt-4o-mini, anthropic:messages:claude-sonnet-4-5]
tests:
  - vars: {question: "I was charged twice"}
    assert:
      - type: icontains
        value: refund
      - type: llm-rubric
        value: Polite, does not ask for card number

def trajectory_score(actual_tools: list[str], expected: list[str]) -> dict:
    correct_order = all(t in actual_tools for t in expected) and \
                    [t for t in actual_tools if t in expected] == expected
    return {"used_expected": set(expected) <= set(actual_tools),
            "correct_order": correct_order,
            "extra_steps": len(actual_tools) - len(expected)}

print(trajectory_score(["get_order", "get_order", "create_refund"], ["get_order", "create_refund"]))

Reading the code. The thresholds make a test pass or fail, so quality regressions break the build. In trajectory_score, extra_steps measures waste: one extra get_order call here.

5.12Guardrails, injection defence, PII scrubbing, output filtering

In one line: wrap the model with input guards (PII masking, injection detection, topic limits) and output guards (schema validation, toxicity, leaked secrets), and decide in code what happens when a guard fails.

Analogy. Airport security on the way in, customs on the way out.

flowchart LR
  IN["User input"] --> PII["Mask PII with Presidio"]
  PII --> INJ["Injection and topic checks"]
  INJ --> LLM["LLM"]
  LLM --> OUTV["Validate: schema, toxicity, no secrets"]
  OUTV -->|pass| USER["User"]
  OUTV -->|fail| FIX["Reask, redact, or refuse"]

Code

from presidio_analyzer import AnalyzerEngine
from presidio_anonymizer import AnonymizerEngine

analyzer, anonymizer = AnalyzerEngine(), AnonymizerEngine()
text = "Hi, I'm Priya Sharma, my phone is 98200 12345 and email priya@example.com"
findings = analyzer.analyze(text=text, language="en")
print(anonymizer.anonymize(text=text, analyzer_results=findings).text)
# Hi, I'm <PERSON>, my phone is <PHONE_NUMBER> and email <EMAIL_ADDRESS>

# Guardrails AI: validators from the Hub (install with `guardrails hub install hub://guardrails/detect_pii`)
from guardrails import Guard
from guardrails.hub import DetectPII

guard = Guard().use(DetectPII(pii_entities=["EMAIL_ADDRESS", "PHONE_NUMBER"], on_fail="fix"))
print(guard.validate("Contact me at priya@example.com").validated_output)

Reading the code. Presidio finds entities, then the anonymiser replaces them with placeholders before text reaches the model or the logs. on_fail sets the policy: fix repairs, while other options refuse or re-ask. Treat prompt injection as a permanent risk: guards reduce it, the arbiter (5.2) contains it.

Trap. Presidio’s default recognisers are tuned for US formats. Add custom recognisers for Aadhaar, PAN, and Indian phone numbers before an Indian client deployment.

Boss level — The Retrieval Bake-Off

Boss level. “The Claims Desk”: a LangGraph claims agent with a Postgres checkpointer, an arbiter in front of payout tools, PII masking on input, and a human approval gate above ₹10,000, plus a DeepEval suite that runs in CI.

Suggested steps.

  1. Model the claim as typed state and draw the graph first (5.5).
  2. Add intake, assessment and payout nodes; swap InMemorySaver for a Postgres checkpointer.
  3. Put an arbiter in front of every payout tool with schema, limit and role checks (5.2).
  4. Mask PII on input with Presidio, with Indian recognisers added (5.12).
  5. Gate claims above ₹10,000 with interrupt and test the resume path (5.5).
  6. Write DeepEval and trajectory tests and run them in CI (5.11).

Appendix B — Debugging checklist for a failing RAG answer

Work down the list in order; most problems are in the first four items.

  1. Do you need an agent at all? If the steps are known, use a workflow (intro diagram).
  2. Is the agent looping? Check recursion_limit and step and cost budgets (5.1).
  3. Is it picking the wrong tool? Rewrite tool descriptions; they are prompts (5.8).
  4. Did a tool call get rejected? Read the arbiter’s reason in the audit log (5.2).
  5. Does a resumed run start from scratch? Check thread_id and the checkpointer (5.5).
  6. Is one failing agent breaking the run? Add timeouts and isolate errors (5.10).
  7. Is context overflowing? Trim or summarise short-term memory (5.9).
  8. Is the answer right but the path wasteful? Score the trajectory, not just the answer (5.11).
  9. Is untrusted text driving actions? Route high-risk tools through the arbiter and guard inputs (5.4, 5.12).

Appendix C — Final self-assessment

Answer without looking. Anything you cannot explain in two sentences is a chapter to revisit.

1. When is a workflow better than an agent?

When the steps are known in advance: it is cheaper and more predictable. (intro)

2. What is the difference between ReAct and planner–executor?

ReAct decides step by step; planner–executor plans first and re-plans on failure. (5.1)

3. Why must permissions be enforced in code, not by an LLM?

An LLM can be tricked or wrong; code gives guarantees. (5.2)

4. Which MCP primitive does the model decide to call?

Tools. (5.3)

5. Why is an MCP server a security risk?

It runs with your credentials, so only trusted servers should be installed. (5.3)

6. What must you return for each parallel tool call?

One tool message with the matching tool_call_id. (5.4)

7. What does a checkpointer enable?

Memory across turns, pause and resume, and replay per thread. (5.5)

8. How does a human resume an interrupted graph?

Invoke again with Command(resume=...) on the same thread_id. (5.5)

9. Why not start with many agents?

Each hand-off loses context and adds cost. (5.6)

10. Sequential or hierarchical for a known pipeline?

Sequential. (5.7)

11. Why are tool descriptions important?

The model reads them to choose tools, so they work as prompts. (5.8)

12. Name the three kinds of agent memory.

Short-term, long-term and episodic. (5.9)

13. How do you isolate failures in a supervisor design?

Timeouts and try/except per agent, returning errors as data. (5.10)

14. Why evaluate the trajectory?

An agent can reach the right answer through unsafe or wasteful steps. (5.11)

15. Why add custom Presidio recognisers?

Defaults target US formats and miss Aadhaar, PAN and Indian phones. (5.12)
