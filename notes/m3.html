3.1Embeddings — text-embedding-3, sentence-transformers, BGE

In one line: an embedding model maps text to a vector so that texts with similar meaning land close together.

Analogy. A map of a city where every sentence gets GPS coordinates. “Refund my money” and “I want my cash back” are neighbours; “KYC selfie” lives across town.

Why it matters for AI work. Keyword search fails when users phrase things differently from the documents. Embeddings let “money back” find a paragraph that only says “reimbursement”. Every semantic search, RAG system and recommender starts here.

Core ideas

What the vector is. A transformer reads the text and pools its token states into one list of numbers (384 to 3072 of them). No single number is human-readable; only distances between vectors carry meaning. The model is trained with contrastive learning: matching pairs are pulled together, random pairs pushed apart.

Asymmetric search. Questions are short and documents are long, so retrieval models such as BGE expect an instruction prefix on the query (for example “Represent this sentence for searching relevant passages:”) but not on documents. Forgetting it quietly lowers quality.

Choosing a model. Look at the retrieval column of the MTEB leaderboard rather than the overall score, then check language coverage, maximum input length, price and whether data may leave your network. Always test on 30 or more of your own questions.

Model Where it runs Notes
OpenAI text-embedding-3-small / -large API Strong default; the dimensions parameter can shrink vectors to save storage
all-MiniLM-L6-v2 Local CPU 384-d, fast, good for prototypes
BAAI/bge-* Local GPU or CPU Top open models; add the query instruction for retrieval

Code

from openai import OpenAI
from sentence_transformers import SentenceTransformer

texts = ["Refund my money", "I want my cash back", "Upload KYC selfie"]

oa = OpenAI()
api_vecs = [d.embedding for d in oa.embeddings.create(model="text-embedding-3-small", input=texts).data]
print(len(api_vecs[0]))  # 1536

local = SentenceTransformer("BAAI/bge-small-en-v1.5")
local_vecs = local.encode(texts, normalize_embeddings=True)
print(local_vecs.shape)  # (3, 384)

Reading the code.

  • embeddings.create accepts a list, so batch many texts per call instead of looping; it is faster and cheaper in overhead.
  • normalize_embeddings=True rescales each vector to length 1, so a plain dot product equals cosine similarity (chapter 3.2).
  • Cache embeddings by a hash of the text. Re-embedding unchanged documents is the most common source of wasted spend.

Trap. You must embed documents and queries with the same model. Switching models means re-embedding the whole corpus, so store the model name in your index metadata.

3.2Cosine similarity

In one line: cosine similarity measures the angle between two vectors: 1 = same direction (same meaning), 0 = unrelated, −1 = opposite.

cos(a, b) = (a · b) / (‖a‖ × ‖b‖)        ranges from -1 to 1

Analogy. Two people pointing. If they point the same way, they agree, no matter how long their arms are (vector length).

Why it matters for AI work. It is the ranking function behind almost every vector search. Understanding it explains why normalised vectors, inner-product indexes and “score thresholds” behave as they do.

Core ideas

Metrics compared. Cosine ignores length and looks at direction. Euclidean (L2) distance measures straight-line gap and is affected by length. Dot product mixes both. For normalised vectors all three give the same ranking, so use whichever your model card recommends.

Scores are relative. A score of 0.42 might be an excellent match for one model and a poor one for another. Use scores to rank, and set any cut-off from labelled examples of your own data.

Code

import numpy as np

def cosine(a, b):
    a, b = np.asarray(a), np.asarray(b)
    return float(a @ b / (np.linalg.norm(a) * np.linalg.norm(b)))

v = local.encode(texts, normalize_embeddings=True)
print(round(cosine(v[0], v[1]), 3), round(cosine(v[0], v[2]), 3))   # high, low

# With normalised vectors, cosine == dot product, which is why vector DBs use inner product
q = local.encode(["give me a refund"], normalize_embeddings=True)[0]
scores = v @ q
print(np.argsort(-scores))  # best matches first

Reading the code. v @ q multiplies every document vector by the query in one matrix operation, which is how brute-force search over thousands of chunks stays fast. argsort(-scores) sorts descending.

Trap. Similarity scores are not probabilities and are not comparable across models. Do not hard-code “0.8 means relevant” without checking your data.

3.3Vector databases — Pinecone, ChromaDB, FAISS

In one line: a vector store keeps vectors plus metadata and finds nearest neighbours fast using approximate indexes (HNSW, IVF).

Analogy. FAISS is a fast index card box in your backpack. Chroma is a small library with a librarian. Pinecone is a managed national library: someone else keeps the lights on.

Why it matters for AI work. Comparing a query with every vector is fine for 10,000 chunks and hopeless for 50 million. The store also gives you persistence, filtering, updates and access control.

Core ideas

Approximate nearest neighbour (ANN). Exact search is O(N). ANN trades a little recall for large speed-ups. HNSW builds a layered graph and hops towards the query (fast, memory-hungry). IVF clusters vectors and searches only the closest clusters. PQ compresses vectors to save RAM at a small accuracy cost.

FAISS Chroma Pinecone
Type Library Embedded or server DB Managed cloud
Metadata filters You build them Yes Yes
Best for Research, offline batch Prototypes, small apps Production scale without ops

Selection checklist. Persistence on disk? Metadata filters and multi-tenant isolation? Update and delete by id? Hybrid (keyword + vector) support? Cost at ten times today’s data? Qdrant, Weaviate, pgvector and Elasticsearch are strong alternatives.

Code

# FAISS: raw speed
import faiss, numpy as np
vecs = local.encode(["refund policy", "kyc rules", "fraud alerts"], normalize_embeddings=True).astype("float32")
index = faiss.IndexFlatIP(vecs.shape[1])     # inner product == cosine for normalised vectors
index.add(vecs)
scores, ids = index.search(local.encode(["money back"], normalize_embeddings=True).astype("float32"), k=2)

# Chroma via LangChain: persistence + metadata
from langchain_chroma import Chroma
from langchain_openai import OpenAIEmbeddings
store = Chroma(collection_name="policies", embedding_function=OpenAIEmbeddings(model="text-embedding-3-small"),
               persist_directory="./chroma")
store.add_texts(["Refunds within 30 days.", "KYC needs PAN and selfie."],
                metadatas=[{"team": "payments"}, {"team": "compliance"}])
print(store.similarity_search("how long for refunds", k=1, filter={"team": "payments"}))

Reading the code. IndexFlatIP is exact search with inner product, ideal up to a few hundred thousand vectors. FAISS returns integer positions, so you must keep your own id-to-text mapping. Chroma stores text and metadata together and applies the filter before ranking.

Trap. Forgetting metadata. In client work you almost always need filters: tenant id, document type, date, access level.

Read: FAISS wiki · Chroma docs · Pinecone docs · Qdrant docs

3.4Chunking strategies

In one line: how you split documents decides what can be retrieved; chunks must be small enough to be specific and large enough to make sense alone.

Analogy. Cutting a pizza. Slices too thin: no topping on any one slice. Too big: you cannot fit one in your mouth (context window).

Why it matters for AI work. Most “the model got it wrong” bugs in RAG are really “the right sentence was never retrieved” bugs, and chunking is the usual cause.

Core ideas

Strategy How Good for
Fixed size + overlap N characters/tokens, overlap 10–20% Quick baseline
Recursive Split on headings → paragraphs → sentences Most prose documents
Structure-aware Markdown/HTML headers, PDF sections, code functions Manuals, wikis, code
Semantic Split where embedding similarity drops Long unstructured text

Tuning. Start around 500 to 800 tokens with about 15% overlap, then evaluate with chapter 3.15. Prepend the section title to each chunk’s text, and store title, section and page as metadata so answers can cite them. Anthropic’s contextual retrieval goes further: an LLM writes one line of context per chunk before embedding.

flowchart LR
  DOC["Policy PDF"] --> H["Split by headings"]
  H --> P["Split long sections by paragraphs"]
  P --> O["Add 10-20 percent overlap"]
  O --> META["Attach metadata: title, section, page"]

Code

from langchain_text_splitters import RecursiveCharacterTextSplitter, MarkdownHeaderTextSplitter

splitter = RecursiveCharacterTextSplitter(chunk_size=800, chunk_overlap=120,
                                          separators=["\n## ", "\n\n", "\n", ". ", " "])
chunks = splitter.split_text(open("refund_policy.md").read())

md = MarkdownHeaderTextSplitter(headers_to_split_on=[("#", "h1"), ("##", "h2")])
sections = md.split_text(open("refund_policy.md").read())
print(sections[0].metadata)   # {'h1': 'Refund policy', 'h2': 'Eligibility'}

Reading the code. The recursive splitter tries the first separator, and only falls back to the next when a piece is still too big, so headings are preserved whenever possible. The header splitter does not size chunks; it gives you sections with heading metadata you can then split further.

Trap. Tables and lists split mid-row produce chunks that are meaningless alone. Keep tables whole, or convert each row to a sentence with its headers.

Read: Pinecone: chunking strategies · LangChain text splitters · Anthropic: contextual retrieval

3.5LangChain — LCEL, chains, retrievers, prompt templates

In one line: LCEL composes steps with the | pipe: retriever → prompt → model → parser, and you get streaming, batching, and async for free.

Analogy. Unix pipes for LLMs: cat docs | grep refund | summarise.

Why it matters for AI work. Clients ask for streaming answers, batch jobs and tracing. Building the chain from standard runnables gives you all three without custom plumbing.

Core ideas

  • Retriever: takes a string, returns documents.
  • Prompt template: fills variables into chat messages.
  • Runnable: anything with invoke, stream and batch. RunnablePassthrough forwards its input unchanged.
  • Output parser: turns the model message into a string or structured data.

A dict at the start of a chain runs its entries in parallel on the same input. Here one branch retrieves and formats, the other passes the question through, and both feed the prompt.

Code

from langchain_chroma import Chroma
from langchain_openai import ChatOpenAI, OpenAIEmbeddings
from langchain_core.prompts import ChatPromptTemplate
from langchain_core.output_parsers import StrOutputParser
from langchain_core.runnables import RunnablePassthrough

store = Chroma(persist_directory="./chroma", embedding_function=OpenAIEmbeddings(model="text-embedding-3-small"))
retriever = store.as_retriever(search_kwargs={"k": 4})

prompt = ChatPromptTemplate.from_messages([
    ("system", "Answer only from the context. If it is not there, say 'I don't know'. Cite [source]."),
    ("human", "Context:\n{context}\n\nQuestion: {question}"),
])

def format_docs(docs):
    return "\n\n".join(f"[{d.metadata.get('source', i)}] {d.page_content}" for i, d in enumerate(docs))

chain = (
    {"context": retriever | format_docs, "question": RunnablePassthrough()}
    | prompt
    | ChatOpenAI(model="gpt-4o-mini", temperature=0)
    | StrOutputParser()
)
print(chain.invoke("What is the refund window?"))
for token in chain.stream("Do you refund shipping?"):
    print(token, end="")

Reading the code. temperature=0 keeps answers stable for factual work. The system prompt does the grounding: only the context, an explicit “I don’t know” escape, and a citation format. format_docs labels each passage with its source so the model can cite it.

Trap. LangChain moves fast; imports change between versions. Pin versions in requirements.txt and read the version-specific docs.

Read: LCEL concepts · LangChain RAG tutorial · Retrievers

3.6End-to-end retrieval pipeline design

In one line: a production RAG system is two pipelines, offline indexing and online answering, plus evaluation and monitoring around both.

flowchart TB
  subgraph Offline
    SRC["S3, SharePoint, DB"] --> ING["Ingest + dedupe"] --> CL["Clean + PII mask"] --> CH["Chunk"] --> EMB["Embed"] --> IDX[("Index + metadata")]
  end
  subgraph Online
    U["User question"] --> RW["Rewrite / filters"] --> RET["Hybrid retrieve"] --> RR["Rerank"] --> GEN["Generate with citations"] --> GUARD["Guardrails"] --> ANS["Answer"]
  end
  IDX --> RET
  ANS --> LOGS["Traces + feedback"] --> EVAL["Offline evals"]

Analogy. A library: the back office catalogues new books overnight (indexing); the front desk answers questions all day (online), and the head librarian checks a sample of answers every week (evals).

Core ideas

  • Freshness: how often do documents change? Re-index incrementally by content hash and delete chunks of removed documents.
  • Access control: filter by the user’s permissions at retrieval time. Never retrieve everything and hide it afterwards.
  • Citations: return source ids and show them in the UI so users can verify.
  • Fallback: “I don’t know” beats a confident hallucination.
  • Cost and latency: embed once, cache frequent queries, give each stage a latency budget.
  • Observability: log the query, retrieved ids, scores, answer and user feedback; you cannot fix what you cannot see.

Code

import hashlib
def doc_id(text: str, source: str) -> str:
    return hashlib.sha256(f"{source}:{text}".encode()).hexdigest()[:16]
# Upsert by id: unchanged chunks are skipped, edited chunks replace old ones.
store.add_texts(texts=chunks, ids=[doc_id(c, "refund_policy.md") for c in chunks],
                metadatas=[{"source": "refund_policy.md"}] * len(chunks))

Reading the code. The id is a hash of source plus text, so an unchanged chunk gets the same id and is overwritten with identical content, while an edited chunk gets a new id. Track the old ids per source so you can remove stale ones.

3.7Parent-document retriever and contextual compression

In one line: search with small chunks for precision, but hand the model the larger parent section for context; compress retrieved text to only the relevant sentences.

Analogy. You find the right sentence with a highlighter, then read the whole paragraph around it so you do not miss the “except when…”.

Core ideas

Small chunks embed one idea cleanly, which makes matching sharp, but they lose neighbouring conditions such as “except for digital goods”. The parent retriever matches the child and returns its parent. A compressor then trims the parent down to the sentences that answer the question, saving tokens.

flowchart LR
  Q["Query"] --> SMALL["Search small child chunks"]
  SMALL --> MAP["Map child to parent id"]
  MAP --> BIG["Return parent section"]
  BIG --> COMP["Compressor keeps relevant sentences"]
  COMP --> LLM["LLM"]

Code

from langchain.retrievers import ParentDocumentRetriever, ContextualCompressionRetriever
from langchain.retrievers.document_compressors import LLMChainExtractor
from langchain.storage import InMemoryStore
from langchain_text_splitters import RecursiveCharacterTextSplitter

parent_retriever = ParentDocumentRetriever(
    vectorstore=store,
    docstore=InMemoryStore(),
    child_splitter=RecursiveCharacterTextSplitter(chunk_size=300),
    parent_splitter=RecursiveCharacterTextSplitter(chunk_size=2000),
)
parent_retriever.add_documents(documents)

compressor = LLMChainExtractor.from_llm(ChatOpenAI(model="gpt-4o-mini", temperature=0))
compressed = ContextualCompressionRetriever(base_compressor=compressor, base_retriever=parent_retriever)
docs = compressed.invoke("Are digital goods refundable?")

Trap. LLM-based compression adds a model call per document. Measure latency; an embeddings-based filter is often enough. InMemoryStore is lost on restart, so use a persistent docstore in production.

Read: Parent document retriever how-to · Contextual compression how-to

3.8RAG evaluation with RAGAS

In one line: score retrieval and generation separately: did we fetch the right context (context recall/precision), and is the answer supported by it (faithfulness) and on-topic (answer relevancy)?

Analogy. Grading an open-book exam. Did the student open the right pages? Did their answer actually come from those pages? Did they answer the question asked?

Core ideas

Metric Question it answers Needs ground truth?
Faithfulness Is every claim supported by retrieved context? No
Answer relevancy Does the answer address the question? No
Context precision Are the top-ranked chunks the relevant ones? Usually
Context recall Did we retrieve everything needed? Yes (reference answer)

Reading the scores. Low recall: fix retrieval (chunking, hybrid search, larger k). Low precision: add reranking or filters. Low faithfulness: tighten the prompt and lower temperature. Low relevancy: the question was misunderstood; consider query rewriting.

flowchart LR
  G["Golden set: 50-200 Q + reference"] --> RUN["Run pipeline"]
  RUN --> S["RAGAS scores"]
  S --> CMP["Compare with last version"]
  CMP -->|better| SHIP["Ship"]
  CMP -->|worse| FIX["Investigate chunks or prompts"]

Code

from ragas import evaluate, EvaluationDataset
from ragas.metrics import Faithfulness, ResponseRelevancy, LLMContextRecall
from ragas.llms import LangchainLLMWrapper
from langchain_openai import ChatOpenAI

samples = [{
    "user_input": "What is the refund window?",
    "retrieved_contexts": ["Refunds are accepted within 30 days of purchase."],
    "response": "You can request a refund within 30 days.",
    "reference": "30 days from purchase.",
}]
judge = LangchainLLMWrapper(ChatOpenAI(model="gpt-4o-mini"))
result = evaluate(EvaluationDataset.from_list(samples),
                  metrics=[Faithfulness(), ResponseRelevancy(), LLMContextRecall()], llm=judge)
print(result)

Trap. RAGAS uses an LLM as judge, so scores are noisy. Use enough questions, fix the judge model, and spot-check by hand. The RAGAS API changes between versions; check the docs for yours.

Read: RAGAS docs · RAGAS metrics · Ragas + LangSmith (LangChain blog)

3.9Context window — stuff, map-reduce, refine, lost in the middle

In one line: when retrieved text is large, either stuff it all in, summarise pieces then combine (map-reduce), or update an answer chunk by chunk (refine), and put the best chunks at the edges.

Analogy. Reading 40 reports for your boss. Stuff: read all, answer once. Map-reduce: summarise each, then summarise the summaries. Refine: keep a running memo and update it after each report.

Core ideas

Approach Calls Good when
Stuff 1 Context fits comfortably
Map-reduce N + 1, parallel Summaries of many docs
Refine N, sequential Order matters, need nuance

Lost in the middle. Research shows models use information at the start and end of a long prompt better than the middle. Reorder retrieved chunks so the strongest sit at the edges.

Code

def reorder_for_edges(docs):
    """Lost in the middle: put the most relevant docs first and last."""
    docs = list(docs)                         # assume sorted best -> worst
    front, back = docs[0::2], docs[1::2]
    return front + back[::-1]

print(reorder_for_edges(["d1", "d2", "d3", "d4", "d5"]))   # ['d1', 'd3', 'd5', 'd4', 'd2']

Trap. A 1M-token window does not mean you should use it. Long prompts are slower, pricier, and models still miss details in the middle.

Read: Lost in the Middle paper · LangChain summarization tutorial

3.10BM25 keyword search

In one line: BM25 scores documents by matching query words, rewarding rare words and penalising very long documents. It is great for ids, codes, and names.

Analogy. Embeddings understand that “automobile” ≈ “car”. BM25 is the colleague who instantly finds “error code E-4471” because it literally appears in the text.

Core ideas

The score combines three effects: term frequency (more occurrences help, with diminishing returns controlled by k1), inverse document frequency (rare words matter more than “the”), and length normalisation (controlled by b, so long documents do not win just by being long). It needs no training and no GPU, and it is explainable: you can see which words matched.

Code

from rank_bm25 import BM25Okapi

corpus = ["Error E-4471 means KYC document expired",
          "Refunds take 5 to 7 business days",
          "Selfie mismatch triggers manual review"]
tokenised = [doc.lower().split() for doc in corpus]
bm25 = BM25Okapi(tokenised)
print(bm25.get_scores("e-4471 kyc".split()))
print(bm25.get_top_n("refund days".split(), corpus, n=1))

Trap. Naive .split() tokenisation misses “refunds” vs “refund”. Use proper tokenisation, lowercasing, and optionally stemming.

Read: Okapi BM25 (Wikipedia) · rank_bm25 · Elastic: practical BM25

3.11HyDE — hypothetical document embeddings

In one line: ask the LLM to write a fake answer, embed that, and search with it, because fake answers look more like real documents than short questions do.

Analogy. Instead of asking the librarian “books on sad robots?”, you describe a made-up book jacket. It is easier to find books that look like your jacket.

flowchart LR
  Q["Short question"] --> LLM["LLM writes hypothetical answer"]
  LLM --> E["Embed the hypothetical answer"]
  E --> S["Vector search"]
  S --> REAL["Real documents"]

Code

def hyde_search(question: str, k: int = 4):
    fake = ChatOpenAI(model="gpt-4o-mini", temperature=0.3).invoke(
        f"Write a short passage from a company policy that answers: {question}").content
    return store.similarity_search(fake, k=k)

hyde_search("can I get money back for an e-book?")

Reading the code. The fake passage may be factually wrong; that is fine, because only its style and vocabulary are used to find real text. The real documents, not the fake, go to the final prompt.

Trap. HyDE adds an LLM call and can hallucinate jargon that pulls in wrong documents. Evaluate it against plain query embedding.

Read: HyDE paper: Precise Zero-Shot Dense Retrieval · LangChain: hypothetical document embeddings

3.12Reciprocal rank fusion (RRF)

In one line: merge ranked lists by summing 1 / (k + rank) for each document, with no need to compare BM25 scores with cosine scores.

Analogy. Two judges rank singers. You do not compare their score scales; you just reward singers who are near the top on both lists.

Core ideas

Only ranks are used, so the incompatible score scales never matter. The constant k (usually 60) softens the advantage of rank 1 over rank 2. RRF needs no tuning and is a robust first hybrid method.

Code

from collections import defaultdict

def rrf(*rankings: list[str], k: int = 60) -> list[tuple[str, float]]:
    scores = defaultdict(float)
    for ranking in rankings:
        for rank, doc_id in enumerate(ranking, start=1):
            scores[doc_id] += 1.0 / (k + rank)
    return sorted(scores.items(), key=lambda kv: kv[1], reverse=True)

bm25_rank = ["d3", "d1", "d7"]
vector_rank = ["d1", "d9", "d3"]
print(rrf(bm25_rank, vector_rank))   # d1 and d3 rise to the top

flowchart LR
  Q["Query"] --> B["BM25 ranking"]
  Q --> V["Vector ranking"]
  B --> F["RRF sum 1 over k plus rank"]
  V --> F
  F --> TOP["Fused top-k"]

3.13Alpha-weighting BM25 and dense retrieval

In one line: hybrid score = α × dense + (1 − α) × sparse, after normalising both to 0–1; tune α on your eval set.

Analogy. A mixing desk with one slider: left is “exact words”, right is “meaning”. Product codes want the slider left; vague questions want it right.

Core ideas

Compared with RRF, alpha weighting keeps score magnitudes (a very strong BM25 hit stays strong) and gives you a tunable knob, but it needs normalisation and an eval set. A cheap improvement is a query-dependent alpha: lean on keywords when the query contains digits or codes.

Code

import numpy as np

def minmax(x):
    x = np.asarray(x, dtype=float)
    return (x - x.min()) / (x.max() - x.min() + 1e-9)

def hybrid_scores(bm25_scores, dense_scores, alpha=0.6):
    return alpha * minmax(dense_scores) + (1 - alpha) * minmax(bm25_scores)

def pick_alpha(query: str) -> float:
    has_code = any(ch.isdigit() for ch in query) or "-" in query
    return 0.3 if has_code else 0.7

q = "error E-4471"
print(hybrid_scores([12.1, 0.4, 0.0], [0.42, 0.40, 0.38], alpha=pick_alpha(q)))

Trap. Raw BM25 scores are unbounded and dense scores are not. Without normalisation, one side silently dominates.

Read: Weaviate: hybrid search explained · Pinecone: hybrid search

3.14Cross-encoder reranking

In one line: retrieve about 50 candidates cheaply, then score each (query, passage) pair jointly with a cross-encoder and keep the best 5.

Analogy. The bi-encoder is a recruiter skimming 1,000 CVs by keywords. The cross-encoder is the hiring manager who carefully interviews the 50 shortlisted.

flowchart LR
  Q["Query"] --> BI["Bi-encoder or BM25: top 50, fast"]
  BI --> CE["Cross-encoder scores each pair, slower"]
  CE --> TOP["Top 5 to the LLM"]

Core ideas

A bi-encoder embeds query and passage separately, so passage vectors are precomputed and search is fast. A cross-encoder reads them together with full attention, which is far more accurate but must run per pair at query time. That is why it is used only on a shortlist.

Code

from sentence_transformers import CrossEncoder

reranker = CrossEncoder("cross-encoder/ms-marco-MiniLM-L-6-v2")
query = "how long do refunds take"
candidates = ["Refunds take 5 to 7 business days", "Refund requests need an order id",
              "KYC review takes 24 hours"]
scores = reranker.predict([(query, c) for c in candidates])
ranked = sorted(zip(candidates, scores), key=lambda x: x[1], reverse=True)
print(ranked[0])

Trap. Cross-encoders are slow on long passages and large candidate sets. Cap candidates (20–100) and passage length. Hosted rerankers such as Cohere Rerank avoid running the model yourself.

3.15Evaluate hybrid search against a pure-vector baseline

In one line: same golden questions, several retrievers, retrieval metrics (hit rate, MRR, recall@k), then the winner goes to RAGAS end-to-end.

Analogy. A taste test with the labels hidden. You do not trust the chef who says “mine is better”; you count votes.

Core ideas

  • Hit rate@k: share of questions with at least one relevant document in the top k.
  • MRR: mean of 1/rank of the first relevant document; rewards putting it first.
  • Recall@k: share of all relevant documents found.

Code

def hit_rate_and_mrr(retrieve, golden, k=5):
    hits, rr = 0, 0.0
    for item in golden:                             # {"q": ..., "relevant_ids": {...}}
        ids = retrieve(item["q"], k)
        for rank, doc_id in enumerate(ids, start=1):
            if doc_id in item["relevant_ids"]:
                hits += 1
                rr += 1 / rank
                break
    n = len(golden)
    return {"hit_rate": hits / n, "mrr": rr / n}

Appendix B — Debugging checklist for a failing RAG answer

Work down the list in order; most problems are in the first four items.

  1. Is the answer in your documents at all? Search the raw text. If not, no retriever can help.
  2. Was the document indexed? Check ingestion logs and chunk counts for that source.
  3. Is the right chunk in the top 20? Inspect retrieved ids and scores directly, without the LLM.
  4. Is the chunk readable alone? Tables, pronouns and missing headings make chunks useless; fix chunking (3.4).
  5. Do query and documents use the same embedding model? A silent mismatch ruins every score (3.1).
  6. Is it an exact-term problem? Codes and names need BM25 or hybrid search (3.10, 3.12).
  7. Is the right chunk retrieved but ranked low? Add a reranker (3.14) or raise the candidate count.
  8. Retrieved but ignored? Reorder for the edges (3.9), shorten context, strengthen the prompt (3.5).
  9. Is the answer unsupported? Check faithfulness (3.8); lower temperature and require citations.

Appendix C — Final self-assessment

Answer without looking. Anything you cannot explain in two sentences is a chapter to revisit.

1. Why must queries and documents share an embedding model?

Vectors from different models live in different spaces, so distances between them mean nothing. (3.1)

2. Why do vector databases use inner product?

With normalised vectors it equals cosine similarity and is cheaper to compute. (3.2)

3. What do metadata filters give you in production?

Tenant isolation, access control, and scoping by type or date. (3.3)

4. Why add overlap between chunks?

So a sentence at a boundary is not cut in half in both chunks. (3.4)

5. What does the dict at the start of an LCEL chain do?

Runs its entries in parallel on the same input and passes the results on as a dict. (3.5)

6. Where should access control be applied?

At retrieval time, as a filter, never after generation. (3.6)

7. What problem does the parent-document retriever solve?

Small chunks match precisely but lack context; it returns the larger parent. (3.7)

8. Which RAGAS metric needs a reference answer?

Context recall. (3.8)

9. What is the “lost in the middle” effect?

Models use information at the start and end of a prompt better than the middle. (3.9)

10. When does BM25 beat embeddings?

For exact tokens such as error codes, ids and names. (3.10)

11. What is the risk of HyDE?

An extra call, and hallucinated jargon can retrieve the wrong documents. (3.11)

12. Why does RRF not need score normalisation?

It uses ranks only, not scores. (3.12)

13. Why normalise before alpha-weighting?

BM25 is unbounded and cosine is not, so one side would dominate. (3.13)

14. Why rerank only a shortlist?

Cross-encoders run per pair at query time and are slow. (3.14)

15. What do hit rate and MRR each measure?

Hit rate: any relevant result in top k. MRR: how high the first relevant result ranks. (3.15)
