6.1FastAPI — async endpoints, SSE streaming, auth, rate limiting

In one line: FastAPI gives you typed request/response models, async handlers, automatic docs at /docs, and streaming responses for token-by-token chat.

Analogy. A restaurant front counter: the menu is the OpenAPI schema, Pydantic checks every order slip, and streaming is serving dishes as they leave the kitchen instead of waiting for the whole table’s order.

Core ideas

Pydantic models validate input before your code runs. A Depends function applies auth to any route. Server-sent events (SSE) stream tokens over plain HTTP, so users see text immediately and time to first token drops. A rate limiter protects both your wallet and your provider quota.

Code

# app.py — pip install fastapi uvicorn slowapi openai
import os, json
from fastapi import FastAPI, Depends, Header, HTTPException, Request
from fastapi.responses import StreamingResponse
from pydantic import BaseModel
from slowapi import Limiter, _rate_limit_exceeded_handler
from slowapi.util import get_remote_address
from slowapi.errors import RateLimitExceeded
from openai import AsyncOpenAI

app = FastAPI(title="Policy Assistant")
limiter = Limiter(key_func=get_remote_address)
app.state.limiter = limiter
app.add_exception_handler(RateLimitExceeded, _rate_limit_exceeded_handler)
llm = AsyncOpenAI()

class Ask(BaseModel):
    question: str

def require_key(x_api_key: str = Header(...)):
    if x_api_key != os.environ["SERVICE_API_KEY"]:
        raise HTTPException(401, "invalid api key")

@app.get("/healthz")
async def health():
    return {"ok": True}

@app.post("/ask/stream", dependencies=[Depends(require_key)])
@limiter.limit("20/minute")
async def ask_stream(request: Request, body: Ask):
    async def events():
        stream = await llm.chat.completions.create(
            model="gpt-4o-mini", stream=True,
            messages=[{"role": "user", "content": body.question}])
        async for chunk in stream:
            delta = chunk.choices[0].delta.content if chunk.choices else None
            if delta:
                yield f"data: {json.dumps({'token': delta})}\n\n"
        yield "data: [DONE]\n\n"
    return StreamingResponse(events(), media_type="text/event-stream")

uvicorn app:app --reload --port 8000
curl -N -X POST localhost:8000/ask/stream -H "x-api-key: $SERVICE_API_KEY" \
     -H "content-type: application/json" -d '{"question":"What is RAG?"}'

Reading the code. Each SSE message is data: ... followed by a blank line. /healthz is the endpoint load balancers and Kubernetes probe. curl -N disables buffering so you can watch tokens arrive.

Trap. async def handlers that call blocking libraries freeze the event loop for every user. Use async clients, or plain def handlers (FastAPI runs those in a thread pool).

6.2Docker — Dockerfile, Compose, slim images

In one line: a Dockerfile builds an image (your app plus its exact dependencies); Compose runs several containers together (API + Chroma + Redis) with one command.

Analogy. A shipping container: whatever is inside, every crane and ship in the world knows how to move it. “Works on my machine” becomes “works on every machine”.

Code

# Dockerfile — multi-stage, slim, non-root
FROM python:3.12-slim AS build
WORKDIR /app
COPY requirements.txt .
RUN pip install --no-cache-dir --prefix=/install -r requirements.txt

FROM python:3.12-slim
WORKDIR /app
COPY --from=build /install /usr/local
COPY src/ ./src/
COPY prompts/ ./prompts/
RUN useradd -m appuser
USER appuser
EXPOSE 8000
CMD ["uvicorn", "src.policy_assistant.api:app", "--host", "0.0.0.0", "--port", "8000"]

# compose.yaml
services:
  api:
    build: .
    ports: ["8000:8000"]
    env_file: .env
    depends_on: [chroma, redis]
    environment:
      CHROMA_HOST: chroma
      REDIS_URL: redis://redis:6379/0
  chroma:
    image: chromadb/chroma:latest
    volumes: ["chroma-data:/data"]
  redis:
    image: redis:7-alpine
volumes:
  chroma-data:

docker compose up --build
docker compose logs -f api
docker image ls            # check the image size

Reading the code. The first stage installs dependencies; the second copies only the result, so build tools never reach production. Running as appuser limits damage if the app is compromised. Inside Compose, services reach each other by name (chroma, redis).

Trap. Copying the whole repo before pip install breaks layer caching: every code change reinstalls all dependencies. Copy requirements.txt first. Add a .dockerignore (.venv, .env, notebooks/).

Read: Docker get started · Multi-stage builds · Docker Compose · Dockerfile best practices

6.3GitHub Actions CI/CD — test, build, push, deploy, prompt regression

In one line: a workflow YAML runs on every push: install, lint, unit tests, LLM evals, build the image, push it, and deploy if everything is green.

Analogy. A factory quality line. Every product (commit) passes the same inspection stations; one failure stops it from leaving the building.

flowchart LR
  PR["Pull request"] --> T["Unit tests"] --> E["LLM evals"] --> M{"Merge to main?"}
  M -->|yes| B["Build image"] --> P["Push to ECR"] --> D["Deploy"]
  E -->|score drops| X["Fail the check"]

Code

# .github/workflows/ci.yml
name: ci
on:
  push: { branches: [main] }
  pull_request:
jobs:
  test:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-python@v5
        with: { python-version: "3.12", cache: pip }
      - run: pip install -r requirements.txt -r requirements-dev.txt
      - run: pytest -q
      - name: Prompt regression
        env: { OPENAI_API_KEY: "${{ secrets.OPENAI_API_KEY }}" }
        run: npx promptfoo@latest eval -c promptfooconfig.yaml --fail-on-error
  deploy:
    needs: test
    if: github.ref == 'refs/heads/main'
    runs-on: ubuntu-latest
    environment: production
    permissions: { id-token: write, contents: read }
    steps:
      - uses: actions/checkout@v4
      - uses: aws-actions/configure-aws-credentials@v4
        with: { role-to-assume: "${{ secrets.AWS_DEPLOY_ROLE }}", aws-region: ap-south-1 }
      - uses: aws-actions/amazon-ecr-login@v2
        id: ecr
      - run: |
          IMAGE=${{ steps.ecr.outputs.registry }}/policy-assistant:${{ github.sha }}
          docker build -t $IMAGE . && docker push $IMAGE
          echo "IMAGE=$IMAGE" >> $GITHUB_ENV
      - run: aws ecs update-service --cluster prod --service policy-assistant --force-new-deployment

Reading the code. needs: test blocks deployment on a failing test job. id-token: write plus role-to-assume is OIDC: GitHub gets short-lived AWS credentials, so no long-lived keys sit in secrets. Tagging images with the commit SHA makes every deployment traceable and roll-back-able.

Trap. Running full LLM evals on every commit gets expensive. Run a small smoke set on PRs and the full suite nightly or before release.

Read: GitHub Actions docs · Workflow syntax · Configure AWS credentials with OIDC

6.4Environments and secrets — staging vs production

In one line: the same image runs everywhere; only configuration differs, injected at runtime from environment variables and a secret store, never baked into the image.

Analogy. The same actor plays in two theatres; only the props list (config) changes per venue.

Local Staging Production
Config source .env Secrets Manager / GitHub env Secrets Manager
Model Cheap or local Same as prod Prod
Data Fake Masked copy Real
Who can deploy You CI on merge CI + approval 
from pydantic_settings import BaseSettings, SettingsConfigDict

class Settings(BaseSettings):
    model_config = SettingsConfigDict(env_file=".env", extra="ignore")
    env: str = "local"
    openai_api_key: str
    model: str = "gpt-4o-mini"
    chroma_host: str = "localhost"
    log_level: str = "INFO"

settings = Settings()      # fails at startup if OPENAI_API_KEY is missing

Reading the code. A typed settings class fails fast: a missing key stops the container at startup instead of failing on the first user request. Staging should mirror production (same model, same image) so a staging pass means something.

Trap. Printing settings in logs prints your secrets. Use SecretStr for keys so they show as **********.

6.5Kubernetes — deployments, services, limits, autoscaling

In one line: a Deployment keeps N copies (pods) of your container running; a Service gives them one stable address; resource requests/limits keep neighbours fair; the HPA adds pods when CPU (or another metric) rises.

Analogy. A franchise. The Deployment says “always keep 3 branches open”; the Service is the single phone number that routes to any branch; the HPA opens more branches during the festival rush.

flowchart LR
  ING["Ingress"] --> SVC["Service"]
  SVC --> P1["Pod 1"]
  SVC --> P2["Pod 2"]
  SVC --> P3["Pod 3"]
  HPA["HPA"] -.->|scales| DEP["Deployment"]
  DEP --> P1
  DEP --> P2
  DEP --> P3

Code

apiVersion: apps/v1
kind: Deployment
metadata: { name: policy-api }
spec:
  replicas: 3
  selector: { matchLabels: { app: policy-api } }
  template:
    metadata: { labels: { app: policy-api } }
    spec:
      containers:
        - name: api
          image: 123456789.dkr.ecr.ap-south-1.amazonaws.com/policy-assistant:abc123
          ports: [{ containerPort: 8000 }]
          envFrom: [{ secretRef: { name: policy-api-secrets } }]
          resources:
            requests: { cpu: "250m", memory: "512Mi" }
            limits:   { cpu: "1",    memory: "1Gi" }
          readinessProbe: { httpGet: { path: /healthz, port: 8000 }, periodSeconds: 5 }
---
apiVersion: v1
kind: Service
metadata: { name: policy-api }
spec:
  selector: { app: policy-api }
  ports: [{ port: 80, targetPort: 8000 }]
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata: { name: policy-api }
spec:
  scaleTargetRef: { apiVersion: apps/v1, kind: Deployment, name: policy-api }
  minReplicas: 2
  maxReplicas: 10
  metrics:
    - type: Resource
      resource: { name: cpu, target: { type: Utilization, averageUtilization: 70 } }

kubectl apply -f k8s/
kubectl get pods -w
kubectl logs deploy/policy-api -f
kubectl rollout undo deploy/policy-api      # instant rollback

Reading the code. Requests are what the scheduler reserves; limits are the ceiling. The readiness probe keeps traffic away from a pod until /healthz answers. The Service finds pods by label, not by name.

Trap. LLM-calling APIs are usually I/O-bound, so CPU stays low while requests queue. Scale on request rate or latency (custom metrics) rather than CPU alone.

Read: Kubernetes concepts · Deployments · Services · Horizontal Pod Autoscaling · Resource management

6.6Helm charts and ingress controllers

In one line: Helm packages Kubernetes YAML as a templated, versioned chart with per-environment values; an ingress controller (NGINX, AWS Load Balancer Controller) turns Ingress rules into a real HTTP entry point.

Analogy. Helm is a recipe with blanks (“add {{ salt }} grams”); values-prod.yaml fills the blanks for the big restaurant, values-dev.yaml for your home kitchen.

charts/policy-api/
├── Chart.yaml
├── values.yaml
├── values-prod.yaml
└── templates/
    ├── deployment.yaml
    ├── service.yaml
    └── ingress.yaml

# templates/deployment.yaml (excerpt)
spec:
  replicas: {{ .Values.replicas }}
  template:
    spec:
      containers:
        - name: api
          image: "{{ .Values.image.repository }}:{{ .Values.image.tag }}"

# templates/ingress.yaml
apiVersion: networking.k8s.io/v1
kind: Ingress
metadata:
  name: policy-api
spec:
  ingressClassName: nginx
  rules:
    - host: {{ .Values.host }}
      http:
        paths:
          - path: /
            pathType: Prefix
            backend: { service: { name: policy-api, port: { number: 80 } } }

helm install policy-api charts/policy-api -f charts/policy-api/values-prod.yaml --set image.tag=abc123
helm upgrade policy-api charts/policy-api --set image.tag=def456
helm rollback policy-api 1

Reading the code. CI can deploy by changing only image.tag. Helm keeps numbered releases, so helm rollback returns to a known-good revision.

Trap. Streaming responses through an ingress often get buffered or cut by idle timeouts. Raise proxy timeouts and disable buffering for SSE routes.

Read: Helm docs · Kubernetes Ingress · Ingress-NGINX docs

6.7Terraform — infrastructure as code and state

In one line: you declare the infrastructure you want in .tf files; terraform plan shows the diff, apply makes it real, and the state file remembers what exists.

Analogy. An architect’s blueprint. You do not tell builders “add a brick”; you hand them the drawing, and they work out what needs changing.

terraform {
  required_providers { aws = { source = "hashicorp/aws", version = "~> 5.0" } }
  backend "s3" {
    bucket         = "acme-tf-state"
    key            = "policy-assistant/prod.tfstate"
    region         = "ap-south-1"
    dynamodb_table = "tf-locks"          # state locking
  }
}
provider "aws" { region = var.region }
variable "region" { default = "ap-south-1" }
variable "env"    { default = "prod" }

resource "aws_ecr_repository" "api" {
  name = "policy-assistant"
  image_scanning_configuration { scan_on_push = true }
}
resource "aws_s3_bucket" "docs" {
  bucket = "acme-policy-docs-${var.env}"
}
output "ecr_url" { value = aws_ecr_repository.api.repository_url }

terraform init
terraform plan -out plan.tfplan
terraform apply plan.tfplan
terraform destroy          # only in sandboxes!

flowchart LR
  CODE[".tf files"] --> PLAN["terraform plan: diff"]
  STATE[("Remote state in S3 + lock")] --> PLAN
  PLAN --> APPLY["terraform apply"]
  APPLY --> CLOUD["AWS resources"]
  APPLY --> STATE

Reading the code. The s3 backend stores state remotely and the DynamoDB table locks it so two people cannot apply at once. Saving the plan to a file means apply executes exactly what you reviewed. Always read the plan for unexpected destroy lines.

Trap. Local state files get lost or conflict between teammates. Use remote state with locking from day one, and never hand-edit resources in the console that Terraform manages.

Read: Terraform docs · Terraform state · AWS provider docs · Terraform tutorials

-- pgvector on RDS
CREATE EXTENSION IF NOT EXISTS vector;
CREATE TABLE chunks (id bigserial PRIMARY KEY, source text, content text, embedding vector(1536));
CREATE INDEX ON chunks USING hnsw (embedding vector_cosine_ops);
SELECT source, content FROM chunks ORDER BY embedding <=> $1 LIMIT 5;

Reading the code. A presigned URL gives temporary access (here 300 seconds) to one private object without making the bucket public. In pgvector, <=> is cosine distance and the HNSW index (Module 3) makes it fast; one database can hold both app data and vectors.

6.9Secrets — AWS Secrets Manager and Vault

In one line: store secrets centrally with access control, audit logs, and rotation; the app or platform fetches them at runtime using its IAM identity.

Analogy. A hotel safe with a log of every time it was opened, versus a key taped under the doormat (.env in production).

import json, boto3
from functools import lru_cache

@lru_cache
def secret(name: str) -> dict:
    sm = boto3.client("secretsmanager", region_name="ap-south-1")
    return json.loads(sm.get_secret_value(SecretId=name)["SecretString"])

openai_key = secret("prod/policy-assistant")["OPENAI_API_KEY"]

ECS can inject secrets directly into environment variables via the task definition (secrets: [{name, valueFrom: arn...}]), so your code just reads os.environ.

# HashiCorp Vault
vault kv put secret/policy-assistant OPENAI_API_KEY=sk-...
vault kv get -field=OPENAI_API_KEY secret/policy-assistant

flowchart LR
  TASK["ECS task with IAM role"] -->|GetSecretValue| SM["Secrets Manager"]
  SM --> AUDIT["CloudTrail audit log"]
  ROT["Rotation Lambda"] -.->|rotates| SM

Reading the code. lru_cache avoids calling Secrets Manager on every request. The task’s IAM role is its identity, so there are no keys to store. Rotation changes a secret centrally without redeploying code.

Trap. Giving the task role secretsmanager:* on *. Grant read access to only the specific secret ARNs the service needs.

6.10Spot instances, autoscaling, and always-on inference cost

In one line: spot capacity is 60–90% cheaper but can be reclaimed with short notice: great for batch jobs and training, risky for a single always-on model server.

Analogy. Standby airline tickets: cheap, but you may get bumped. Fine for a flexible trip (batch embedding), not for your wedding (production chat).

def monthly(hourly, hours=730, count=1): return hourly * hours * count

on_demand_gpu = monthly(1.20)            # example: one GPU instance
spot_gpu = monthly(0.40)
min_two_for_ha = monthly(1.20, count=2)
print(f"on-demand ${on_demand_gpu:,.0f}  spot ${spot_gpu:,.0f}  HA pair ${min_two_for_ha:,.0f}")
Workload Capacity choice
Nightly embedding / re-index Spot, with checkpoints
Fine-tuning runs Spot, frequent checkpoints
Stateless API (calls an LLM API) Fargate on-demand base + Fargate Spot burst
Self-hosted model serving On-demand base, spot for overflow, scale-to-zero off hours if allowed

  BASE["Base capacity: on-demand, always on"] --> SERVE["Serve traffic"]
  BURST["Burst capacity: spot"] --> SERVE
  SCALE["Autoscaler on queue depth or latency"] -.-> BURST

Trap. A self-hosted GPU costs the same at 3 a.m. with zero users. Always compare with API pricing at your real traffic curve.

6.11LangSmith — tracing, cost, latency, debugging

In one line: LangSmith records every LLM call, retrieval, and tool step as a trace tree with inputs, outputs, tokens, latency, and cost, and lets you turn bad traces into eval datasets.

Analogy. A flight data recorder for your AI. When the answer crashes, you replay exactly what happened.

export LANGSMITH_TRACING=true
export LANGSMITH_API_KEY=lsv2_...
export LANGSMITH_PROJECT=policy-assistant-prod

from langsmith import traceable
from langsmith.wrappers import wrap_openai
from openai import OpenAI

client = wrap_openai(OpenAI())          # every call is traced automatically

@traceable(name="retrieve")
def retrieve(q: str) -> list[str]:
    return ["Refunds within 30 days."]

@traceable(name="answer", metadata={"prompt_version": "answer_v3"})
def answer(q: str) -> str:
    ctx = retrieve(q)
    r = client.chat.completions.create(model="gpt-4o-mini",
        messages=[{"role": "user", "content": f"{ctx}\n\n{q}"}])
    return r.choices[0].message.content

answer("What is the refund window?")

Reading the code. @traceable creates a span, and nested calls become child spans, giving a tree like answer → retrieve + model call. The prompt_version metadata lets you filter traces by prompt, which pays off during regressions.

Trap. Traces contain user prompts. Configure redaction or masking before sending production traffic, and check where the data is stored for compliance.

Read: LangSmith docs · LangSmith observability quickstart · Arize Phoenix (open-source alternative)

6.12Structured logging with correlation IDs

In one line: generate one request id at the edge, pass it through every service and log line (and into traces), so one search shows the whole story of a request.

Analogy. A courier tracking number. Every depot scans the same number, so you can see exactly where the parcel got stuck.

import uuid, contextvars, logging
from fastapi import FastAPI, Request

request_id = contextvars.ContextVar("request_id", default="-")

class RequestIdFilter(logging.Filter):
    def filter(self, record):
        record.request_id = request_id.get()
        return True

logging.basicConfig(format='{"ts":"%(asctime)s","lvl":"%(levelname)s","rid":"%(request_id)s","msg":"%(message)s"}')
log = logging.getLogger("api")
log.addFilter(RequestIdFilter())
log.setLevel(logging.INFO)

app = FastAPI()

@app.middleware("http")
async def add_request_id(request: Request, call_next):
    rid = request.headers.get("x-request-id") or str(uuid.uuid4())
    request_id.set(rid)
    response = await call_next(request)
    response.headers["x-request-id"] = rid
    return response

@app.get("/ask")
async def ask(q: str):
    log.info("retrieval_start")
    # pass rid downstream: httpx headers={"x-request-id": request_id.get()}
    return {"ok": True}

Reading the code. A ContextVar holds the id per request, even with async code running concurrently, and the logging filter stamps it on every line. Accepting an incoming x-request-id keeps one id across services, and returning it in the response lets a user quote it in a bug report.

Read: OpenTelemetry: context propagation · W3C Trace Context · Python contextvars

6.13Load testing with Locust, SLOs, alert thresholds

In one line: simulate realistic users to find where latency and errors break; set SLOs (for example “p95 under 3 s, 99.5% success”) and alert on burning through the error budget.

Analogy. Testing a bridge with trucks before opening it to the public, then putting a sign on it saying the maximum safe load.

# locustfile.py — locust -f locustfile.py --host http://localhost:8000
from locust import HttpUser, task, between

class Asker(HttpUser):
    wait_time = between(1, 4)

    @task(3)
    def common_question(self):
        self.client.post("/ask", json={"question": "What is the refund window?"},
                         headers={"x-api-key": "test"}, name="/ask common")

    @task(1)
    def long_question(self):
        self.client.post("/ask", json={"question": "Compare refund rules for digital and physical goods"},
                         headers={"x-api-key": "test"}, name="/ask long")
SLI SLO Alert when
Success rate 99.5% over 30 days Burn rate above 2x for 1 hour
p95 latency (non-streaming) under 3 s p95 above 4 s for 10 min
Time to first token (streaming) under 1 s p95 above 1.5 s for 10 min
Cost per request under $0.003 Daily spend above budget

Reading the code. @task(3) makes the common question three times as likely as the long one, mimicking real traffic. Look for the knee: the user count where latency suddenly explodes. Set capacity and SLOs below it. An SLO of 99.5% gives an error budget of 0.5%, and alerts fire when you burn it too fast.

Trap. Load testing against the real LLM API burns money and hits provider rate limits. Use a mock LLM server for capacity tests, and a small real-API test for end-to-end numbers.

Read: Locust docs · Google SRE book: service level objectives · Google SRE workbook: alerting on SLOs

6.14Guardrails AI and the OpenAI moderation API

In one line: run a cheap moderation check on inputs and outputs, and validators (PII, schema, banned topics) around the model, with a defined action on failure.

Analogy. A bouncer at the door (input moderation) and a manager checking what leaves the kitchen (output validation).

from openai import OpenAI
client = OpenAI()

def moderate(text: str) -> bool:
    r = client.moderations.create(model="omni-moderation-latest", input=text)
    result = r.results[0]
    if result.flagged:
        flagged = [k for k, v in result.categories.model_dump().items() if v]
        print("blocked:", flagged)
    return not result.flagged

user_text = "How do I reset my password?"
if moderate(user_text):
    pass     # call the main model, then moderate(output) before returning

flowchart LR
  I["Input"] --> MI{"Moderation ok?"}
  MI -->|no| REF["Polite refusal + log"]
  MI -->|yes| G["Guarded LLM call"]
  G --> MO{"Output validators ok?"}
  MO -->|no| FIX["Re-ask or redact"]
  MO -->|yes| OUT["Return"]

Reading the code. The function returns a simple boolean so the calling code decides the action (refuse, log, escalate). Moderate the output too, since a safe prompt can still produce an unsafe answer. See Module 5 (5.12) for PII masking and injection defence.

Trap. Moderation APIs catch harmful content, not business-policy violations (“do not promise refunds”). Those need your own validators and evals.

6.15DeepEval in CI and Promptfoo prompt regression

In one line: treat prompts like code: every change runs an eval suite, and a score drop fails the build.

Analogy. Unit tests stop you breaking a function; prompt regression tests stop you breaking the personality and accuracy of your assistant.

# DeepEval: tests live next to unit tests
deepeval test run tests/evals/test_answers.py

# Promptfoo: compare prompt versions and fail on regression
npx promptfoo@latest eval -c promptfooconfig.yaml
npx promptfoo@latest view          # local web UI of results

# promptfooconfig.yaml (excerpt)
defaultTest:
  assert:
    - type: latency
      threshold: 4000
    - type: cost
      threshold: 0.003
tests: file://tests/evals/golden.yaml

flowchart LR
  CH["Prompt or model change"] --> PR["Pull request"]
  PR --> SMOKE["Smoke evals: 20 cases"]
  SMOKE -->|pass| REVIEW["Human review"]
  REVIEW --> MAIN["Merge"]
  MAIN --> FULL["Nightly full evals: 300 cases"]
  FULL -->|drop| ALERT["Alert + open issue"]

Reading the code. Latency and cost assertions make performance regressions fail builds just like wrong answers. The golden file is a version-controlled set of questions and expectations; grow it from real bad traces (6.11).

Trap. Flaky LLM judges cause flaky CI. Use deterministic checks (contains, JSON schema, regex) wherever possible and reserve LLM-as-judge for nuanced criteria with thresholds that tolerate noise.

6.16LLMOps — why non-deterministic AI needs different ops

In one line: classic ops watches “is it up and fast?”; LLMOps also watches “is it still right?”, “what did it cost?”, and “did the provider silently change the model?”.

Analogy. Running a restaurant where the chef is brilliant but occasionally improvises a new dish without telling anyone. You need tasting (evals), receipts (cost tracking), and a recipe book under version control (prompts).

Classic DevOps LLMOps adds
Uptime, latency, errors Answer quality, groundedness, refusal rate
Code versioning Prompt, model, and dataset versioning
Unit tests Eval suites and LLM judges
Logs Traces of prompts, retrievals, and tool calls
Infra cost Token cost per feature, per customer
Deploy rollback Prompt/model rollback, provider fallback 
flowchart LR
  DEV["Develop prompts and chains"] --> EVAL["Offline evals"]
  EVAL --> DEPLOY["Deploy with versions"]
  DEPLOY --> MON["Monitor quality, cost, latency"]
  MON --> FEED["User feedback + bad traces"]
  FEED --> DATA["Grow eval dataset"]
  DATA --> EVAL
FALLBACKS = ["gpt-4o-mini", "claude-haiku-4-5", "local-llama"]

def complete_with_fallback(prompt, call):
    last = None
    for model in FALLBACKS:
        try:
            return model, call(model, prompt)
        except Exception as e:          # rate limit, outage, timeout
            last = e
    raise RuntimeError("all providers failed") from last

Reading the code. The loop tries providers in order and returns which model answered, which you should log. Pin exact model versions where the provider allows, and re-run evals whenever a provider announces a change.

Appendix B — Debugging checklist for a failing RAG answer

Work down the list in order; most problems are in the first four items.

  1. Does it run in the container the same way? Run the exact image locally with the same env vars (6.2).
  2. Did CI fail on evals? Open the failing case; check for judge flakiness before blaming the prompt (6.15).
  3. Is a pod crash-looping? kubectl logs and describe; check readiness probe and memory limit (6.5).
  4. Is streaming cut off or buffered? Raise ingress timeouts and disable buffering for SSE (6.6).
  5. Did Terraform plan show a destroy? Stop and read it; check for manual console changes (6.7).
  6. Is the secret missing at startup? Check the task role, secret ARN and settings class (6.4, 6.9).
  7. Is latency high but CPU low? The service is I/O-bound; scale on latency or request rate (6.5).
  8. Cannot trace one request? Confirm the correlation id is logged and propagated (6.12).
  9. Is cost above plan? Compare cost per request to the SLO and check always-on GPUs (6.10, 6.13).
  10. Did quality drop after a provider change? Re-run the full eval suite and compare traces (6.11, 6.16).

Appendix C — Final self-assessment

Answer without looking. Anything you cannot explain in two sentences is a chapter to revisit.

1. Why does a blocking call in an async handler hurt?

It freezes the event loop for all users. (6.1)

2. Why copy requirements.txt before the code?

So dependency layers stay cached when only code changes. (6.2)

3. What does OIDC avoid in CI?

Long-lived cloud keys stored as secrets. (6.3)

4. Why use a typed settings class?

It fails fast at startup if config is missing. (6.4)

5. Requests vs limits?

Requests are reserved by the scheduler; limits are the ceiling. (6.5)

6. Why scale an LLM API on latency, not CPU?

It is I/O-bound, so CPU stays low while requests queue. (6.5)

7. What does helm rollback do?

Returns to a previous numbered release. (6.6)

8. Why use remote state with locking?

Prevents lost state and concurrent applies. (6.7)

9. What is a presigned URL?

A temporary link to a private S3 object. (6.8)

10. Why scope secret access to specific ARNs?

Least privilege limits damage if a role is compromised. (6.9)

11. Which workloads suit spot capacity?

Batch embedding and training with checkpoints. (6.10)

12. What does a trace show?

The timed tree of calls, tokens and cost for one request. (6.11)

13. Why return the request id in the response?

Users can quote it to find the exact logs. (6.12)

14. What is the “knee” in a load test?

The load where latency suddenly explodes. (6.13)

15. What do moderation APIs not catch?

Your business-policy violations. (6.14)

16. Why track provider and prompt versions?

Non-deterministic systems can change behaviour silently. (6.16)
