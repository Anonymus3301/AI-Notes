4.1Query rewriting and multi-hop retrieval

In one line: rewrite vague questions into good search queries, and for questions that need several facts, decompose them and retrieve once per hop.

Analogy. “Who approved the vendor that caused last month’s outage?” is two questions wearing a trench coat: (1) which vendor caused the outage, (2) who approved that vendor.

Core ideas

Users type short, ambiguous questions; documents use different words. A rewriting step fixes the query before retrieval. For multi-part questions, the answer to hop 1 becomes input to hop 2, so a single search can never find both facts.

flowchart LR
  Q["Complex question"] --> D["Decompose into sub-questions"]
  D --> H1["Hop 1: retrieve + answer"]
  H1 --> H2["Hop 2: query uses hop 1 answer"]
  H2 --> S["Synthesise with citations from each hop"]

Code

from langchain_openai import ChatOpenAI
llm = ChatOpenAI(model="gpt-4o-mini", temperature=0)

def decompose(q: str) -> list[str]:
    text = llm.invoke(f"Break this into the minimal ordered sub-questions, one per line:\n{q}").content
    return [line.strip("- ").strip() for line in text.splitlines() if line.strip()]

def multi_hop(q: str, retriever):
    notes = []
    for sub in decompose(q):
        query = llm.invoke(f"Known so far: {notes}\nRewrite as a search query: {sub}").content
        docs = retriever.invoke(query)
        ans = llm.invoke(f"Answer briefly from context only.\nContext: {docs}\nQ: {sub}").content
        notes.append({"q": sub, "a": ans, "sources": [d.metadata.get("source") for d in docs]})
    return llm.invoke(f"Answer '{q}' using these findings and cite sources:\n{notes}").content

Reading the code. notes carries earlier answers into later rewrites, which is what makes it multi-hop. Sources are kept per hop so the final answer can cite each fact.

Other tricks: multi-query (generate 3 to 5 paraphrases and union the results), step-back (ask a more general question first), and extracting filters (dates, product names) from the question.

Trap. Every hop multiplies latency and cost and can drift. Cap the hops (2 to 3), and stop early when a hop finds nothing.

Read: LangChain MultiQueryRetriever · Step-back prompting paper · Least-to-most prompting paper

4.2Cross-encoder reranking as a pipeline stage

In one line: in advanced RAG, reranking is not optional: retrieve wide (top 30–50), rerank, then keep a small, high-precision context.

Analogy. Casting: open auditions pull in 40 people; the director’s callback picks five; if nobody is good enough, you do not cast someone anyway.

Core ideas

Wide retrieval protects recall; reranking restores precision so the prompt holds only strong passages. The reranker score also enables a threshold: if even the best passage scores low, answer “I don’t know” or ask a clarifying question instead of guessing.

import cohere
co = cohere.ClientV2()   # reads CO_API_KEY

def rerank(query: str, docs: list[str], top_n=5):
    r = co.rerank(model="rerank-v3.5", query=query, documents=docs, top_n=top_n)
    return [(docs[x.index], x.relevance_score) for x in r.results]

flowchart LR
  R["Hybrid retrieve 40"] --> RR["Rerank"] --> T["Top 5"] --> TH{"Best score above threshold?"}
  TH -->|yes| GEN["Generate"]
  TH -->|no| IDK["Say I don't know or ask a clarifying question"]

Trap. A reranker threshold tuned on one domain will not transfer to another. Re-tune on each client’s golden set.

Read: Cohere Rerank docs · Sentence Transformers cross-encoders

4.3Self-correcting RAG — CRAG, Self-RAG, agentic RAG

In one line: grade the retrieved documents; if they are weak, rewrite the query or search elsewhere; grade the answer for grounding before returning it.

Analogy. A student who checks the textbook, realises it is the wrong chapter, goes back, and finally checks their answer against the page before handing it in.

flowchart TD
  Q["Question"] --> RET["Retrieve"]
  RET --> G{"Docs relevant?"}
  G -->|yes| GEN["Generate"]
  G -->|no| RW["Rewrite query or web search"]
  RW --> RET
  GEN --> H{"Answer grounded in docs?"}
  H -->|yes| OUT["Return"]
  H -->|no| GEN

Code

from typing import TypedDict
from langgraph.graph import StateGraph, START, END

class S(TypedDict):
    question: str; docs: list; answer: str; tries: int

def retrieve(s): return {"docs": retriever.invoke(s["question"])}
def grade(s):
    verdict = llm.invoke(f"Are these docs relevant to '{s['question']}'? yes/no\n{s['docs']}").content
    return "generate" if "yes" in verdict.lower() or s["tries"] >= 2 else "rewrite"
def rewrite(s):
    return {"question": llm.invoke(f"Rewrite for better search: {s['question']}").content,
            "tries": s["tries"] + 1}
def generate(s):
    return {"answer": llm.invoke(f"Answer from context only.\n{s['docs']}\nQ: {s['question']}").content}

g = StateGraph(S)
g.add_node("retrieve", retrieve); g.add_node("rewrite", rewrite); g.add_node("generate", generate)
g.add_edge(START, "retrieve")
g.add_conditional_edges("retrieve", grade, {"generate": "generate", "rewrite": "rewrite"})
g.add_edge("rewrite", "retrieve"); g.add_edge("generate", END)
app = g.compile()
print(app.invoke({"question": "refund for damaged item?", "tries": 0})["answer"])

Reading the code. The graph is a state machine: nodes update shared state, and grade is a conditional edge choosing the next node. The tries counter guarantees the loop ends.

Pattern Key idea
CRAG A lightweight grader decides: use docs, discard, or fall back to web search
Self-RAG Model emits reflection tokens deciding when to retrieve and whether output is supported
Agentic RAG An agent decides which tool or index to search, possibly several times

Trap. Loops without a counter become infinite loops with a credit card attached. Always cap retries.

Read: CRAG paper · Self-RAG paper · LangGraph agentic RAG tutorial

4.4LoRA and QLoRA (bitsandbytes 4-bit)

In one line: LoRA freezes the base model and trains two tiny matrices per layer; QLoRA does that on top of a 4-bit quantised base, so a 7–8B model fine-tunes on one consumer GPU.

Analogy. Instead of repainting the whole house (full fine-tune), you add removable wallpaper to a few walls (LoRA). QLoRA also shrinks the house to a dollhouse so it fits in your garage (4-bit) while you wallpaper it.

Why it matters for AI work. Full fine-tuning an 8B model needs far more GPU memory than most teams have. LoRA makes specialised models affordable, and the adapter is only a few MB to ship.

Core ideas

Full update: W' = W + ΔW      (ΔW is d × d, millions of params)
LoRA:        W' = W + B·A     (B is d × r, A is r × d, r ≈ 8–64)
Trainable params drop by 100–1000×.

flowchart LR
  X["Input"] --> W["Frozen W, 4-bit in QLoRA"]
  X --> A["A: r x d, trainable"]
  A --> B["B: d x r, trainable"]
  W --> SUM["Add"]
  B --> SUM
  SUM --> Y["Output"]

Key knobs. r (rank) sets adapter capacity; lora_alpha scales its effect (often 2×r); target_modules chooses which layers get adapters. QLoRA adds NF4 4-bit weights, double quantisation, and bf16 compute.

Code

import torch
from transformers import AutoModelForCausalLM, AutoTokenizer, BitsAndBytesConfig
from peft import LoraConfig, get_peft_model, prepare_model_for_kbit_training

base = "meta-llama/Llama-3.1-8B-Instruct"
bnb = BitsAndBytesConfig(load_in_4bit=True, bnb_4bit_quant_type="nf4",
                         bnb_4bit_compute_dtype=torch.bfloat16, bnb_4bit_use_double_quant=True)
model = AutoModelForCausalLM.from_pretrained(base, quantization_config=bnb, device_map="auto")
tok = AutoTokenizer.from_pretrained(base)
model = prepare_model_for_kbit_training(model)
lora = LoraConfig(r=16, lora_alpha=32, lora_dropout=0.05, task_type="CAUSAL_LM",
                  target_modules=["q_proj", "k_proj", "v_proj", "o_proj"])
model = get_peft_model(model, lora)
model.print_trainable_parameters()   # e.g. trainable params: 13.6M || all params: 8.0B || 0.17%

Trap. Fine-tuning does not reliably teach new facts; it teaches behaviour (format, style, a narrow skill). For facts, use RAG.

Read: LoRA paper · QLoRA paper · Hugging Face: 4-bit with bitsandbytes

4.5Adapters, prefix tuning — transformers, PEFT, datasets

In one line: PEFT is a library of parameter-efficient methods (LoRA, prefix tuning, prompt tuning, IA3); datasets loads and formats training data; transformers + TRL run the training.

Analogy. The base model is a camera body. Adapters are lenses: swap a macro lens (legal summaries) for a zoom lens (SQL generation) without buying a new camera.

Method What is trained Typical use
LoRA Low-rank matrices in attention/MLP Default choice
Prefix tuning Learned key/value vectors prepended per layer Generation tasks, very small budgets
Prompt tuning Soft prompt embeddings only Huge models, many tasks
IA3 Learned scaling vectors Even fewer params than LoRA

Code

from datasets import load_dataset
from trl import SFTTrainer, SFTConfig

ds = load_dataset("json", data_files="train.jsonl", split="train")   # {"messages": [...]} rows
trainer = SFTTrainer(
    model=model,                      # the PEFT-wrapped model from 4.4
    train_dataset=ds,
    processing_class=tok,
    args=SFTConfig(output_dir="out/lora", per_device_train_batch_size=2, gradient_accumulation_steps=8,
                   num_train_epochs=2, learning_rate=2e-4, logging_steps=10, bf16=True, report_to="wandb"),
)
trainer.train()
model.save_pretrained("out/lora-adapter")   # only a few MB

Each training row is one conversation:

{"messages": [{"role": "system", "content": "Return SQL only."},
              {"role": "user", "content": "Total refunds last week by city"},
              {"role": "assistant", "content": "SELECT city, SUM(amount) FROM refunds WHERE ... GROUP BY city;"}]}

Reading the code. Batch size 2 with 8 accumulation steps behaves like an effective batch of 16 while using little memory. Saving only the adapter keeps the artefact small, and you can load several adapters on one base model.

Trap. Data quality beats data quantity. 500 clean, consistent examples outperform 20,000 noisy ones.

Read: PEFT docs · Transformers docs · Datasets docs · Prefix-tuning paper

4.6Fine-tuning with Axolotl (YAML)

In one line: Axolotl wraps the whole fine-tuning pipeline in one YAML file: model, dataset format, adapter, and hyperparameters.

Analogy. A meal kit. The recipe card (YAML) lists everything; you do not have to write the cooking script yourself.

# qlora.yml
base_model: meta-llama/Llama-3.1-8B-Instruct
load_in_4bit: true
adapter: qlora
lora_r: 16
lora_alpha: 32
lora_dropout: 0.05
lora_target_linear: true
datasets:
  - path: data/train.jsonl
    type: chat_template
val_set_size: 0.05
sequence_len: 2048
sample_packing: true
micro_batch_size: 2
gradient_accumulation_steps: 8
num_epochs: 2
learning_rate: 0.0002
optimizer: adamw_bnb_8bit
lr_scheduler: cosine
bf16: auto
output_dir: ./outputs/qlora-sql
wandb_project: specialist

pip install axolotl
axolotl preprocess qlora.yml          # tokenise and check the data
axolotl train qlora.yml
axolotl inference qlora.yml --lora-model-dir ./outputs/qlora-sql
axolotl merge-lora qlora.yml          # optional: merge adapter into base weights

Reading the config. val_set_size holds out 5% for eval loss, sample_packing fills each sequence with several short examples for speed, and merge-lora bakes the adapter into the weights for simpler deployment.

Trap. Always run preprocess and inspect a few tokenised samples. A wrong chat template silently trains the model on garbage.

Read: Axolotl docs · Axolotl GitHub

4.8Distillation, RLHF, and DPO with TRL

In one line: distillation trains a small model to imitate a big one; RLHF trains a reward model on human preferences and optimises against it; DPO skips the reward model and learns directly from chosen-vs-rejected pairs.

Analogy. Distillation is an apprentice copying a master chef. RLHF is a food critic scoring dishes and the chef chasing higher scores. DPO is simply showing the chef “this plate, not that one” many times.

flowchart LR
  SFT["SFT model"] --> RM["Reward model from human rankings"]
  RM --> PPO["PPO optimise against reward"]
  SFT --> DPO["DPO on chosen vs rejected pairs"]
  PPO --> A["Aligned model"]
  DPO --> A

Code

from datasets import load_dataset
from trl import DPOTrainer, DPOConfig

# rows: {"prompt": "...", "chosen": "...", "rejected": "..."}
pairs = load_dataset("json", data_files="prefs.jsonl", split="train")
trainer = DPOTrainer(model=model, ref_model=None, train_dataset=pairs, processing_class=tok,
                     args=DPOConfig(output_dir="out/dpo", beta=0.1, per_device_train_batch_size=2,
                                    learning_rate=5e-6, num_train_epochs=1, bf16=True))
trainer.train()

Distillation recipe. Generate high-quality answers with a large model on your task prompts, filter them with evals, then SFT a small model on that data. (Check provider terms of service before training on another model’s outputs.) In DPO, beta controls how far the model may drift from the reference.

Trap. DPO with a high learning rate destroys general ability fast. Use small learning rates and evaluate on a general benchmark too, not only your task.

Read: TRL docs · DPO paper · Illustrating RLHF (Hugging Face) · Knowledge distillation paper (Hinton et al.)

4.9Training monitoring with Weights & Biases

In one line: log loss, learning rate, eval scores, and sample generations live, so you can kill a bad run in minutes instead of hours.

Analogy. The dashboard in your car. You would not drive across the country with the dashboard taped over.

import wandb
wandb.init(project="specialist", config={"r": 16, "lr": 2e-4, "base": "llama-3.1-8b"})
for step in range(100):
    wandb.log({"train/loss": 2.0 * 0.97 ** step, "lr": 2e-4})
table = wandb.Table(columns=["prompt", "output"])
table.add_data("Total refunds by city", "SELECT city, SUM(amount) ...")
wandb.log({"samples": table})
wandb.finish()

What to watch. Training loss falling smoothly; eval loss rising while training loss falls (overfitting); gradient-norm spikes (instability); GPU memory and utilisation (waste). Logging sample generations catches problems loss curves hide, such as the model rambling past the answer.

flowchart LR
  TL["Train loss falling"] --> OK{"Eval loss also falling?"}
  OK -->|yes| GOOD["Keep training"]
  OK -->|no, rising| STOP["Overfitting: stop or add data"]

4.11GGUF quantisation — Q4_K_M and Q8_0

In one line: GGUF is the llama.cpp file format for quantised models; the suffix says how many bits each weight uses and which scheme.

Analogy. Photo compression. Q8 is a high-quality JPEG (barely different), Q4 is a smaller JPEG (fine for most uses), Q2 is a meme screenshot of a screenshot.

Quant Bits per weight (approx.) 8B model size (approx.) Quality
F16 16 16 GB Reference
Q8_0 8.5 8.5 GB Near-lossless
Q5_K_M 5.7 5.7 GB Very good
Q4_K_M 4.8 4.9 GB Popular default
Q2_K 2.6 3.2 GB Noticeably worse

Rule of thumb: model memory ≈ parameters × bits ÷ 8, plus KV cache for your context length.

ollama pull llama3.1:8b-instruct-q4_K_M
ollama pull llama3.1:8b-instruct-q8_0
# llama.cpp directly:
llama-cli -m Llama-3.1-8B-Instruct-Q4_K_M.gguf -p "Hello" -n 64

Trap. Quality loss shows up first on reasoning, maths, and non-English text. Run your own eval set on each quant before choosing.

4.13Model selection and cost–performance trade-offs

In one line: choose the cheapest model that passes your eval bar at your latency target, and compare API cost per call with the all-in cost of hosting.

Analogy. Taxi vs owning a car. Few trips: taxi (API). Driving all day every day: owning (self-hosting) can win, if you also count insurance, parking, and maintenance (ops time).

def api_monthly(calls_per_day, tok_in, tok_out, price_in, price_out):
    return calls_per_day * 30 * (tok_in * price_in + tok_out * price_out) / 1e6

def selfhost_monthly(gpu_hourly, gpus=1, hours=24 * 30, ops_overhead=1.3):
    return gpu_hourly * gpus * hours * ops_overhead

print(f"API:       ${api_monthly(50_000, 1200, 200, 0.15, 0.60):,.0f}/month")
print(f"Self-host: ${selfhost_monthly(1.2):,.0f}/month")
Option Quality Latency Monthly cost Data leaves VPC?
Large API model ★★★★★ Medium $$$ Yes
Small API model ★★★★ Fast $ Yes
Fine-tuned 8B, self-hosted ★★★★ on task Fast $$ fixed No
Local 8B Q4, no tuning ★★★ Fast $ fixed No

Boss level — The Retrieval Bake-Off

Boss level. “The Specialist”: QLoRA-tune an 8B model on 1,000 text-to-SQL examples for one client schema, then show it beats a much larger general model on accuracy and cost on a held-out set.

Suggested steps.

  1. Write 1,000 clean examples in chat format (4.5) and hold out 100 for testing.
  2. Train with QLoRA via Axolotl on a rented GPU (4.4, 4.6, 4.7); watch eval loss in W&B (4.9).
  3. Merge or load the adapter and serve it locally (4.10, 4.11).
  4. Run the held-out set through your model and a large API model; record exact-match or execution accuracy.
  5. Build the cost-per-1,000-queries table (4.13) and recommend one option.

Appendix B — Debugging checklist for a failing RAG answer

Work down the list in order; most problems are in the first four items.

  1. Is prompting enough? Try a stronger prompt and examples before any training (intro flowchart).
  2. Is the problem knowledge or behaviour? Knowledge: RAG. Behaviour or format: fine-tune (4.4).
  3. Is the data clean and consistent? Read 50 random rows; fix contradictions first (4.5).
  4. Does the chat template match the model? Run preprocess and inspect tokenised samples (4.6).
  5. Is eval loss rising? You are overfitting: fewer epochs, more data, lower rank (4.9).
  6. Did general ability collapse? Lower the learning rate, check a general benchmark (4.8).
  7. Did quantisation hurt quality? Compare Q4 and Q8 on your own eval set (4.11).
  8. Is the licence compatible with the client? Read it before deployment (4.12).
  9. Does the cost table still favour your choice? Recompute with real volume and ops time (4.13).

Appendix C — Final self-assessment

Answer without looking. Anything you cannot explain in two sentences is a chapter to revisit.

1. Why can one search not answer a multi-hop question?

The second fact depends on the first answer, so you must retrieve in sequence. (4.1)

2. Why retrieve 40 and keep 5?

Wide retrieval protects recall; reranking restores precision. (4.2)

3. What stops a self-correcting RAG loop?
